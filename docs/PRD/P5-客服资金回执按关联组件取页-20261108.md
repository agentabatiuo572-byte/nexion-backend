## 最小实现约定

- 完整参与方闭包确定后，沿用原关联组件算法并只计算一次；该步骤只处理已读取的参与方元数据，不增加业务验证或提前读取 JSON。组件遍历顺序保持。
- 全局目录仍按原 ID 升序、每256项读取，原 wrapper 对象及其全局列表位置保持。主循环、前驱或原始回执查找、coverage 所见的 `ops` 不重排，也不替换 wrapper。
- 另建按组件连续排列的 JSON ID 引用及 `int[]` 路由，将原全局 index 映射到 JSON position。每32项子页重新按 ID 升序，保持原完整13字段查询、返回 ID 集合和顺序核对。所有原 ID 均保留；无参与方的 ID 仍保留在路由末尾，不增加新的异常分类。
- 相邻组件的尾项可能共用一页；不按组件分别创建缓存。仍只有一个最多8页、估算8MiB的局部 LRU，超限页仍仅保留当前页；原字符串字节估算、物理只读 RR 连接检查、MyBatis 清理与续租回调保持。路由只存 ID 引用和整数，不存全历史 JSON。

保留 `validateRaw → authBirth → directReversals → 主循环 → coverage → replay`、组件内 operation 顺序及全部 RAW、摘要、协议、来源、金额、历史、资格和 UNKNOWN 判断。不修改写入、摘要、Legacy UVT 投影、接口、页面、金融配置或原压力工具门槛。

## 适用边界与风险

该调整减少跨组件长期交错的取页；同一组件超过局部窗口的整遍回访、跨操作引用及不同后台物理快照仍可能重新读取，不承诺每份 JSON 全程只读一次。少量短组件可能增加单组件首次访问的 SQL 次数；实际 I/O、耗时及堆表现须沿原完整业务观察。

在同一物理 RR、查询按契约返回既有 ID 行时，各 wrapper 得到的完整内容及业务校验次序不变。取页组合和请求时点改变；数据库查询失败或返回 ID 缺失、重复、错序时仍走原 `READ_FAILED`／`RECEIPT` 分支，但不能声称故障首先发生的组件与旧请求轨迹完全相同。新路由不预先认证其他组件的 JSON，不把业务验证移出原异常捕获范围。
