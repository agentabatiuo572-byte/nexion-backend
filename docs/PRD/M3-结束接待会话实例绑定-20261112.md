# M3 结束接待：命令绑定接待实例（BUG-416）

## 2026-11-19 BUG-424 App 专属客服会话的写入状态

- App 的专属客服聊天读取 `advisor` 及历史 `support` 线程。详情（含 `beforeMessageId` 加载更早消息）、发送、已读回执和发送回放返回的会话详情都会在 `data.writeState` 提供两项：`canReply`（布尔值）和 `writableConversationNo`（会话编号或 `null`）。命令查询回放的会话详情位于 `data.result`。
- `canReply` 按 App 回复的客服归属和认领条件计算。

  1. 线程存储的客服与当前专属客服相同，返回 `true`。
  2. 线程归属为空且客户未分配专属客服，返回 `true`。未分配的欢迎语线程可继续留言。
  3. 线程归属为空且客户已有专属客服，只有原发送认领条件全部满足时才返回 `true`。线程为 `advisor` 或 `support`，生效分配对应当前专属客服，该客服账号及资料有效，且存量消息中没有 `sender_type='agent' AND (origin IS NULL OR sender_id IS NOT NULL)` 的记录。读取和发送使用同一组认领条件，发送时实际认领。
  4. 其余返回 `false`。`writableConversationNo` 复用管理端查询，取当前专属客服名下最新的 `advisor` 或 `support` 线程号。没有当前专属客服或该客服名下没有线程时返回 `null`。

- `canReply` 为 `true` 时，`writableConversationNo` 是本线程号。`OPEN`、`RESOLVED`、`CLOSED` 的回复限制仍按 `conversation.status` 判断。
- `ai` 会话和系统通知等其他类型省略 `writeState`。专属客服的 `writeState` 仅提供上述两项。
- 该状态通过只读查询取得。读取不会修改线程归属或创建线程。发送继续执行原有权限、会话状态、版本、客服认领和归属校验。

2026-11-12 · 后端合同 · PC 接入待后续页面任务

## 问题

原 `POST /api/admin/content/support-workbench/customers/{customer}/session-hold/end` 的幂等键只按「管理员 + 客户」保存。原结束命令没到后端、接待因空闲结束、超过 24 小时后同一管理员再接待同一客户时，旧命令号查不到回执又不能重试，占住新接待的手动结束入口。

## 后端合同

- `GET .../session-hold` 的 `State` 新增 `sessionRef`，标识一次接待实例（`assignmentId:startedAt`）。同一客户重新接待后该值改变。
- `POST .../session-hold/end` 可选 body：
  ```json
  { "sessionRef": "15:2026-11-11T16:55:23.237313" }
  ```
- 带 `sessionRef` 时：
  - 实例一致性只在**首次执行**时校验；请求的实例必须与当前接待实例一致，否则 `409 SUPPORT_SESSION_CHANGED`，不会结束当前另一个接待。
  - 幂等请求哈希绑定 `customer | sessionRef`；同一键在新接待上使用会因哈希不同返回 `409 IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`，PC 应在新接待生成新命令号。
  - 原命令成功后再用同一键、同一 body 重试，先返回原回执，不读取也不改变当前新接待 R2；实例校验不会把成功回放变成 409。
- 不带 `sessionRef` 时保留旧行为（`admin + customer` 哈希），仅用于尚未升级的 PC；该旧路径仍有原缺陷，PC 必须按 `sessionRef` 保存命令号后才完成整单修复。

## PC 接入要求（改版候选已接，待目标发布与实景）

- 读取 `State.sessionRef`。
- 结束命令的持久化 fingerprint 改为 `session-end:{adminId}:{customerId}:{sessionRef}`。
- 旧命令号在新 `sessionRef` 下收到 `409 SUPPORT_SESSION_CHANGED` 时，才允许清除旧记录并生成新命令；不得删除原号、超时解锁或换号冒充原命令重试。
- 若旧命令确实到过后端，仍先用原命令号查回执；只有明确失败或确认未执行才进入新接待的新命令。

## 边界

- 不改变接待超时、转绑、分配和消息发送逻辑。
- 不用 B38 通用核查替代实例绑定：原命令从未到后端时不存在可核查记录。
- 本单后端局部通过不代表整单关闭，PC 未接入前保持开放。

## 2026-11-16 补充：旧线程与当前分配的只读事实（BUG-424）

管理端会话详情在原对象读取权限校验后增加可空 `writeState`，分别返回线程存储的 `threadOwnerAgentId/Name`、当前分配的 `currentAssignmentAgentId/Name`，以及当前分配下最新 advisor/support 线程的 `writableConversationNo`。`canReply` 只表示该线程号与本次详情线程号相同，不替代资格、状态、写权限、peer 或当前线程校验。

本补充的三条查询无锁、不改变线程归属或自动建线程；原回复及 `409 CONVERSATION_PEER_CHANGED` 保持。它与上文接待 `sessionRef` 是两个不同概念。

## 2026-11-17 M3-BE-03：原请求的归属前置拒绝回执

- 只覆盖回复 `M3_CONVERSATION_REPLY` 和首次联系 `M3_CONVERSATION_INITIATE` 在登记前的 `requireMessageWriter` / 原生产路径守卫真实拒绝。已知客户标识且原键去空白后长 8–128、原 `clientMessageId` 符合既有 `[A-Za-z0-9_-]{8,128}` 时，记录这次实际 4xx。没有这些身份事实的旧请求、缺原记录或仅当前状态拒绝，不推断旧请求未发送，不补造历史。
- `SupportSessionService.rejectedSend` 通过独立 `REQUIRES_NEW` 事务，复用 `nx_admin_idempotency_record` 的原 `operation:可信actorId` scope、原键及原请求 hash，仅 INSERT 明确拒绝回包，并在同一事务保存 `SUPPORT_SESSION_REJECTED` 审计。存储原键、消息编号、客户、操作、服务端身份及指纹，均不从 request.operator 取身份，不新增保存正文、附件或其它私有内容；原 holder 审计保持。持久化或审计失败不得返回可确认的拒绝事实。
- 原表 `uk_admin_idem_scope_key(scope,idempotency_key)` 仲裁新回执与正常命令。同键已有任何原成功、在途、未知、失败或过期记录时，不 UPDATE/重置它；仍保留此次前置拒绝审计，但不声称替换了原命令结论。
- 回执内部 `status=SUCCEEDED` 只表示非零业务码的拒绝回包已留存，不表示消息发送成功。复用原 `executeRetained` 的成功回包恢复与保留规则，`expires_at` 仍按现有 Clock/24小时填写，不引入新租约或全局TTL政策。以后归属恢复，同一键/同一 hash 迟到时返回原拒绝，不执行 action 或发送；不同 hash 仍原 `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`。首次请求仍抛原4xx，恢复拒绝回包的发送重试设置相同HTTP状态码。正常成功、发送事务、首次联系行为及后续会话校验不改。
- `GET /api/admin/content/support-workbench/commands/{key}` 仅在原 actor scope 的留存回包带真实新拒绝标记、且原键/hash/actor/operation匹配时，返回 `status=REJECTED`、`sent=false`、`customerId/operation/idempotencyKey/clientMessageId/businessCode/businessReason`。这类**本人被拒回执**只要求当前 `service_m3_read` 与原 actor scope，不再按当前客户所有权校验（见下条 2026-11-18 修订）；除这类回执外的其它回执仍要求当前客户可读范围，失去读取范围不得返回该客户事实。GET 只读取原记录，不补审计、不发消息、不修改状态。
- **2026-11-18 M3-BE-04（本人安全拒绝回执读取）**：发送人在发送时客户被转走而收到 4xx，原键的 GET 曾在“客户尚归别人”时因当前客户读取校验返回 404，只有客户转回后才看到 `REJECTED`。现明确：本人查询**自己这条**被拒发送，不要求当前客户读取权，只回“未发出”与业务原因。该分支保留 `isAuthenticated`、当前 `service_m3_read`、原 `actor scope:key` 筛选，以及 actor/key/hash/operation/clientMessageId/4xx 业务码/`sent=false` 的可信标记校验；仅移除该安全分支的当前客户锁与可读校验，读取结论不再依赖客户当前归谁。响应仍只有 `status/sent/operation/idempotencyKey/clientMessageId/businessCode/businessReason` 与原请求目标 `customerId`，**绝不**返回正文、附件、客户档案或当前 holder。其它成功、在途、未知、无可信标记的回执照原客户范围、恢复顺序与权限执行，原成功优先不变；不改 producer、存储、hash、TTL、幂等与审计，查不到仍按未知，不清号、不换号、不超时自结案。
