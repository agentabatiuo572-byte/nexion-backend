## 事实

- `PATCH /api/admin/growth/check-in` → `OpsGrowthService.updateCheckIn` → `normalizeCheckInValue`：
  - `baseRewardNex` 当前只做 `0..100` 的 `BigDecimal` 边界；
  - `streakBonusNex` 当前只做 `0..1000`；
  - 因而 0 和 2.5 这样的正小数可保存；负数原已被bounded拒绝。
- `PATCH /api/admin/growth/check-in/rules/{ruleKey}` → `updateCheckInRule` → `normalizeCheckInRuleNumber`：
  - `baseline` / `bonus7` 当前只做 `0..100000`；
  - 同样可保存 0 或小数；A2/版本/锁/幂等/回执存在，但输入边界不足。
- App 实际签到 `AppGrowthEngagementService.checkIn`：
  - `base = positiveInt(mapper.checkInRule("baseline"), 1)`；
  - `streakBonus = streak % 7 == 0 ? positiveInt(mapper.checkInRule("bonus7"), 5) : 0`；
  - `positiveInt`（`:1300-1307`）只接受 `Integer.parseInt` 的正整数，0/小数/科学计数法字符串抛 `409 DAILY_BASE_REWARD_INVALID`。
- 所以保存 0 或小数后，正常 App 签到会失败；这不是 H5-A02 的连签里程碑奖励，后者已有独立 typed/A2 实现，本项不重复。

## 最小修复

在 `OpsGrowthService` 增加最小 helper：

```java
private BigDecimal positiveWholeReward(BigDecimal value, BigDecimal max) {
    BigDecimal normalized = value.stripTrailingZeros();
    if (normalized.signum() <= 0 || normalized.scale() > 0 || normalized.compareTo(max) > 0) {
        throw new IllegalArgumentException("CHECKIN_REWARD_POSITIVE_INTEGER_REQUIRED");
    }
    return normalized;
}
```

并只把以下字段改为该 helper：

- `normalizeCheckInValue`：`baseRewardNex`（max 100）、`streakBonusNex`（max 1000）；
- `normalizeCheckInRuleNumber`：`baseline`、`bonus7`（max 100000）。

行为：

- 0、负数、小数（如 2.5）拒绝，返回 422 `CHECKIN_REWARD_POSITIVE_INTEGER_REQUIRED`；不写入、不舍入成合法值。
- 正整数 2 保存为 `2`；`2.0` 只做精确末尾零归一化为 `2`，不做四舍五入；`2.0000001` 仍拒绝。
- `luckyMultiplierMax` 保留原 1..10 小数倍率合同；`p15`/`p2` 概率、`broken` 天数、`saver` 字符串不变。
- `updateCheckIn` 和 `updateCheckInRule` 都保留原有命令边界、A2（如适用）、方向/覆盖率、版本 CAS、对象锁、幂等和回执；只在原边界处前置校验。
- 历史已保存的非法值不自动改写；运营需按正常入口改为合法正整数。不新增迁移或回填。
