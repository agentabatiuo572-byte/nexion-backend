# B34：USDT 提现原键只读恢复

适用于 USDT-TRC20、USDT-BEP20、USDT-ERC20。新增 `GET /api/withdrawals/attempts/{idempotencyKey}`，由现有用户登录态确定本人，不接受请求参数指定其他用户。管理员令牌不作为用户令牌使用，未登录或非 USER 身份沿用 `401 / USER_AUTH_REQUIRED`。键校验和规范化与原提交、放弃入口相同。

读取只使用既有提现尝试、本人原键订单、共享幂等回执及原合规提交审计，不创建或修补尝试，不建单、不预留或扣款、不发事件、不续期、不改历史、不调用提交或放弃。先复用提交和放弃已有的本人用户事务锁，再锁读本人尝试，在 READ_COMMITTED 事务中观察已提交结果，避免同键写请求在途时读到旧拒绝并过早释放冻结件。整条 GET 只执行 SELECT；事务不能标注数据库 readOnly，因为 MySQL 的只读事务不允许已有 SELECT FOR UPDATE。原提交与放弃的锁、原键同内容重发及原错误处理均保持不变。

## 返回契约

外层沿用 `ApiResult`，以下为五类完整结构示例。`withdrawal` 使用既有本人提现详情字段，下例仅示意原单部分字段，实际保留详情原字段及已存在的合规审计快照。状态表示原提交结果，不表示链上付款已成功；订单当前状态由 `withdrawal.status` 表示。

本人原键订单存在时优先返回原单，即使尝试表缺失、仍为 ACTIVE 或有旧 ABANDONED 标记。订单必须同时匹配登录用户、原 `d2_idempotency_key` 且未删除；有多条历史同键单时按原订单 ID 取最早单，不新建、合并或重写历史。原费用、SLA、完成时间及合规字段继续取既有持久记录，不按当前策略重算。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "state": "COMMITTED",
    "withdrawalNo": "WD-ORIGINAL",
    "withdrawal": {
      "withdrawalNo": "WD-ORIGINAL",
      "chain": "USDT-BEP20",
      "amount": 20.000000,
      "status": "REVIEW_PENDING"
    },
    "canRetrySameKey": false
  }
}
```

只有已证实本人尝试绑定的共享成功回执中保存了明确非零业务结果和原原因，才返回 REJECTED。共享状态 SUCCEEDED 表示回执已保存，不能单凭这个状态认为提现建单成功。原业务错误码和原 message 分别投影为 `reasonCode`、`reason`，不返回共享原始请求、hash、其他账号信息或任意附加回执字段。已有 ABANDONED 墓碑在没有本人原键订单时同样返回 REJECTED，原原因是 `409 / WITHDRAWAL_ATTEMPT_ABANDONED`。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "state": "REJECTED",
    "reasonCode": 409,
    "reason": "WITHDRAWAL_POLICY_VERSION_CONFLICT",
    "canRetrySameKey": false
  }
}
```

本人 ACTIVE 尝试绑定的共享回执仍是 PROCESSING 时返回处理中，不重新执行或延长其租期。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "state": "PROCESSING",
    "canRetrySameKey": false
  }
}
```

FAILED 只保存异常类或事务回滚摘要，不具备原业务拒绝原因，故不能冒充明确拒绝。共享 UNKNOWN、缺失/已删除回执、摘要不符、损坏 JSON、成功回执但没有本人原键订单、COMMITTED 尝试却找不到该原键单，均保持 UNKNOWN；不替用户释放本地冻结件，不推断未执行。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "state": "UNKNOWN",
    "canRetrySameKey": false
  }
}
```

没有本人尝试且没有本人原键订单时返回相同的 `404 / WITHDRAWAL_ATTEMPT_NOT_FOUND` 与 NOT_SEEN 数据，其他人的键也完全相同。接口不读取这些键的共享回执，不能通过比较状态、金额、单号或拒绝原因枚举其他用户。404 是现有 ApiResult 的业务码；HTTP 状态仍遵循项目统一返回方式。NOT_SEEN 仅表示本人的已提交记录中没有观察到尝试或订单，不承诺从未收到网络请求，也不承诺没有尚未提交事务。

```json
{
  "code": 404,
  "message": "WITHDRAWAL_ATTEMPT_NOT_FOUND",
  "data": {
    "state": "NOT_SEEN",
    "canRetrySameKey": true
  }
}
```

`canRetrySameKey=true` 表示可以保留原冻结请求、由用户选择用原键及原请求体重发，由现有写入口继续处理幂等与资格；不保证重发一定成功。其他状态为 false，表示本次读取没有提供重新执行的确定依据；这不改变原人工同键重发或放弃入口的契约，不能据此自动换键、自动重发、自动放弃或放松幂等规则。原键存在于其他用户时写入口仍按原幂等冲突规则拒绝，不泄露原回执。

## App 与 H5 Lite 接入边界

客户端页面变更单独遵守前端确认门禁，本后端交付不代表页面已改、已发布或已验收。已分析方案为仅在提现页可见、前台、联网且本人会话绑定就绪时，对已有原键冻结件自动只读恢复；隐藏/后台停止调度，恢复或重连后再读，账号/绑定代次/环境变化使旧回包失效。COMMITTED、REJECTED 才可按本账号及此 key 收口并提示一次；PROCESSING、UNKNOWN、NOT_SEEN 与读取失败保留原冻结件。原键原 body 重发和服务端 abandon 继续由用户明确操作。共用读取恢复调度器及其他支付、银行卡、兑换、质押页面不因本接口改变。

## 必要业务验收

本次源码编译仅验证可构建性，下列真实业务验收由本轮主流程统筹，本文不将计划写成通过。

1. 本人三网之一真实提交后保留原 key，GET 返回相同提现号、原详情和当前订单状态；连续 GET 前后本人钱包、提现订单、账本、attempt 和共享幂等记录（含状态、租期、updated_at）不变。三网各有既有本人记录时分别读取，不为验证重复出账。
2. 当前策略下用明确拒绝请求（例如原请求的错误 policyVersion）取得原回执，再用原 key GET，返回同一原错误码和原因；不依赖当前策略变化重算原因，无订单或余额变动。
3. 未提交过的随机键连续 GET，返回上述 404 / NOT_SEEN / true，无 attempt、订单、账本或幂等记录新增。用另一个用户读取真实已提交键，返回与随机键完全相同的结构，不包含单号、金额、原因；无登录及管理员身份返回 USER_AUTH_REQUIRED。
4. 使用现有整体业务服务的在途/异常场景验证 PROCESSING、UNKNOWN、FAILED、摘要不符和损坏回执；读取不得 claim、reset、markFailed、续期或改租期。无确凿原拒绝原因时不得返回 REJECTED，异常时不宣称资金未执行。不得为此建立永久测试脚手架。
5. 本人的 ABANDONED 原键 GET 返回 REJECTED 与 WITHDRAWAL_ATTEMPT_ABANDONED；既有提交/放弃原链路继续工作。本人原键订单存在但旧尝试不完整时，以原订单事实恢复，GET 后 attempt 历史仍保持原值。

SQL 定位以测试登录态实际 `userId` 和抓取的原 `Idempotency-Key` 为准：`nx_withdrawal_attempt_control(user_id,idempotency_key)`；`nx_withdrawal_order(user_id,d2_idempotency_key,is_deleted)`；共享回执为 `nx_admin_idempotency_record(scope='USER_WITHDRAWAL_SUBMIT',idempotency_key)`，仅验收人员在已核对归属后只读比对 `request_hash/status/response_json/expires_at/updated_at`。余额及预留取 `nx_user_wallet.user_id`，比对 `usdt_available/nex_available/pending_withdraw/version`；流水取 `nx_wallet_ledger.user_id` 与原提现号关联的 biz_no。实际表字段先由现场 schema 核实。报告只保留必要键、用户编号与结果，不写令牌、密码或原地址。
