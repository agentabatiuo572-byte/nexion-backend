# P5 客服资金历史有界读取

## 问题与目标

2026-11-07 的 m7i.4xlarge 隔离运行中，尚未启动压力，两个客服资金历史查询已分别持续约 905 秒和 897 秒；随后隔离 JVM 记录 `OutOfMemoryError: Java heap space` 并退出。数据库资金操作表约 147 万行、数据约 11.2 GB。当前证据没有给出两个连接的完整 IN 参数，不能将大 IN 的具体执行计划当作已证实根因。

原读取器虽将请求根用户分成每批 32 人，但会展开关联用户并一次性读取该范围的全部历史资金操作及三个 JSON 字段。TEST 已有 `54ecb4e2` 在每批根用户读取完成后释放 MyBatis 一级缓存；本批在 TEST 保留该既有行为，但 main 候选不依赖该未合入变更。本批利用现有 Mapper 的 flushCache 标志，解决单批内原始 JSON 同时驻留的问题。

## 读取约定

- 原根用户范围、关联用户闭包及 4096 人闭包上限不变；所有历史操作 ID、关联参与方和资金分录均完整读取，不加历史时间窗或总行数上限。
- 操作目录、参与方和分录每次最多使用 256 个 operation ID，按原 operation ID、参与方及分录次序拼接完整结果。操作目录读取原 13 字段中的 10 个非 JSON 字段。
- 三个原始 JSON 字段仅按需读取，每页最多 32 个 operation ID。验证器继续使用完整 13 字段 Map 视图；普通字段来自目录，JSON 字段、完整字段遍历和 Map 相等比较来自该操作的原始完整行。缺键与 null 的原有语义保持。
- 内存中只保留当前一页原始操作行；切页前释放旧页。目录、参与方、分录和 JSON 查询均保留 `@Options(flushCache=TRUE)`；MyBatis 3.5.16 在每次顶层查询前清除同一 SqlSession 的一级缓存，因此不累计之前的原始 JSON 页。末页最多 32 个 operation ID，并在下一次带该标志的查询（包括下一根用户批的 schemaReady）或事务结束时释放。不新增缓存清理回调，不开启新事务或更换连接。
- 原收据摘要认证、完整 proof、原始业务来源、钱包连续性、来源覆盖及 UNKNOWN 判定继续执行。后续验证需要历史原行时，在同一物理只读 RR 快照中重新读取对应页，不跳过或延后验证。
- 向调用方返回的仍为原 NetSnapshot：客户金额与状态、贡献来源和贡献变更；不返回操作目录、Map 视图或原始 JSON。

## 边界与剩余成本

本次只限制单次 operation ID 列表及原始操作 JSON 页的驻留量。全量 ID、目录、参与方、分录、钱包历史、业务来源和紧凑回放事件仍随实际历史规模增长；同一条 JSON 的最大大小也没有新增限制。既有收据解码缓存保留原 64 MiB 字节上限与单条 256 KiB 上限。试用退款验证所需的少量 source/authority/reward 解析树仍持续到对应连通分量结束，因此不能宣称所有解析树都只存活一页。

来源覆盖和跨操作 proof 校验可能重读已释放的 JSON 页；总数据库 I/O 和总运行时间是否改善，需要实际快照及业务验收。两个后台任务的并发、刷新周期及锁租约不在本次范围。

## 必要验收

1. 在同一个冻结 RR 快照比对原实现与候选的完整操作 ID 和顺序、NetCustomer 金额与状态、UNKNOWN 原因、origins 与 changes；包含跨用户连通分量、长历史及末页不足 32/256 条。
2. 通过现有业务流程验证注册资金出生、任务收益、跨操作原始收据引用、来源覆盖及幂等重放；缺失或损坏收据/proof 不得成为 READY。核对缺键、null 与完整 Map 相等比较。
3. 实际观察每次 JSON 查询最多 32 个 ID、目录/参与方/分录查询最多 256 个 ID，始终使用同一物理只读 RR 连接；核对堆与 MyBatis 一级缓存没有累计保留所有原始 JSON 页。
4. 验证完整后台代际成功发布及相应正常 API 读取，再继续原 1000 人诊断档和 10000 人目标。编译、SQL 计划或空集合比较不能代替业务和容量通过。

本批基于 TEST `2195f875`，另从 main `a1462405` 准备相同的两个 Java 文件和本 PRD；两份 Java 17 必要打包均通过（`mvn -DskipTests -Dmaven.test.skip=true package`，未编译或运行测试源码）。独立只读代码复核未发现 Map 语义或全量 JSON 长期保留的阻断问题。

在 PROD 隔离库，同一物理只读 RR 连接对原 12 个隔离资金/结算样本的 1024 个操作做了实际 SQL 读取比对：完整 13 字段、操作顺序、1024 条参与方及 1024 条分录均一致；覆盖 SUPPORT_DEVICE_EARNING、SUPPORT_PAYMENT、SUPPORT_WITHDRAWAL，原始 JSON 每页最大约 130338 字节。本样本无 null JSON，不代表缺 proof/UNKNOWN 分支或完整 NetSnapshot 已验收。原全字段与分批重建 SHA256 同为 `74992053d717cab884a06dcdbb2f0ba26e3f7457bd98760ef130547c24733535`。
