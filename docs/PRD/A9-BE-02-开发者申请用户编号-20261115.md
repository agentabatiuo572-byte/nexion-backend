# A9-BE-02:开发者访问申请的管理端可空用户编号

状态:候选,未提交、未推送、未部署、未业务验收。
日期:2026-11-15
范围:`nexion-backend` 管理端 A9 申请列表投影;不改 A9 写链、App 申请/状态、页面或权限。

## 1. 问题与目标

A9 管理端申请列表当前只返回内部 `userId`,没有 `U…` 用户编号。运营无法从申请行安全定位用户。目标:

- 只在现有管理端列表 `records[]` 增加可空 `userNo`;
- 只对有权查看该用户的人返回编号;
- 用户不存在/已删除/无权/历史缺源返回 `null`,不拼造新编号;
- 不改变 `userId`、申请字段、时间、排序、分页、`total`、`statusCounts`、过滤、状态机、幂等和审计。

## 2. 权威来源

当前 schema 没有 `nx_user.user_no` 列。现有管理用户投影的统一合同是由 `nx_user.id` 生成的规范编号:

```text
U + LPAD(id, GREATEST(8, LENGTH(CAST(id AS CHAR))), '0')
```

来源:

- `user/mapper/UserOpsMapper.java:350-352`(C1 `PROFILE_SELECT`);
- K1 既有收益投影 `finance/mapper/EarningsReleaseMapper.java:155-165`;
- K1 决定 36 的后端 `4d11e40e` 已按该合同返回可空 userNo。

本候选不发明另一种编号,也不把 A9 的 `userId` 直接拼成字符串。只按当前页 `userId` 批量查询 `nx_user`,并要求 `is_deleted=0`;查不到或已删除返回 null。

## 3. 权限与对象范围

- 列表本身仍只要求 `developer_access_read` 或 `ROLE_SUPER_ADMIN`(`OpsDeveloperAccessController.java:29`)。
- `userNo` 额外要求现有 C1 用户详情权限 `user_c1hub_read`:
  - 来源:`OpsUserController.java:200-201` 的 `/profiles/{userKey}/360` 只要求该权限;
  - 本候选不新增权限,不把 A9 读权当作用户详情读权。
- 没有 `user_c1hub_read` 的 A9 读者:列表仍正常读取,`userNo` 全为 null,不额外查询用户表、不扩大可见范围。
- 有 `user_c1hub_read` 且不是客服对象范围读者:C1 详情为全局读权,当前页所有存在的用户返回 `userNo`。
- 有 `user_c1hub_read` 且是客服对象范围读者:复用 `SupportOwnershipService` 的既有逐用户对象范围,只对当前 actor 可读的 `userId` 返回 `userNo`,其余 null。批量查询复用 `SupportBindingMapper.CUSTOMER_SCOPE_PREDICATE`,不按行调用权限服务。
- 权限查询/用户编号查询失败时按现有 Spring/MyBatis 错误向上返回,不吞成 null;只有“无权限/无来源/已删除”按设计为 null。

## 4. 数据流与代码边界

管理列表:

1. 现有 `OpsDeveloperAccessMapper.page` 仍按 status/keyword/sourceEnvironment/sort 分页读取申请行;
2. `OpsDeveloperAccessService.page` 仍先构造原 `view` 字段;
3. 新增 `attachUserNumbers(records)`:
   - 无 `user_c1hub_read` → 每条 `userNo=null`;
   - 有权限 → 收集当前页 `userId`,一次 `userNos(ids)` 批量查 `nx_user`;
   - 客服对象范围读者 → 一次或两次按现有 `availableReadModes` 的批量 scope 查询,得到可读 `userId` 集合;
   - 按行填 `userNo` 或 null。
4. `OpsDeveloperAccessPage` 的 total/pageNum/pageSize/statusCounts 及 records 原有字段不变。

新增/修改:

- `OpsDeveloperAccessMapper.userNos(List<Long>)` 和内部 `UserNoRow`;
- `SupportBindingMapper.readableCustomers(scope, ids)`(复用 `CUSTOMER_SCOPE_PREDICATE`);
- `SupportOwnershipService.readableCustomerIds(ids)`(批量组合现有读模式);
- `OpsDeveloperAccessService.attachUserNumbers` 和 `SupportOwnershipService` 注入。

不新增:

- 端点、请求参数、字段搜索/排序;
- 每行 SQL、全库拉取、内部 HTTP、缓存、框架;
- DDL/索引/表;
- A9 写链、App DTO、页面或新权限。

## 5. 消费边界

- `OpsDeveloperAccessService.view` 仍用于 approve/reject/revoke 回执和 replay;本候选**不向写回执**添加 userNo,不增加写路径查询/失败依赖。
- `OpsDeveloperAccessPage.records` 只用于管理端列表;新增 `userNo` 只在这个读取投影。
- `AppDeveloperAccessService`/`AppDeveloperAccessController` 的申请提交/最新状态 DTO 不变,不把 userNo 或用户 PII 带给 App。
- A9 当前没有独立详情 GET;本次不新增详情接口。未来若接详情,应复用同一权限/来源和可空语义。
- PC/App/H5 和既有下发文案不改;未来 PC 只能在 `user_c1hub_read` 且目标详情可达时消费 `userNo`,不得自行拼详情地址或把 null 当新用户。

## 6. 缺失、软删和历史记录

- 申请行 `userId` 保留原值。
- `nx_user` 不存在/已软删:userNo=null;不按 `U`+A9 userId 发明编号。
- 申请行本身 `is_deleted=1`:沿用现有列表读取集合,不因本字段改变。
- 历史申请指向旧用户:`userNo` 按当前权威用户表返回;若当前已删除则 null;不重编排既有编号。
- 无 `user_c1hub_read` 或客服范围不可读:null,不泄露用户是否存在以外的信息;不返回手机号/姓名/邮箱等新 PII。

## 7. 兼容性与错误

- 字段:仅 `records[].userNo`(string|null);其它字段和顺序保持。
- 状态/排序/分页/计数/过滤/软删集合、申请/批准/驳回/撤销写链、A2/锁/幂等/审计均不变。
- 没有 C1 详情权时,列表仍 200,userNo 为 null;不把无权变成请求失败。
- 有 C1 详情权但用户不存在:userNo null,列表仍成功。
- 批量用户/范围查询失败:正常抛出,不伪造 null;具体 HTTP 仍由现有异常映射决定。

## 9. 开放边界

- A9 当前无管理详情 GET;本候选只覆盖列表 records。若产品要求详情单独返回 userNo,需另立读取端点,不在本单硬造。
- `userNo` 的权威仍是现有规范公式;若未来引入独立 user_no 列,应另单切换来源,不能同时混用两套编号。
- PC 的展示/链接权限复核另行处理,本单不改页面。
