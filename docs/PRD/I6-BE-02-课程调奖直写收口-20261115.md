## 2. 实际调用链

### 2.1 直接 PATCH（要关闭的入口）

`OpsI18nLearningController.java:237-246`：

```java
@PatchMapping("/courses/{courseId}/reward")
@PreAuthorize("hasAuthority('content_i7_course_reward_adjust')")
public ApiResult<LearningCourseView> updateCourseReward(...) {
    return executeCommand("I7_COURSE_REWARD:" + courseId, idempotencyKey, request,
            () -> i18nLearningService.updateCourseReward(courseId, idempotencyKey, request));
}
```

`executeCommand`（`:258-273`）：

- 先 `acceptanceGate.requireProductionMutationAllowed()`；环境门先于幂等/业务。
- 有 key 时调用 `AdminIdempotencyService.execute(scope,key,hash,ApiResult.class,action)`；hash 为 `scope + NUL + String.valueOf(request).trim()`（`:275-282`）；当前 `2aa` **没有** `LearningCommandIdempotencyService`，实际是 `AdminIdempotencyService`。
- 无 key 时直接执行 service，由 service 的 `requireRewardUpdate` 返回 `IDEMPOTENCY_KEY_REQUIRED`。
- 权限为 `content_i7_course_reward_adjust`；旧成功 key 的有效回执在 action 前回放，沿用 AdminIdempotency 默认 24h TTL；过期按原 TTL/回收语义，不承诺永久恢复。
- **有效回执/403 缓存边界**：新直接请求返回 `ApiResult.fail(403,...)` 后，`AdminIdempotencyTransactionExecutor.completeClaim` 仍会把 action 结果通过 `markSucceeded(writeJson(result))` 标为 **SUCCEEDED**，响应 code=403；这表示 idempotency handler 完成，不代表调奖成功。同一 key/同一 body 再请求会回放该 403；课程、reward、revision 和成功业务 audit 没有写，但 idempotency claim/success 记录本身会写（有 key 时）。无 key 的直接请求在 `requireRewardUpdate` 先返回 422，不会进入这条缓存路径。

`OpsI18nLearningService.updateCourseReward`（`:651-661`）当前：

1. `requireRewardUpdate`：idempotency key、8–200 reason、reward 范围；
2. 进入私有 `updateCourseReward(..., review=null)`；
3. 非 replay 时查 `learning_course` 锁；
4. 锁课程、要求 published、覆盖率、写 `nx_help_article.reward_nex`/revision、audit。

## 3. 最小改动

只改 `OpsI18nLearningService` 的**公共直接方法**，不改私有 A2 写链：

```java
@Transactional
public ApiResult<LearningCourseView> updateCourseReward(String courseId, String idempotencyKey, LearningRewardUpdateRequest request) {
    ApiResult<Void> guard = requireRewardUpdate(idempotencyKey, request);
    if (guard != null) {
        return fail(guard);
    }
    return ApiResult.fail(403, "LEARNING_COURSE_REWARD_APPROVAL_REQUIRED");
}
```

效果：

- 新的直接 PATCH（调高/调低/同值）在通过原有 key/reason/reward 范围校验后，明确返回 HTTP 403 `LEARNING_COURSE_REWARD_APPROVAL_REQUIRED`，不进入查课程/coverage/仓储写/成功业务 audit 路径。
- 缺 key、缺/短理由、reward 越界仍按原服务校验返回原错误；按当前 `OpsErrorCode` 分别是：缺 key → `IDEMPOTENCY_KEY_REQUIRED` 422；reason 缺失/长度不合 → `REASON_REQUIRED` 422；reward 缺失或越界 → `LEARNING_REWARD_OUT_OF_RANGE` 422。HTTP 权限在 Controller 先 403；环境门先于这些服务校验（现有 gate 行为不变）；malformed body 走框架 400，不是本 service 错误。
- `updateApprovedCourseReward` 及其私有 `updateCourseReward(..., review)` 完全保留；A2 批准后正常写/覆盖率/review stale/奖励精度不变。
- 不使用 `A2ReplayContext.isReplaying()` 作为直接授权；普通直写即使伪造 replay 标志也走公共拒绝。
- 环境门/Controller 权限/幂等 scope/hash/旧有效成功回执顺序不变；旧成功 key 命中仍返回原回执；过期沿原 TTL。
- 不改 A2 maker/checker/业务权、存储 target、旧票兼容、coverage、发布/激活/回滚、i18n、App 发奖规则、前端/页面文案。

## 4. 剩余边界

- 旧成功 key 的有效命中仍可返回历史 direct 成功回执（不重写）；这是保留旧回执，不代表新直写被允许。
- 新 key 或过期 key 的直接 PATCH 返回 403；有 key 时现有 AdminIdempotency 会把该 `ApiResult` 缓存为 SUCCEEDED（响应 code=403），同 key/体回放 403；这不等于调奖成功，也不表示“完全无 DB 写”——课程/reward/revision/成功业务 audit 无写，但 idempotency 记录有 claim/success 写。
- A2 旧票缺 review 仍 `REPROPOSE_REQUIRED`；旧 review stale 仍 `LEARNING_COURSE_REWARD_SNAPSHOT_CHANGED`；均已由 BUG-321/现有代码负责。
- 不新增 maker active、双 target 互斥或其他未定 I6-BE04 政策。

## 2026-11-16 补充：I1 同步发布不再静默覆盖 I6 未发布草稿

`MybatisI18nLearningRepository.saveMessagePair(..., "published", ...)` 在发布分支里会先取该 `message_key` 的现有 `DRAFT` 行（`latestVersion(key, "DRAFT")`），随后直接把正文写进这一行并改状态——也就是**未发布的草稿会被发布内容原地覆盖**，草稿作者看不到任何提示。I1 文案发布（`OpsCopyAbService.syncPublishedI18n` → `saveMessagePair(..., "published", ...)`）与模板保存走的是同一条路径，因此同词条的未发布 I6 草稿确实会被静默冲掉。

现只加一道内容冲突判断，不新增版本模型、schema 或锁：

- 发布前若存在 `DRAFT` 行，且其 `zh/en/vi` 或附加语种翻译与本次要发布的文本**不同**，抛 `409 I18N_DRAFT_OVERWRITE_CONFLICT`，草稿原样保留；调用方（I1 发布）整体回滚，不会静默覆盖。
- 若草稿内容与要发布的文本**相同**（I6 自己的发布流程：`OpsI18nLearningService` 已先校验请求与草稿一致），仍按原逻辑复用该行转 `PUBLISHED` 并归档旧 `PUBLISHED`，普通发布语义不变。
- 未改动正文/模板/下发页面说明/前端/App/PC，未改 I1 的发布校验、I6 的草稿 CAS、版本号生成、审计与事件，也未引入把草稿另起版本的新策略（那属产品决定）。

## 2026-11-16 补充：课程「完成条件」「发奖事件」两个选项退役

`LearningCourseView.completionCondition` / `rewardEvent` 能选能存，但判定完成与发奖只按 `passScore`（`AppLearningService` 的完成/领奖流程），这两个字段没有任何消费者。原句要求「落实…或退役」，本项取**最小退役支**：

- **新建**课程时提交非空的 `completionCondition` / `rewardEvent` → `422 LEARNING_COURSE_OPTION_RETIRED`；不再允许把它们当作生效配置写入。
- **编辑**草稿时只拒绝「改动」：与库里已存值不同（含空↔非空）即同上 422；原值原样回传（编辑器通常整对象回填）视为未改动，允许保存，避免历史值被误判成新配置或丢失。
- 带题目课程不再强制要求这两个字段（`requireQuizPayload`、`hasCompleteQuiz` 去掉非空条件），发布与判定语义不变，仍按及格分与题目完整度。
- 历史行不改写、不回填、不新增字段或迁移；`LearningCourseView` 仍如实回显已存文本（只作历史记录展示，不再是生效配置）；课程正文/模板/题目/i18n 发布、领取与既有学习流程均未改。
