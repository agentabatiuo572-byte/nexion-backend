# 用户昵称生成与唯一（2026-11-17）

## 规则
- 系统生成的昵称是 `{形容词} {名词} {后缀}`，如 `Azure Falcon K7`。形容词、名词各 48 个（`UserNicknames`）；后缀 1 个字母 + 1 个数字，顺序随机，字符集去掉 I/O/0/1，不出现纯数字编号。连续 8 次抽到已占用的名字后改用 3 位后缀（仍须字母数字都有），16 次仍无空闲名字时抛 `USER_NICKNAME_SPACE_EXHAUSTED`。
- 使用方：手机注册、第三方注册（含 sandbox）、改名候选 `GET /api/app/profile/nickname-candidates`、后台 C2 重置昵称。第三方平台的显示名只记在 `nx_user_oauth_identity.display_name`，不再作昵称。
- 改名 `PUT /api/app/profile` 只接受上述格式（否则 `USER_NICKNAME_NOT_CURATED`）。

## 唯一
- `nx_user.nickname` 加唯一索引 `uk_user_nickname`（表排序规则 `utf8mb4_0900_ai_ci`，不区分大小写），含已删除行。
- 生成时先查 `nicknameTaken`，只给出空闲名字；并发撞到生成的 UID 或昵称时，手机注册、正式第三方注册和 sandbox 第三方注册返回 422 `USER_REGISTRATION_GENERATED_IDENTITY_CONFLICT`。已有身份绑定和手机号冲突沿用原错误。改名和后台重置昵称的昵称撞库返回 409 `USER_NICKNAME_TAKEN`；后台可重新提交生成新昵称。Sandbox 第三方重试须重新获取 challenge。

## 迁移
- `scripts/migrations/20261117_user_nickname_unique.sql`：同名（不区分大小写）的多条记录中，未删除且注册最早的一条保留原名，其余改为 `原名-<id 的 36 进制>`，再建索引；可重跑。

## 用户 UID（nx_user.id）
- 新用户的主键由 `UserIds` 在插入前分配：随机、未占用、至少 6 位。先在 6 位（100000–999999）里抽，连续 8 次都被占用再用 7 位，最多 8 位（PC 用户编号按 8 位显示）。App 显示的 UID 和 PC 的用户编号（`U` + 8 位补零）都由它而来，不再暴露注册顺序和用户数量。
- 分配点：`UserRegistrationWriteAdapter.insertNewAccount`（手机注册、第三方注册）和第三方 sandbox 建号。并发抽到相同主键按生成值冲突返回可重试错误。
- id 大小不再代表注册先后；需要按注册时间排序的地方用 `created_at`。存量用户的 id 不变。已改：PC 用户列表（最新注册在前）和专属客服的客户列表改按 `created_at, id` 排序。
- F3 直推安置按 `(created_at, id)` 升序。算力排名、创世积分榜同分按同一顺序，创世积分榜的本人名次采用相同规则。邀请榜及 F4 对应结算沿用规定的 UID 同分规则。
- Nova 广播只扫描注册时间早于业务事件所在秒的用户，双方时间记录存在秒级精度差异时排除同秒记录；扫描上界、实际入队、剩余检查共用事件时间边界，续跑沿用原数字进度。活动状态与通知偏好继续在当前批次判定。
- App／H5 Lite 团队网络继续兼容数字 UID 游标。改为按注册时间遍历需要客户端支持新游标，并同步显示同算力成员的次序。
- 客服有权查看的客户搜索，精确数字 UID 或完整 `U` 用户编号排在模糊匹配和尾号匹配前；其余按原注册时间倒序，权限范围及查询总数沿用现有合同。
