## 64 GiB 资源基线

下表正式服务配置已在当前大规格主机生效，并完成实际参数读回及 MySQL 重启核对；隔离复测预算尚待准备。配置生效不代表容量通过。正式应用保留 #29 产物；认证、TLS、数据卷及 MySQL 完整持久化刷盘规则沿用原约束。

| 服务 | 进程或容器内存硬上限 | 关键配置 |
|---|---:|---|
| 正式 API | 8 GiB | JVM 堆 2–4 GiB，直接内存上限 1 GiB；Hikari 64，Tomcat 200 线程 / 16,000 连接，WebSocket 12,000 |
| 正式 MySQL | 12 GiB | 缓冲池 8 GiB，全局临时表内存 1 GiB、redo 容量 2 GiB，max_connections 200；保留原刷盘规则 |
| 正式 Redis | 1 GiB | maxmemory 512 MiB |
| RocketMQ broker / namesrv | 4 / 1 GiB | 沿用原业务配置 |
| MinIO | 3 GiB | 沿用原业务配置 |
| PROD Jenkins / CI agent | 4 / 4 GiB | 复测期间暂停 |

正常正式服务硬上限合计 37 GiB，另留约 8 GiB 系统余量；隔离大服务保持停止。复测暂停 Jenkins 和 CI agent 后，正式服务合计 29 GiB；隔离 API / MySQL / Redis / provider / 发生器（四分片合计）分别预留 8 / 12 / 0.5 / 0.5 / 3 GiB，总计 53 GiB，另留约 8 GiB 系统余量。隔离 API 和 MySQL 沿用上述堆、连接池及缓冲池候选；开测前重新核对全部活动服务和实际内存，工作集或延迟不满足时依据监控调整。

## 配置实施与恢复要求

1. 保存本轮变更前的配置文件、Docker 限额和 MySQL 持久化值。先缩 MySQL 缓冲池并 `SET PERSIST`，再降低容器上限；同步 compose，核对运行值与持久化值一致。
2. 持久化 JVM 参数后重启并核对实际参数、cgroup 额度和自动启动状态，避免缩容重启恢复旧大配置。隔离旧大规格 JVM 禁止直接重启；后续按新预算重建隔离应用，保留旧容器回退，不重建数据库数据。
3. 检查公网健康及 APP / H5 的登录、首页、商品、任务、收益、账单、周任务和资料查询，并验证无 JWT 请求被拒绝。配置和基本业务检查完成后，再由用户切换 EC2 类型。
4. 配置失败时按已保存文件恢复服务。在 64 GiB 主机上恢复旧大规格内存值前，须先恢复大实例。
