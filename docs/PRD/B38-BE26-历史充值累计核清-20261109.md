# B38-BE-26 历史充值累计按证核清

本条只涉及后端历史累计的核清与修复约束，前端不变。2026-11-09 已完成源码写点核对及只读取证准备；尚未取得财务负责人、逐项签认或完整现代累计基线，未执行历史清理，也未新增通用调累计接口。盘点不能作为清理完成或当前累计准确性的证明。

## 计量口径

`nx_user_wallet.cumulative_deposit_usdt` 是独立于可用 USDT 余额的累计指标。现行后端会在钱包银行充值和 USDT 链上充值时增加，在 E4 实际退款时减去实退金额并在每次退款后钳零；旧拒付追回同样保存当次累计前后值。Cregis 重组的 `REVERSE` 减去对应净充值额，`RESTORE` 加回一次；`HOLD`、`RELEASE_HOLD`、`COLLECT_DEBT` 不再次增减累计。

同一银行充值的意图、HDPay 结算、reconciliation 和钱包账本是同笔贡献的证据，不能相加。Cregis 事件、`CR-{cid}` deposit、`CHAIN_TOPUP` 账本和储备同样只能贡献一次。商城 `COMMERCE_ORDER` 直接付款和 `ORDER_PURCHASE` 钱包支出不属于充值。过期未入账银行单不产生累计贡献。

重建必须以有效的权威累计基线为起点，按可证实的实际执行顺序重演完整贡献，逐次执行退款钳零。不得以“全部充值总额减全部退款总额后钳零”替代时序；不得用旧 CARD_TOPUP／USDT deposit 公式与当前值的差额当修复额。业务实际顺序不能确定时保留未核清，单靠不同表的 ID 或原始 DATETIME 不能推定跨表先后。

## 基线与证据边界

- 退休归档中既有的 wallet reset proof／item 是基线候选，核清时须一并核对父证明的 source／zero 计数、`mock_amounts_reused=0`、原始 cutoff、逐钱包 `zero_balance_verified`、精确 wallet／user 身份及当前身份连续性。item 本身没有 incarnation，不因匹配一行就认定当前钱包具备基线。
- `nx_support_wallet_journal` 的 `NEW_ZERO` 不记录累计字段，不能证明该指标为零。
- E4 审计中的 `cumulativeDepositBefore/After` 只证明该次执行观察到的前后值；不能据其反推最初累计正确。缺字段保留 NULL，不能补零。冷归档审计须保留原 audit identity，并核对已有内容摘要。
- 只见当前累计为零、当前 OPEN 为零或旧 migration marker 缺失，均不能证明现代累计已核清。只读身份看不到归档时应记录可见范围，不能断言归档不存在。

## 单项处理与权限

财务负责人需对明确的钱包／业务编号、起止基线与截止、完整贡献证据、拟处理的异常 ID、当前值、目标值和理由逐项签认。缺基线、证据冲突或时序无法核实的对象继续未核清；不得用整体同意替代具体目标，也不得批量将 OPEN 改为 RESOLVED。

只有已核清且实际需要修复的一类形成后，才针对该类实现最小受控执行方式，可复用既有运维 `plan/apply` 模式，不预先开放任意累计输入入口。执行方案须绑定当前钱包身份和版本、原值、核清证据与签认摘要；按原处理号恢复同一回执，证据或状态变化先重新核清。处理、前后结果和必需审计在同一事务内落地；审计保存财务签认编号、核清人、执行人及对应证据。

累计指标纠正不得补造现金、充值账本、储备或旧 migration marker，也不得借已退役的拒付接口执行。若具体证据表明缺失的是实际资金事实而非累计指标，须按该资金链路另行核清和授权，不能用累计修改掩盖。

该字段是 K1 多账户风险 `depositCumulativeUsdt` 的直接来源；累计纠正可能改变后续 K1 判断，财务签认必须了解此影响。核清累计不授予 K1 参数修改、冻结／解冻或任何新增资金权限。
