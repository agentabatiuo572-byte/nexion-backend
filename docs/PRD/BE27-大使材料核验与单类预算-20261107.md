# BE-27 大使材料核验与单类预算

2026-11-07。对应原47项 BE-27；银行卡同号问题不在本项。本文记录本轮后端实现约定，编译与 TEST 验收分别记录，不将代码完成记作业务验收通过。

申请先创建，再由本人上传并提交材料。类别仍为 `venue/kol/print/dev`；按类别要求收集材料：

| 类别 | 必需材料 kind | 最终预算类别 |
| --- | --- | --- |
| venue | attendance、activity、expense | EVENT |
| kol | promotion、traffic、expense | KOL |
| print | materials、quota、expense | PROMOTION |
| dev | requirements、work_hours、acceptance、expense | DEV |

每次提交生成递增材料版本，保留原申请编号、附件元数据及历史核验记录。上传文件本身不产生版本；成功提交才生效。材料说明必填，最多4000字符；单版本1至12份附件。PNG/JPEG/PDF 根据文件头校验，单文件不超过10MiB。文件存放在现有对象存储的私有目录，访问必须经过本人原申请归属或 F4 读权限校验；接口不接受外部 URL 或跨申请文件引用。客户端 fileId 为不透明字符串。原生选图支持 JPEG/PNG，PDF 由 H5 文件选择完成，实际设备能力须实测。

BUSINESS 与 FINANCE 是独立核验阶段，各自记录版本、实际认证管理员、时间、结论、理由和明确缺项。业务核验通过线下场地类时必须填写至少100人的有效去重人数，不以预计人数或日常签到替代。财务核验保存认可金额；认可金额不足申请额时保留原申请额并阻止最终批准。本人在当前版本退回补交时，可将申请额下调到大于0且不高于原额；提交下调和补交一并产生新版本，两项原结论均失效。终态申请不能新增附件、提交材料或核验。

最终批准须满足同一当前版本两项 PASSED、分类必需材料齐全、财务认可金额不少于本申请额、活动日期不晚于当前业务日，且实际最终执行管理员从未参与该版本的任一核验。超管同样受职责分离约束。批准再核对当前最终批准权限和原有 B1 覆盖率可靠性及红线。状态、单类预算和必要审计处于同一事务，失败回滚。仅所选 EVENT/KOL/PROMOTION/DEV 获得完整合法申请额，无 TRAVEL 或额外预算；不执行钱包转账。历史 APPROVED 及既有四桶不修改，不生成虚构历史材料通过。

权限码 `network_f4_ambassador_material_review` 默认仅超管，供 A1/A6 显式分配给指定业务负责人；不新增 GROWTH_LEAD，不通过 `network_%` 给普通 GROWTH。`network_f4_ambassador_finance_review` 默认财务主管与超管，财务主管同步获得 F4 读权限及 F/F4 菜单。审计默认只读。原最终批准权限保持不变。

App 接口为 `/api/app/team/ambassador-applications/{id}/materials` GET/POST、`/files` POST（multipart file、kind）、`/files/{fileId}` GET。管理员对应 `/api/admin/teams/ambassador-applications/{id}/materials` GET、`/files/{fileId}` GET、`/review` POST。上传、提交和核验必带 `Idempotency-Key`，复用既有持久幂等回执；同键同载荷重试返回原回执，冲突载荷拒绝，必要审计失败后原键可恢复。上传指纹包含类别、文件名、实际类型与文件字节摘要，响应丢失后原键返回同一附件。申请行锁串行化材料提交、核验和批准。

以下为请求示例，附件ID需使用实际上传返回值，不代表已实测返回：

```json
{"expectedMaterialRevision":0,"attachments":[{"fileId":"2d30dc76-a1b6-41db-9f29-45be0dcb607f","kind":"attendance"}],"statement":"活动签到来源与去重规则说明"}
```

```json
{"expectedMaterialRevision":1,"stage":"BUSINESS","decision":"PASSED","reason":"已核对活动与去重签到原始材料","verifiedAttendees":100}
```

```json
{"expectedMaterialRevision":1,"stage":"FINANCE","decision":"PASSED","reason":"已核对费用凭证与可认可金额","recognizedBudgetUsdt":"1000.000000"}
```

响应沿用 ApiResult，`data` 直接为材料包，上传 `data` 直接为 `{fileId,kind,name,contentType,sizeBytes}`。材料包包含 bucket（旧缺失为null）、materialRevision、materialState、requirements、attachments、businessReview、financeReview、missingKinds、statement、可用动作及 approvalBlockers。另提供 `requirementsByBucket` 四类材料要求字典；旧待审缺类别时，页面根据本人新选类别显示对应要求，按受支持kind上传，再将明确 bucket 与附件一并首次提交，不猜默认类。未核验时 review.status 为 PENDING，主体、时间、理由及金额/人数为null。reviewHistory 提供历史版本和阶段的核验记录，不下发管理员ID用于客户端权限推断。

原 `F.ambassador.{id}.status` 批准命令增加独立的 `expectedMaterialRevision`，不复用 expectedVersion。A2 原提案保存该版本；回放再次进入同一最终批准门禁，缺失/过期版本不自动绑定新材料。A2 使用 `{domain:"F",type:"ambassador_application",id:String(id)}` 对象锁、obj=String(id)、sourceDomain=F4。队列返回 `ambassadorMaterialProposal`，展示本申请类别、申请/认可金额、原票预期版本与当前版本、两阶段结论及批准阻断原因。材料补交不删除 A2 旧票，原票因版本不一致拒绝生效。

F4 材料包另提供 `proposalBlockers`：从 approvalBlockers 中去掉 `SELF_REVIEW_APPROVAL_FORBIDDEN`；缺最终业务权限保留 `PERMISSION_DENIED`，缺 `platform_a2_write` 和 `platform_a2_proposal_create` 时加入 `A2_PROPOSAL_PERMISSION_REQUIRED`。`canProposeApproval` 仅在该列表为空时为true。参与核验的人可以作为提案人，最终由另一有权管理员执行。`canApprove` 始终按实际最终执行人的职责分离计算，A2 摘要继续使用该严格字段；A2 创建权限不进入 approvalBlockers 或最终执行门禁。

A2 的 `ambassadorMaterialProposal.applicationDecision` 由原 command.params.value 独立映射：approved／通过／已批 为 `APPROVE`，rejected／驳回／已驳 为 `REJECT`，未知值为null并拒绝创建此类提案。页面不得通过 afterValue 说明文案猜测批准或驳回；原票材料版本始终从 expectedMaterialRevision 展示。
