# BE-27 F4 榜单取消资格的风险证据

依据 B30 第 27 项、S06 与 F-PD06。

取消成员本周榜单资格需要该成员有本业务周内由 K2 服务产生的有效刷榜信号，且信号关联的有效榜单行必须以该成员为检测对象。同簇成员随该行收到的信号和通用风控接口录入的同名信号不能作为 K2 依据。K1 依据要求该成员实际属于达到检测阈值的待处理簇，或属于已标记或已冻结的簇。已解除、已清除或已删除的簇不作为依据。K2 信号按 GROWTH_TEAM 业务周计算，包含周初，截止于下一周周初之前。

A2 发起和实际处置时都核验证据。无证据返回 HTTP 422 `NO_RISK_EVIDENCE`，不会取消资格。审批前证据已失效时，原申请保持待审。直接通过原 F4 配置接口发起的同一成员处置也受证据检查。成功处置的审计包含实际使用的 K1 簇编号或 K2 信号编号。

区域大使审批的材料核验门槛待明确权威数据来源和操作入口。申请单目前只记录 App 提交内容、审批状态和开通预算。需明确线下签到真实性与人数、KOL 发票及流量的独立核验结果，以及物料和 SDK 配额如何映射到现行预算类别与申请号。材料核验应是独立于大使批准和 A2 决策的持久状态，本次维持现有批准与拒绝流程。

## 2026-11-16 补充：派奖只读预览与取消资格可读判据

总榜派奖在批准前看不到后果，取消资格只能提交后才知道会不会被拒。现补两个只读读取，均沿 `network_f4_read`，**不写任何东西**：不结算、不建事件、不动榜单/额度/审计、不认领幂等键、不加锁。

- `GET /api/admin/teams/leadership-pool/payout-preview?period=week&periodKey=YYYY-MM-DD` 按批准派奖同一规则解析 `today`、`week`、`month`、`allTime`。日、周、月未结束时返回 `422 F4_CLOSED_PERIOD_REQUIRED`。返回真实用户（`userId` 和榜单同格式 `userNo`）、名次、`computePoints`、`amount`、本期奖池、`topN`、`minComputePoints` 及金额合计。现行金额和告警见下方 BUG-698 补充。
- 预览与结算调用同一套分配计算。两次读取所用配置和候选一致时，预览金额等于实际发放金额。只读路径不取得结算互斥锁，也不写 `lastSettled` 检查点。
- 读不到真实依据时返回 `available=false` 与原因，不填猜测值：`F4_LEADERBOARD_POOL_NOT_CONFIGURED`（奖池未配置或为 0）、`F4_LEADERBOARD_PAUSED`、`F4_LEADERBOARD_ALREADY_SETTLED`（本期已有结算键）、`F4_LEADERBOARD_NO_CANDIDATES`（门槛以上无人）。
- `GET /api/admin/teams/leadership-pool/disqualification-readiness?limit=50`：返回本业务周榜单候选行，逐行给 `disqualificationAvailable` 与该行实际依据 `riskEvidenceRef`（K2 信号编号或 K1 簇编号），无依据时 `reason=NO_RISK_EVIDENCE`。判据复用 A2 发起与实际处置同一查询，不新增风险定义，不放宽也不收紧。
- 榜单展示快照（暂停冻结信封）与 `leaderboardPeriods` 结构不变；本补充只新增独立读取，页面是否展示另议。

## 2026-11-16 补充：两种真实派奖在批准执行时复核兑付覆盖率

团队池提前结算（A2 `f4_pool_settle`）与总榜派奖（A2 `f4_leaderboard_period_payout`）的执行链此前只校验权限与周期，没有任何兑付覆盖率调用——覆盖率只在提交提案或旧确认文案里提过。现按与补发相同的判据，在批准回放、第一笔事件或钱包写入之前复核一次：

- 快照不可用或不可靠（`null` / `reliable()=false`）→ `503 COVERAGE_SNAPSHOT_UNAVAILABLE`，不当 0、不放行；
- 覆盖率低于红线 → `422 COVERAGE_BELOW_REDLINE`；等于红线按既有规范放行；实际覆盖率为 0 仍按读取值参与比较，不特殊放行。
- 已结算的周或周期保持原来的幂等空操作（团队池按 `countLeadershipByWeek`、榜单按 `countLeaderboardBySettlementKey` 判断），重复批准不会因为之后覆盖率读数变化而由成功变为失败。
- 只加这两条 A2 批准路径的门：自动/系统周期结算（`injectAndSettleCurrentWeek`、`injectAndSettleLastClosedWeek`、`settleClosedLeaderboardPeriods`）与只读预览（`payout-preview`）保持原行为，不触发写入、不认领结算键。
- A2 双人、对象锁、回放事务、周期解析、派奖金额、remark、审计与账本幂等键均不变；未新增锁、表、配置或框架，未改前端与下发文案。

## 2026-11-17 补充：原业务周资格排除只在指定业务周生效

`nx_team_leaderboard_action` 记录的是业务周处置提交时的事实，没有独立的目标周列；原读取只按 `period='week'` 连接/排除，导致历史上提交的取消资格在之后的每个业务周继续生效。现按既有同一周时基补齐读取边界，不改任何记录：

- PC 侧当前榜单/奖池投影（`leaderboardPodium`、`leaderboardSummary` 的命中数与 `periodStatus`、旧候选读取）在原有 `period='week'` 之外要求动作 `created_at` 落在当前 `VietnamBusinessPeriodSql.WEEK_START` 至 `NEXT_WEEK_START`；
- App 与 F4 共用的 `LEADERBOARD_ELIGIBLE_SQL` 仅在 `actionPeriod=week` 时，使用调用方已传入的同一目标周 `fromInclusive`/`toExclusive` 过滤动作；F4 周结算、周派奖预览和周资格就绪读取因此只认该指定业务周内提交的处置。
- 周调用方已有可靠的半开周边界；不补当前周。`today`、`month`、`allTime` 等其它周期的动作时间过滤策略保持原样，无界 all-time 不表示缺失周窗口。历史动作保留原行，不回填、不改 `period` 或 `created_at`。

排名指标、候选 SQL 的订单窗口、结算/奖励算法、金额、奖池、审批、权限、历史周记录均未改；未新增 schema、过期模型或页面文案。本轮只准备 Java 与既有 F4 PRD，未执行 HTTP/DB/E2E。

## 2026-11-24 补充 · BUG-698 榜单头部占比告警

- 按 OP-142，日、周、月自动结算和 A2 批准的榜单派奖均按原名次权重 `N…1` 分配 USDT。每人金额保留六位小数并向下舍入，按舍入后的各人金额合计发放。团队激励池按票权分配沿用原规则。
- 第 1 名金额和前 5 名金额之和各自除以配置奖池，严格超过各自阈值时分别记录 `top1MaxPct` 和 `top5MaxPct`。阈值只用于告警，继续使用 0–100 百分数点和未配置时的 25、60。支持已保存的纯数值和带百分号数值。
- 预览和成功结算审计 `F4_LEADERBOARD_PRIZE_SETTLED` 返回相同规则产生的 `concentrationWarnings` 字符串列表，并记录两项有效阈值。没有命中时列表为空。预览兼容字段中，每行 `amountBeforeCaps` 等于 `amount`，`limitedBy` 为空列表。汇总 `amountBeforeCaps` 等于 `payableAmount`，`reducedByCaps` 为 0。
- 两项阈值写入沿用 `network_f4_pool_fund`，调整阈值按普通参数变更处理。现有奖池和注入比例的资金校验继续生效。A2 榜单派奖仍以原 `period` 和 `periodKey` 为审批对象，回放时使用当时配置及候选，并在首笔资金写入前复核兑付覆盖率。暂停、周期幂等、审批权限和历史结算记录沿用现行规则。
- 后端发起 A2 榜单派奖时保存本次分配规则。升级前仍待审的派奖单批准时返回 `409 F4_LEADERBOARD_PAYOUT_REVIEW_REQUIRED`。发起人撤回或审批人驳回后，可查看新预览再重新提交。已执行的审批保留原回执。

## 2026-11-27 补充 · B134 F4 审批回执记录实际入账

- 批准榜单派奖 `f4_leaderboard_period_payout` 或团队激励池提前结算 `f4_pool_settle` 后，批准响应的工单、A2 概览 `operationQueue` 里的同一工单及发起人原号查询返回 `businessResult`。成功批准的原号重放返回同一结果，沿用各入口现有的可见权限。
- 已入账返回 `status=EXECUTED`、实际入账笔数 `creditedCount`、按币种汇总的 `amountsByCurrency` 和实际 `settlementKey`。当前两项均以 USDT 入账，金额合计取已入账金额。例如配置奖池为 1 USDT，两名榜单获奖人分别入账 0.666666 和 0.333333 USDT，回执金额为 0.999999 USDT。工单结果和资金写入同一事务提交。
- 空操作按原规则完成审批，回执保存 `status=NOT_EXECUTED`、`creditedCount=0`、`amountsByCurrency={}`、`reasonCode` 和 `settlementKey`。榜单原因包括已结算 `F4_LEADERBOARD_ALREADY_SETTLED`、没有合格名单 `F4_LEADERBOARD_NO_CANDIDATES`、奖池未配置 `F4_LEADERBOARD_POOL_NOT_CONFIGURED`、金额舍入后无可支付值 `F4_LEADERBOARD_NO_PAYABLE_AMOUNT`。团队池原因包括 `F4_POOL_ALREADY_SETTLED`、`F4_POOL_NO_ELIGIBLE_VOTERS`、`F4_POOL_NO_VOLUME`、`F4_POOL_MONTHLY_CAP_REACHED`、`F4_POOL_NO_PAYABLE_AMOUNT`。
- 暂停 `409 F4_LEADERBOARD_PAUSED` 和覆盖率不足 `422 COVERAGE_BELOW_REDLINE` 保留原错误码，工单继续待审批并保留对象锁。该批准号的错误响应在 `data.businessResult` 给出零入账、原因和 UTC 时间 `attemptedAt`，查询原批准号可读到拒绝状态和错误码。业务事务回滚后，待审批工单通过 `lastApprovalAttemptResult` 回读最近一次此类阻断。工单的 `canApprove` 表示当前审批资格，阻断记录表示当次业务检查结果。限制解除后，经重新确认可用新批准号处理同一工单。审批完成后工单显示最终 `businessResult`，原批准号仍可读回对应尝试。覆盖率快照不可用和事务结果不明沿用原号恢复规则。
- 历史工单缺少当次结果时省略 `businessResult`。自动结算和只读派奖预览仍分别使用原调度与预估规则。

## 2026-11-27 补充 · B145 已结算团队池的审批结果

- A2 批准提前结算取得该周互斥锁后，先核对已有入账或已完成的零笔结算记录。已结算时返回 `NOT_EXECUTED` / `F4_POOL_ALREADY_SETTLED`，工单照常完成，回执的入账笔数与金额均为空操作结果。此时允许结算设置处于 `HOLD`。
- 未结算周继续执行覆盖率和结算配置检查。结算设置不完整仍返回 `503 F4_SETTLEMENT_CONFIG_UNAVAILABLE`，审批保持待处理，资金无变更。
