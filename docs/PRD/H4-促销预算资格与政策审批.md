# H4 促销预算资格与政策审批

## 预算资格（BUG-268）

`RULE_STOP` 按购买规则判断新预留的可用性。App/H5 活动列表、首页推广位及详情读取当前预算净额、活动可用名额及赠品库存。全部规则停止新增预留时，首页停止投放，活动列表仅保留供团队页读取既有进度的直邀活动。已知链接仍可读取详情和原条款。保留的活动记录继续使用原生命周期，返回 `INELIGIBLE` 和可用性原因。已有订单可继续按原预留处理。

部分规则仍可用时，继续展示该活动及可用奖励。`ANY` 返回仍可领取奖励的商品，`ALL` 保留完整组合所需的商品。规则资格预估使用最小合格数量，已登录且符合活动人群的用户按实际受益人及使用记录计算。实际订单按所选商品、数量、受益人和实时资源重新计算。资源释放后，后续读取恢复可用资格和推广投放。

显式选中活动但没有任何可发放奖励时，`POST /api/orders/quote` 返回 `PROMOTION_NOT_ELIGIBLE_OR_UNAVAILABLE`。未指定活动时，满足购买条件的普通报价仍可继续，`expectedRewards` 为空。报价不占用额度。

## 政策批准（BUG-272）

每个政策版本必须由与创建人不同且持有 `growth_promotion_policy_approve` 权限的管理员批准。以当前登录管理员和成功创建该版本的服务端审计为准，创建审计移入冷档后继续适用。创建人本人批准返回 `PROMOTION_MAKER_CHECKER_REQUIRED`，创建人无法可靠核实时保留草稿，返回 `PROMOTION_POLICY_MAKER_UNAVAILABLE`。

批准沿用版本校验、审批人的审计证据或已批准的 H 域 A2 凭证，以及按管理员、操作、政策版本划分的幂等范围。成功重放读取原回执，审批审计与状态变更只写入一次。

## 2026-11-16 补充：促销命令原键只读恢复

`GET /api/admin/growth/promotion-commands/{idempotencyKey}?operation=&targetId=` 的恢复读取不再要求该 operation 的写权限：当前已认证管理员持有 `growth_promotion_read`、且 operation 属于合法命令即可。记录仍按 `PROMOTION_ADMIN:{actor}:{operation}:{sha256(target)}` 限定为本人原记录，原成功／失败／处理中／结果未知／不存在的回执形状不变；非原操作者、换 operation 或 target 仍返回原 `NOT_FOUND`。读取不重跑命令、不写审计、不续期、不结案，也不授予任何写权。

## H4-BE-14/15：复制与保存的预期版本（2026-11-16）

复制活动的请求同时携带活动 `expectedRevision`、所见源 `expectedSourceVersion` 和 `expectedSourceRevision`。后端比较真实源版本及其内容修订号，避免源草稿在版本号不变时已被他人保存。保存草稿除原 `expectedRevision` 外还比较 `expectedVersion`，避免删除重建后的同修订号草稿接收旧请求。缺失或不一致均沿用 `PROMOTION_CONCURRENT_CHANGE`，成功原键仍先恢复。

新增字段只在对应复制或保存入口要求，不影响共用动作的其它操作。只更新后端请求合同，未修改 PC、下发文案或运行数据；按本轮代码口径验收，未 E2E。

## 2026-11-16 补充：政策读取按真实批准人给出可空姓名与账号

政策版本的读取此前只回 `approvedBy`（`nx_promotion_policy.approved_by` 的原样编号），管理端无法显示批准人是谁。现在管理端两个只读投影（`GET /promotion-policies` 列表与 `GET /promotion-policies/{policyId}/versions/{version}` 详情，权限仍是 `growth_promotion_policy_read`）在原有字段之外追加可空结构 `approvedByAdmin`：

- `approvedByAdmin` 由 `approvedBy` 的真实编号查询**当前未删除**的 `nx_admin` 得到，形如 `{ id, displayName, username }`；`displayName` 沿用仓库既有规则（优先 `nickname`，为空回退 `username`）。
- `approvedBy` 保持原样（含空值与历史编号），不改数值、不改字段含义；`approvedByAdmin` 在该编号对不上当前管理员、或从未有批准人时为 `null`，不用操作者、最近修改人或其它人冒充历史批准人，也不补历史快照。
- 共用解析器 `PromotionPolicyResolver.view` 与 App/H5 侧输出**不新增**任何管理员姓名或账号；本次只改管理端服务层投影，公开读取、可见范围与权限不变。
- 姓名查询失败按「无真实来源」处理为 `null`，不影响政策读取本身；不新增表、缓存、配置或页面文案。

## 2026-11-16 补充：奖励处置证据上传只给该处置专权

H4 奖励处置（取消 / 回退 / 结案）需要在提交时附可核验证据图片。管理端上传走共用 `POST /api/admin/media/uploads`，原授权只放行 `device_e1_write` 与「`growth_promotion_edit` + `domain=growth` + `usage=promotion-banner`」，合法的奖励处置操作者既无 E1 写权也无政策编辑权，无法上传；而提交时 `evidenceRefs` 又只接受 `admin/growth/promotion-evidence/` 命名空间下的资产，形成死路。

现按用途精确放行，不把其它媒体权限一起放开：

- 允许 `domain=growth` 且 `usage=promotion-evidence` 的上传，前提是操作者持有奖励处置专权之一：`growth_promotion_reward_cancel`、`growth_promotion_reward_reverse`、`growth_promotion_reward_resolve`（与三个处置端点同权）；HTTP 前置过滤的精确名单同步加入这三项，否则请求到不了方法层。
- 同一次上传的其它用途仍按原规则：E1 图片只有 `device_e1_write`，横幅只有 `growth_promotion_edit`；只持 `growth_h4_read` 或 `growth_promotion_reward_read` 的操作者仍不能上传。
- 不新增权限码、不改前端请求参数与文案、不改读取侧：`preview-url` 的读取名单保持 `device_e1_read` / `growth_promotion_read` / `growth_promotion_edit`，上传回执自带预览地址。
- 文件类型/大小校验、幂等键与请求摘要、存储命名空间、owner 归属、私有存储与上传回执均不变；未创建任何资源或历史证据。

## 2026-11-18 H4-BE-03：整单退款结案的处理元数据

- 政策读取（`PromotionPolicyService.get` 与 `page`，两者共用 `withApproverIdentity` 投影）对已知合同 `kind=REFUND` 且 `executorCode=PROMOTION_WALLET_REFUND_V1` 的行，额外返回只读 `execution` 元数据；其它政策不新增该键，响应保持原样。
- 字段与真实依据：`basis=WHOLE_ORDER_REFUND_CONFIRMED`（已确认整单退款依据）；`walletRecovery=SAME_ASSET_AVAILABLE_BALANCE` **只指钱包类资产（UVT、USDT）**按同币种可用余额追回（`crossAssetDeduction=false`、`negativeBalance=false`）；`deviceRecovery=REVOKE_GIFT_DEVICE_CANCEL_OPEN_TASKS_KEEP_POSTED_EARNINGS`（赠品设备 `ownership_status=REVOKED`/`DEACTIVATED`、未完成计算任务取消、运行时停止，已完成/已到账收益保留并计入平台损失）；`insufficientRecovery=PLATFORM_LOSS_AND_CLOSE`（追回不足部分计平台损失并结案）；`terminalState=REVERSED`。来源为 `PromotionRewardService.reverseLocked`：整单退款路径 `next = wholeRefund || outstanding==0 ? REVERSED : MANUAL_REVIEW`，`outstanding>0` 时写入 `platformLoss` 与 `evidence.platformLoss`；资产为 `DEVICE` 时走设备回收分支，仅非 `DEVICE` 才走钱包同币种追回。
- 边界：`manualReviewAppliesTo=APPROVED_CORRECTION` 表明 `MANUAL_REVIEW` 只用于独立纠正追回不足的情形；`unknownEvidence=ORIGINAL_REFUND_CHECKS` 表明退款证据或发放状态未知时仍走原有核对（不进入该元数据描述的处理）。
- 历史意义：严格 v1 `content` 仍写 `insufficientRecovery=MANUAL_REVIEW`（已存的合同文本、`content_hash`、schema 与签名均不改，不回填历史行）；`execution` 是对现状的只读说明，不替代也不改写 content。
- 未改：权限、退款/审批/写回执、预算与奖励实际行为、页面与下发文字、非 REFUND 政策。

## 运营区域语言（2026-11-18）

普通促销草稿可分步录入，创建、保存、复制和建立草稿版本保留提交的语言键和值。翻译键可省略，给出时至少有一个字符。送审时将标题及条款作为一组校验，在同一事务内保存完整合同、内容哈希和待审状态。创建设备权益、资产及退款政策版本时，分别校验权益说明、可用性说明和退款条款，并在创建不可变版本前补齐。正式提交要求英文和运营区域语言。未选中的中文或越南语整组留空时复制对应英文，部分填写时拒绝。批准和发布消费已冻结的文案和内容哈希。
