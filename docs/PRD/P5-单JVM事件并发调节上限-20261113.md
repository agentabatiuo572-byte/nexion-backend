# 单JVM计算事件并发可调上限

PROD44恢复期按同口径SQL调用采样，发布UPDATE约401次/秒，新增INSERT约662次/秒；缓冲池8→10→8 GiB、600秒对照的发布UPDATE约395次/秒。它们不是唯一已提交事件吞吐，负载随恢复过程变化，不能据此认定因果或万人容量。仅扩大缓冲池未观察到发布瓶颈改善。

本批将 `task.completed`、`earnings.credited` 每类lane上限从8改为16，总计算线程可配置上限从16改为32。`nexion.outbox.compute-dispatch-workers` 默认仍为8，原夹取逻辑保持；已有显式16不会自动变成32。发布后的实际线程数必须读回。

每lane仍以原顺序一次读取最多40条并逐事件处理。数据库lane锁、逐事件命名锁、owner检查、各消费者事务、claim/terminal、失败重试、DEAD与幂等规则保持。分片仍由原 `MOD(id DIV 2, laneCount)` 算法确定，laneCount随上限变为16；正常滚动或回滚的跨版本重叠仍由逐事件锁协调。资金、资格、任务600秒周期、页面与客户端刷新行为不变。

部署复测参数候选为：单JVM，计算线程先24，公共调度12，Hikari max96/min8，MySQL max_connections200。只有24线程的资源、竞争和结果允许时再对照32。连接池扩大是运维候选，代码提交不表示上述参数已生效；正式和隔离分别留存原件。容器预算、JVM堆、Buffer Pool与资金耐久1/1/ON按已核配置保持。

验证计划：

1. test及窄main候选用Java17打包并跳过全部测试源码和测试执行，进行独立静态复核；打包不算业务验收。
2. 本批main得到明确批准后，在PROD构建，核对实际JAR、worker数、lane数、Hikari、RR、严格TLS和正式健康。TEST服务器不构建、不压测。
3. 在PROD隔离核对自然任务、结算、收益及钱包/账本不重复；分别统计新增和消费的唯一提交事件、SQL调用、分类型积压、连接等待、CPU/IO/GC/内存及死锁。不能只以线程参数或SQL计数放行。
4. 按1000→5000→10000逐档验证，每人6台正常付费激活设备、原600秒任务；900/900/1800秒计量与60秒尾段、10秒观察SQL、1800秒预热、全部在线/资金/幂等/时延门槛保持。冷恢复另列，无自动升档。
5. 沿用原混合登录、查询、下单、提现及结算入口；QA C正常新增购买与同key重放、QA B 20/1/19 Mock提现仍按既有授权及完整账务要求。并发增加出现新死锁、连接等待或结果不一致时保留FAIL并停止升档。

参数回退到16线程/64连接只能恢复并发和池大小；如需完全恢复每类8lane，回滚到已知PROD44产物与对应原配置。结束或等待用户批准时，取得同owner正式与私基线的实际恢复回执，不遗留正式临时小配置。
