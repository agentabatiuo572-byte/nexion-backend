# K1 账户组解除与规则放宽的覆盖率

- 解除误判（`released`）和判定为正常（`cleared`）沿用 A2 双人审批。批准执行时以 B1 精确覆盖率与红线比较，恰好达到红线允许执行。有效正覆盖率低于红线返回 `COVERAGE_BELOW_REDLINE`，覆盖率不可用或显示值为零时返回 `K1_COVERAGE_UNAVAILABLE`。失败时账户组、提现限制、审批单和对象锁保持原状态。恢复后可用同一个批准幂等键重试。
- 批准移除该组状态造成的提现限制。其他待处置组、账号数达到现有冻结起点、受保护收益和账户自身状态仍按各自规则判断。
- A2 工单在这两种操作上返回 `coverageCheckOnApproval=true`，供确认文案说明校验时点。
- 新增或重新启用 IP 白名单、延长有效期，以及调大同 IP 24 小时注册、同设备关联或同支付工具关联的账号上限，在保存时执行同一覆盖率检查。停用、缩短有效期、仅修改备注及调低上限继续按原流程执行。
- 定时检测按当前白名单和上限发现新风险。既有待处置组仍需人工处置。即使当前检测没有该组，或关联投影减少了成员，系统也保留原组和原成员的提现限制。规则放宽后没有当前风险信号的组仍可在 K1 查询和处置。

## 2026-11-17 K1-BE-01：复用收益审核规则与人工放行审批候选

本次只接续已验生产候选 `7fd79d45` 的 K1-A09/A11 局部差异，保留当前 A2 其它业务分支。后端源码入口为 `K1RiskApproval`、`RiskReleaseParamsService.approvalBefore/previewApproval/applyApproved` 和 `EarningsReleaseService.approvalBefore/previewApproval/applyApproved`。不改现有候选的审批摘要或客户端页面，不夹带其它 Bug 范围。

### 提案输入与服务端绑定

两类提案均使用 `POST /api/admin/platform/audit/operations`，请求头为原 `Idempotency-Key`。发起人具当前 `risk_k1_cluster_release` 及 `platform_a2_proposal_create` / `platform_a2_write` 之一。以下为源码定义的请求形状示例，没有实际发送 HTTP：

```json
{
  "action": "放宽收益审核规则",
  "obj": "duplicateAccountPendingFrom",
  "type": "fund",
  "reason": "填写本次放宽的真实理由",
  "sourceDomain": "K1",
  "command": {
    "domain": "K",
    "op": "k1_release_param",
    "params": {
      "values": {
        "key": "duplicateAccountPendingFrom",
        "value": "3",
        "expectedVersion": 1
      }
    }
  },
  "target": {"domain": "K", "type": "release_param", "id": "duplicateAccountPendingFrom"}
}
```

示例的值及版本必须替换为实际读取值和本次拟值。A09 的另一个合法 key 为 `duplicateAccountFreezeFrom`。A11 使用相同外层结构，`action` 为原候选的“人工放行收益”，`obj` 为真实 `entryNo`，`command.op=k1_earnings_release`，`command.params.values` 仅为 `{"entryNo":"实际收益编号"}`，`target={domain:"K",type:"earnings_release",id:entryNo}`。两类都不传多目标 `targets`；values 中未知字段拒绝。

客户端提供目标、新值、A09 的 `expectedVersion` 和理由；不提供可信 before、maker 或批准人。`bindMaker` 重建 params，绑定真实管理员数字 ID 及服务端读取的完整 `before`，A2 再保存服务端 `proposalReason`。客户端的外层 `beforeValue/afterValue/operator/operatorRole/roleGate/amplifies/sos` 不作为业务快照或权限依据，可省略；action/type 在 A2 先做原基本校验，再由服务端 descriptor 写入最终值。提案必须使 `obj/sourceDomain/target` 与真实命令一致，否则 `403 A2_BUSINESS_CONTEXT_MISMATCH`。

| 操作 | 服务端 before | 最终票据元数据 |
|---|---|---|
| A09 | `key/value/version/values`，其中 values 是当前有效收益参数完整快照，version 以字符串保存 | `action=放宽收益审核规则`，`obj=key`，`type=fund`，`amplifies=true`，`roleGate=超管`，`sos=false` |
| A11 | `entryNo/userId/sourceType/sourceRef/sourceEnvironment/asset/grossAmount/recoveredAmount/netAmount/bucket/status`；userId 及三个金额在 command before 中为无损十进制字符串 | `action=人工放行收益`，`obj=entryNo`，其余同上 |

请求的 `sourceDomain` 必须为 `K1`；既有 A2 持久化/票据返回按首字母规范化为 `K`，不要要求票据返回 `K1`。结构化 before 存于 `command.params.before`；原 A2 票据的 beforeValue/afterValue 仍为已批准候选的摘要，不从这些字符串反解金额。

摘要保持原候选模板：A09 的 before 为 `{key} = {旧值}；版本 {version}`，after 为 `{key} = {新值}；版本 {version+1}`。A11 的 before 为 `收益 {entryNo}；用户 {userId}；{asset} 净额 {netAmount}；来源 {sourceType}/{sourceRef}；{bucket} → withdrawable；当前覆盖率 {coverage}% / 红线 {redline}%`；after 为 `批准后仅将该受保护 entry 的 bucket 改为 withdrawable，净额 {netAmount}；不新发奖、不生成提现单、不重复记账；冻结/簇/钱包限制仍按后续提现链执行`。

### 实际读取入口与执行边界

- A09 从原 `GET /api/admin/risk/multi-account/overview` 的 `releaseParams` 读取 key/value/version，沿用 `risk_k1_read`。提高两个阈值为放宽；新直写返回 `409 K1_RELEASE_PARAM_APPROVAL_REQUIRED`。收紧/同值直写、范围、阈值关系、退役 410 及原成功键恢复保持。待审期间合法收紧/同值直写不新增对象锁；旧票在版本/完整快照变化后拒绝。
- A11 从原 `GET /api/admin/risk/multi-account/releases` 的 items 读取完整净额快照，沿用 `risk_k1_read`、原 userId/clusterId/limit 筛选及行范围。同一 SELECT 返回 `grossAmount=e.amount`、`recoveredAmount=e.recovered_amount`、`netAmount=e.amount-e.recovered_amount`、`sourceEnvironment=e.source_environment`、`status=e.status`，金额为原精度数值；原 `amount` 继续等于净额，其余原字段不变，不新增读取端点或放宽权限。建单不信任客户端把这些读取值传成 before，仍由服务端重新读取。新直放返回 `409 K1_EARNINGS_RELEASE_APPROVAL_REQUIRED`；旧成功键按原 body 恢复。
- 同一 target 已待审时，原 A2 检查或唯一键并发冲突返回 `409 OBJECT_ALREADY_PENDING`，不以 `OBJECT_LOCKED_BY_A2` 冒充建单返回码。待审只存票据及对象锁，不改业务值。本人按原 `GET /api/admin/platform/audit/operations/proposals/by-idempotency-key` 恢复，仍需原 maker 和当前精确 K1 业务权加提案资格；不授全局 A2 读权。
- 批准人须为另一名有效超管且有 `platform_a2_operation_approve`，自批 `A2_MAKER_CHECKER_REQUIRED`。回放复核服务端 proposalReason、唯一原票对象锁与现 A2 operationId。A09 比较完整 before/version，再复用正式范围、关系和 B1 校验及写入，陈旧 `K1_RELEASE_PARAM_STALE`。A11 保持用户→钱包→source 锁顺序，锁定 RecoveryEntry 比较完整来源/环境/毛额/已追回/净额/bucket/status，陈旧 `K1_EARNINGS_RELEASE_STALE` 或保护状态拒绝，再沿正式释放、审计及资金投影；不新发奖或入账，不新增账户/簇放行规则。
