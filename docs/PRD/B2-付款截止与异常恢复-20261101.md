# B2 付款截止与异常恢复（2026-11-01）

依据：用户2026-10-31后发付款合同，uvel-docs 20-B2及本轮P01–P06测试计划。钱包继续要求PIN；外部三通道不读PIN。费用维持未配置，不开通或发起实款。

- 订单自创建30分钟截止；既有促销pay_by更早时从严。付款单expiresAt=deadlineAt，报价有效期≤15分钟且≤deadline。无既有订单的换购/体验转正等从不可变业务报价时刻计30分钟。
- BEP20确认宽限3分钟、ERC20/银行卡5分钟。宽限只接截止前已付款而确认慢的款项；付款链接/地址在用户视图截止后不再提供，paymentAllowed=false。银行卡还取已核供应商expirationTime较早值；confirmationGraceEndsAt始终从订单截止起算。
- 到宽限终点先查原意图，再与订单PAYMENT_TIMEOUT终止、原有预占库存/配额/券/促销释放同事务；新未预占不增加库存。查询失败不延长可付款窗口，reconciliationStatus=QUERY_UNKNOWN单独持久保留；EXPIRED意图仍由原编号持续查单，后到款进入人工处理，不生成替代收款或自动退款。任何已确认资金或已交付事实不会被超时覆盖。旧失败单不得取消正在进行的新尝试。所有曾直付订单（含失败可重试）均退出generic TTL关单，统一由直付固定截止与宽限终止，防止旧TTL配置10/90分钟改变用户窗口。冻结账号仍按硬截止释放。
- HDPAY5→EXPIRED/PAYMENT_FAILED，截止前允许新报价/新付款键重试；4→MANUAL_REVIEW/PAYMENT_REFUNDED_REVIEW。首次截止后观察成功但无可信付款时间→PAYMENT_TIME_UNVERIFIED；到宽限外或确实截止后付款→PAYMENT_LATE_REVIEW。不得以查单时刻填供应商实际付款时间。
- BUG-160：商城订单已到截止、仍待付款且确认到账为 PAYMENT_LATE_REVIEW 时，通过原超时流程关单并释放已有预占。付款单保留 MANUAL_REVIEW、确认时间及付款凭据，继续由财务复核，无交付或自动退款。若有仍可能正常结算的新付款单，由新单按原规则结算或超时关单。重复回调与对账不会重复释放预占或发布结果通知。
- HDPAY明确付款时刻不得早于原意图created_at；早于创建时保留原paidAt并进入既有PAYMENT_BEFORE_ALLOCATION人工审核，自动交付和显式重审均不得交付。
- 正常交付仍原子复核商品、库存、槽位、配额、优惠等。只有服务端已经验证及时到账的直付作用域允许宽限期交付，钱包付款截止规则保持原有行为。
- BUG-701 试用转购直付以原付款单核定的付款时刻和渠道确认宽限为准。截止前付款且宽限内确认的，按原领取单、报价和机位交付，支持交付重试。待确认付款由对账判定终结，仍可交付的已确认付款继续保留试用和机位。确认宽限内待财务复核的款项也保留试用，宽限结束后由财务按原渠道处理。试用被付款占用时，定时任务延后关闭，用户取消返回 `TRIAL_EXTERNAL_PAYMENT_IN_PROGRESS`。H2 审批强制取消继续走原路径。
- B104 试用转购首次生成 USDT 或银行卡外付报价时，冻结 `trialPurchaseBreakdown`。明细包括商品编号、名称、可用的商品副标题，以及试用接受报价的售价、购机折扣、试用抵扣金、提前购买立减和业务应付金额。创建付款单原样保存这份明细，本人凭原付款号读取时，商品改价、改名和报价到期都不会影响明细。没有明细的历史付款单省略该字段。渠道费用、收款金额和结算按原合同处理。
- B109（BUG-752）试用转购按六位业务应付判断。应付大于 0 且低于 0.01 USDT 时，购买清单的 `paymentMethods` 只返回 `WALLET`，验密后按六位应付扣款。新银行卡和 USDT 报价在外付按分取整、检查渠道前返回 HTTP 409 `TRIAL_PAYMENT_AMOUNT_REQUIRES_WALLET`。旧的未用报价按原报价的六位金额校验，缺少六位快照时按通过价格核对的原报价计算。拒绝的新建单无付款单、地址分配或名额预占。原键找回、已受理付款的读取和结算继续按原付款单处理。应付恰为 0 或达到 0.01 USDT 时沿现有规则。
- B109 补充（2026-11-26）。同一领取单和报价版本确认创建外付时，预检和建单事务都复核当前六位业务应付。累计抵扣使应付从 0.020000 降到 0.008000 USDT 时，返回 HTTP 409 `TRIAL_PAYMENT_AMOUNT_REQUIRES_WALLET`，钱包验密后扣 0.008000 USDT。降到 0.000000 USDT 时，返回 HTTP 409 `ZERO_PAYMENT_REQUIRES_WALLET`，钱包验密后完成转购，无扣款借方。这两种拒绝均发生在创建付款单、分配收款地址、预占名额和发起渠道付款之前。当前应付仍达到 0.010000 USDT 时，符合原有校验的报价仍按原金额建单。报价版本变化仍返回原报价冲突回执，已受理付款可凭原付款号继续或用原请求键找回。
- 同一领取单有在途外部付款时，延长试用和钱包转购也返回 `TRIAL_EXTERNAL_PAYMENT_IN_PROGRESS`。旧付款转为财务复核时，后续未付款尝试仍能独立超时，超时只释放该付款单的预占。定时任务分批轮转已经到期的领取单，前一批仍在等待付款时继续扫描后续领取单。
- BUG-673 外部直付在同一已核付款作用域内，用已核付款时刻复核促销 pay_by 并保存实际付款时刻。钱包付款的订单落库按数据库当前时间校验 pay_by。
- BUG-674 迟到款关单在原事务中释放本付款单仍为 HELD 的预占，保留人工复核凭据。历史上订单与付款状态都已 EXPIRED 的迟到款，由原对账轮转释放同一付款单仍为 HELD 的预占。
- 交付/超时/人工分别提交唯一结果事实；现有消息中心/原生推送投影按事实去重，超时按订单跨重试去重。推送订单目标再次校验归属。丢响应/回调重放不多扣钱包、不多交付设备。

API字段与迁移见[直付合同](../direct-purchase-payment-contract.md)。本轮源码与隔离MySQL自测不代替供应商沙箱、真实资金、TEST发布、App实景或原生推送送达验收。供应商实际有效期、H5内嵌能力及商户时间语义仍需运行态核实；未获证据不编造。

补修（2026-11-01）：活跃业务批次同时包含仍关联PENDING订单的EXPIRED失败意图，不能按付款意图终态把尚未结束的商务截止移入历史配额。只有已结束商务单的纯资金对账使用历史轮转；600条历史记录下失败待付单仍在deadline+宽限的下一次观察正常关单。

官方文档核对（2026-11-01）：[用户提供的HDPAY接口页](https://www.eolink.com/share/inside/7e6a0a7950f9c43ceee62f6085d8400a/doc/630897/detail/769055)已取得。代收查询的实际字段为expirationTime与payTime（支付成功时间），创建成功仅返回URL，未列有效期请求参数。代收日期示例无offset，整页未说明代收时区；不能从代付示例、VN国家或业务时区推断，也不能把示例十分钟差当成商户固定有效期。HTTP层仅将这两个真实字段中自身带Z或明确数值offset的ISO时间转为绝对时刻；缺失/null/非法/非字符串/无offset均保留未知，不用createTime或非官方paidAt别名回填。官方无offset示例仍不能证明截止前付款或更早供应商绝对截止，截止后确认继续人工保护；此解析能力不代表商户已实际返回带offset格式，不开放费用或通道。
