# A3 / E3 跨进程后台事件认领与收益验收

任务完成、收益入账、订单和提现状态由各自业务事务写入。事务提交后，后台投递通用事件和 Webhook 事件。多台后端可以并行处理不同事件。同一条事件由获得数据库会话锁的一个投递者处理，投递前重新核对事件仍待处理且已到期。

投递争用保留原状态和重试次数。若上一投递进程退出、消费者仍在已有的处理期限内，投递延期到该期限之后。达到期限后可重新认领，业务失败沿用原有重试和死信规则。若业务已经提交而投递确认未保存，后续重投使用相同事件 ID，消费者按原消费组唯一键读取结果。消费者认领在一个事务中取得行锁并更新状态，首次和可重试认领各递增一次尝试次数。等待绑定和已有消费终态按原状态机处理。

通用和 Webhook 调度保留各自的扫描范围。查询使用已有的事件类型、名称与状态索引，每个分支只取一批 ID，再合并、去重和排序。旧事件和延期到期事件仍按同一规则进入候选，通用扫描继续核对 C1 审计关联，Webhook 继续支持事件名别名。

任务完成和收益入账在 Webhook 调度中各保留每轮 50 条最新和 50 条最旧的到期额度，两批各按 ID 升序投递。通用调度继续处理最旧到期事件。新版发布前已存在的隔离积压约 88.4 万条，需要同时观察历史消化速率和新增事件的端到端投递时间。

多 JVM 压测同时验证 K4 评分维护。评分用户按缺失、退役或需要重算的状态处理，单用户重算按账号主键定位，保持评分和人工覆盖规则。验收时分别记录事件认领、K4 同步、收益和会话锁等待来源。

隔离业务验收同时核对事件、消费回执、任务回执、收益金额、钱包账本和付款或提现终态。用固定的事件 ID 范围观察待投递数量和最旧账龄变化，另记录新增事件是否追上。重复触发和进程重启后，用业务键检查同一任务和收益只入账一次。

7,200 人混合窗口以真实 App 登录、持续查询和 WebSocket 有效在线为基线，订单和提现由同一批在线用户按样本分流，并核对任务收益结算。支付和出款外部回执使用隔离替身，内部业务状态和账本按正式逻辑执行。后续扩档需同时满足在线人数、混合终态、账本一致性和后台队列消化指标。
