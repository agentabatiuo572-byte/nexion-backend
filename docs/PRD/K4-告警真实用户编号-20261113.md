# K4-BE-02：提现升级告警补真实用户编号（候选 PRD）

基线：`nexion-backend` / `origin/test` = `dd7ff8cdd5dbe4637cb91189096bf3118e757955`（A2/E6 + 历史摘要补正，#523 公共 TEST 候选）。本项只补告警读取的真实 `userNo`，不改提现、告警状态、权限或页面。

## 事实与合同

- `AppWithdrawalService` 只有在 `riskFacts.userNo()` 非空且其它风险事实齐全时才提交提现；`risk.withdraw_escalated` 事件的 payload 明确带 `"user_no": riskFacts.userNo()`（`AppWithdrawalService:518,643-648`）。
- `K4WithdrawalEscalationAlertConsumer` 将完整事件 payload 持久化到 `nx_k4_withdrawal_alert_receipt.payload_json`；读取按当前管理员自己的 receipt 过滤。
- 原 `GET /api/admin/risk/scoring/withdrawal-alerts` 只投影 riskScore/priority/modelVersion/scoreAsOf 等，缺 `userNo`。这是本次可达缺口。
- `user_no` 是事件内可信归属，不是从提现单号切字符串，也不按 userId 猜编码；没有可用归属时保持未知（返回 `null`），不生成 `U0000` 或把未知当合法用户。

## 最小修复

2 个 Java 文件、`+13/-3`：

1. `K4WithdrawalAlertMapper.listAlerts` 在同一 SELECT 增加：
   `NULLIF(JSON_UNQUOTE(JSON_EXTRACT(payload_json,'$.user_no')),'') userNo`
   —— 不新增查询、不逐行查用户、无 N+1/全表扫描。
2. `K4WithdrawalAlertService` 将 `row.userNo()` 放入告警响应；空/旧缺失为 `null`，不伪造。
3. `AlertRow` 增加 userNo 字段；保留旧 9 参数构造器仅用于既有 fixtures/读取兼容，缺失归属为 null。

不改：
- `risk.withdraw_escalated` 发布字段、提现流程、回执写入
- 告警筛选（当前管理员 receipt、`is_deleted=0`、时间倒序、50 条上限）、已读更新
- K4 `risk_k4_user_override`/superadmin 读取权限与数据范围
- PC `K4WithdrawalAlert` 类型和页面展示；点击评分/展示接入由 PC 后续按文档做
- 手机号、姓名等个人信息；不扩大无权用户信息
- 历史数据/事件/审计；不回填旧 receipt

## 公共 TEST 自然样本矩阵（由小6执行）

只读现有测试告警/事件/评分数据；不造提现、不发送真实提现/付款/通知，不改告警状态。

1. **真实编号**：取一条现有升级告警，由有 K4 告警读取权的账号调用 GET；响应该条 `userNo` 与事件 payload 的 `user_no` 一致，并与 K4 评分用户/既有提现归属一致；不按 `withdrawalNo` 或 `userId` 拼造。若没有自然告警样本记未验。
2. **旧缺归属**：旧 receipt 无 `user_no` 时返回 `userNo:null`（或按既有未知字段约定缺省），不出现 `U0000`、空字符串冒充合法编号；其它告警字段、已读、排序不变。
3. **权限/隔离**：无权 K4 告警读取的账号仍被拒绝；有权限账号只看到自己的 receipt，不能借本条看到他人告警或额外手机号/姓名；空列表仍返回空 `alerts`。
4. **筛选/状态**：`is_deleted=0`、当前 recipient、时间倒序和 50 条上限保持；标记已读仍只改当前管理员自己的行，GET 不产生写入。
5. **一致性**：同一条告警重复读、分页/多行排列不受 `userNo` 新增字段影响；没有 N+1 查询或全表扫描；不执行提现或通知。
