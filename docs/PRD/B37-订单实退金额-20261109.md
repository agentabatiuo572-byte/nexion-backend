# B37 订单退款指定实退金额

2026-11-09。依据 `uvel-docs/handoffs/2026-10-28/backend/20-backend-pending-20261031.md` B37。范围仅后端；PC E4 金额输入和少退原因展示、App／H5 Lite 文案仍为前端待办。本次不发布公共 TEST。

## 资金及订单规则

- `DeviceOrderActionRequest.refundAmountUsdt` 为可选 USDT 数值。省略或 `null` 保持原全额退款；旧 A2 指令无该字段时仍按原规则重放。
- 金额必须大于 0、不超过订单 `amount_usdt`，最多六位有效小数。订单实付上限沿用原整单可退本金，不加入银行、网络或其他额外支付费用；不得静默四舍五入为 0 或更大金额。
- 少于原整单金额必须填写原因；原 A2 理由长度政策继续生效，全额退款也保留原有理由要求。
- 覆盖率检查、钱包 `usdt_available` 增额、`cumulative_deposit_usdt` 扣减（最低为 0）、退款账本和账单全部使用实退金额。
- 实退金额持久到 `nx_order.refund_amount_usdt`。订单依旧进入终态 `REFUNDED`，无“部分退款”状态；设备回收、库存归还、未完成任务停止、已完成普通任务收益保留不变。试用转购收益及促销奖励追回继续采用原整单关闭规则，不按少退比例减免追回。

## 执行入口及权限

`POST /api/admin/platform/audit/operations` 创建 `E/e4_order_refund` 待审；另一名合法超管通过 `POST /api/admin/platform/audit/operations/{operationId}/approve` 批准并执行。

新提案的 `command.params` 示例：

```json
{
  "orderNo": "ORD-<服务器订单号>",
  "refundChannel": "WALLET",
  "refundAmountUsdt": 70,
  "refundReasonCode": "OTHER"
}
```

原因在 A2 提案顶层 `reason` 填写；原因码沿用现有枚举，可不传。示例仅表示参数，实际原因码需使用既有可选项。

- A2 `sourceDomain=E4`，`obj` 为订单号，`target={domain:E,type:device_order,id:订单号}`；不接受替换目标或扩展目标。
- 超管或既有合法财务主管且持有 `device_e4_order_refund` 可发起，批准仍需不同超管及原审批权限。客服和增长不增加退款权限。
- 直接 `POST/PATCH /api/admin/devices/orders/{orderNo}/refund` 仍返回 `E4_REFUND_APPROVAL_REQUIRED`；原支付渠道未接 PSP 仍失败关闭，`WALLET` 是可执行渠道。
- 无效金额为 `422 E4_REFUND_AMOUNT_INVALID`；少退缺理由由原 A2 理由门禁或 `E4_REFUND_REASON_REQUIRED` 拒绝。无效提案不得建立待审或改变余额、订单、设备。

## 审批、审计与幂等

- 新 A2 指令由服务器固定 `originalAmountUsdt` 和规范化 `refundAmountUsdt`；客户端原金额不能覆盖权威订单事实。省略金额的新提案也固定当次全额。
- 待审及已执行票据返回 `originalAmountUsdt`、`refundAmountUsdt`，`beforeValue/afterValue` 同时显示原金额与实退金额，`reason` 保留发起理由。老票据没有新增快照时新字段为空，不伪造历史申请金额。
- `E4_ORDER_REFUNDED` 审计保留原 `amount`，新增 `originalAmountUsdt` 与 `refundAmountUsdt`；A2 发起、批准审计的前后摘要同步保存两个金额。`order.refunded` 和 `admin.order_refunded` 事件原 `amount` 字段改为实际到账金额。
- A2 原键绑定原提案全部参数，修改金额返回幂等冲突；E4 执行幂等哈希也绑定指定金额。同额同键重试不再次入账。省略字段时恢复 B37 前的 DTO 字符串哈希，旧收据和旧 A2 重放保持可恢复。

## 读取与相邻事实

- 管理端订单列表／详情、执行返回增加 `refundAmountUsdt`；App 订单详情现有同名字段读取持久实退金额，老单回退到原 `E4-BILL-{orderNo}` 退款账单金额。
- 客服资金事实保留完整原支付证明，核实实退金额、退款账本、订单和退款审计一致，且退款总额不超过原支付金额；旧全退证明仍可核查。
- 促销退款确认按持久实退金额核对账本，整单奖励追回规则保留。促销销售报表按实退金额扣减，按冻结报价的商品金额比例累计分摊至六位小数，分项合计精确等于实退金额。
- E4 订单详情原有 `refundAllowed/projectedCoverageRatio` 是全额退款预览；实际审批执行按本次实退额检查覆盖率。

## 迁移与验收边界

发布前运行幂等前向迁移 `scripts/migrations/20261109_b37_order_refund_amount.sql`。只新增可空列，不改旧迁移、不推断回填历史金额；旧账单和账本继续作为旧退款事实。

候选编译：`mvn -q '-Dmaven.test.skip=true' compile` 已通过，未编写或运行单元／独立集成测试。业务验收由本轮私有完整服务正常 HTTP 流程执行，最终结果见六项后端交付回执；本文不把计划标为已通过。

需要核对的业务终点：

| 场景 | 账本、订单及资产预期 |
|---|---|
| 实付 100，省略或显式 100 | 钱包 +100，累计充值减 100（最低 0），实退 100；终态退款与资产回收 |
| 实付 100，指定 70，有原因 | 钱包 +70，累计充值减 70（最低 0），实退 70；同样终态退款与资产回收 |
| 0、负数、超过 100、超过本金但不超含费支付总额、超过六位有效小数 | 拒绝，无退款账本／账单、余额及状态不变 |
| 同键同额／同键异额 | 同额仅一次；异额冲突且无追加到账 |
| 迁移前无金额旧 A2 | 经不同审批人批准仍整单退，并写真实实退金额 |
| 全退越红线而少退符合 | 全退失败保持待审，少退按实退增负债通过 |
| 客服／增长及直接退款入口 | 原权限拒绝／仍要求 A2，不开放绕过 |
| 促销单少退 | 钱包仅收到实退金额，原整单奖励追回与配额恢复；促销销售净额减实退金额 |

每笔成功退款仅一条 `nx_wallet_ledger`：`biz_type=ORDER_REFUND,biz_no=E4-REFUND-{orderNo}`，以及一条 `nx_wallet_bill`：`type=ORDER_REFUND,bill_no=E4-BILL-{orderNo}`。试用或促销追回可有原规则要求的其他独立账本，不把它们误算为第二次退款。
