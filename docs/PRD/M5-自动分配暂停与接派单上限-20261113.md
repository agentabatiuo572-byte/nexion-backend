# M5-BE-01：自动分配遵守既有暂停与接派单上限（候选 PRD，返修）

基线：`nexion-backend` / `origin/test` = `dd7ff8cdd5dbe4637cb91189096bf3118e757955`；权威文档 `uvel-docs` / `origin/main` = `f07ccbe`。旧候选 JAR `935c82a4…` 已退回历史，不作为交付制品。

## 共享调用范围与返修原因

- `SupportBindingService.freezeRandomScope:445`（主管随机预览/逐人冻结）和 `randomUnbound:316`（提交选人）共用 `randomCandidates → groups.candidates`。
- `SupportBindingRandomService.previewLocked` 逐人冻结；`executeOnce` 逐客户事务提交并用 `frozen.equals(current)` 检查范围。若在共享 `candidates` 上直接过滤 busy/容量，预览后首客户占用 A、次客户重算少 A，会触发原 `SUPPORT_RANDOM_SCOPE_CHANGED`，前客户可能已提交，超出自定义自动范围。
- 因此返修：`groups.candidates` 原样保留给主管预览/确认及已冻票；只有 `supervisor==null && frozen==null` 的自动首次咨询/主管模式超时兜底使用新的自动候选查询。

## 可达自动调用链（仅这两条）

- 首次咨询：`assignOnInquiry` → `retryAutomatic`；`AUTO_RANDOM` 在 `:360-364` 调 `randomUnbound(..., supervisor=null, frozen=null)`。
- 超时兜底：同一方法在等待达到 `fallbackMinutes` 后 `:366-368` 调 `randomUnbound(..., supervisor=null, frozen=null)`。
- 两条都经 `randomCandidates(..., automatic=true)` → `SupportGroupMapper.automaticCandidates` → `leastLoaded` → `insertAssignment`。
- 主管随机预览/确认：`freezeRandomScope` 使用原 `candidates`；`randomUnbound` 传入 `supervisor != null` 或 `frozen != null` 时走原 `candidates`，不应用新过滤。

## 公共 TEST 自然样本矩阵（由小6执行）

不造咨询/工单，不发真实客服消息，不转接或重分配旧客户，不改客服在线/暂停/上限数据；无自然样本记未验。

1. **首次咨询暂停**：真实未分配客户 + 同组 `busy=true` 客服，触发原首次咨询自动分配；暂停客服不入候选/不收到新客户。
2. **首次咨询满额**：`assignedUserCount >= maxConcurrent` 的自然客服与同组未满客服；满额不入结果，未满按原负载分配。无自然满额样本记未验，不手改上限凑样本。
3. **超时兜底**：自然主管模式待分配客户等待到期；兜底同样排除暂停/满额，未暂停未满候选仍按原规则。
4. **主管随机预览/确认**：取两个以上自然候选（A/B），不实际提交；确认预览仍用原 `candidates`，A 的 busy/容量变化不会因新自动过滤导致预览集合被删；原 `frozen` 范围变化仍按原合同 409，不新增恢复/预留框架。不转接旧客户。
5. **空候选/正常**：同组全暂停/满额时保留原等待池及 `NO_CANDIDATE`；未暂停未满客服仍按最低负载/同分随机，不改变在线筛选或轮询。
6. **人工转接/旧客户**：人工转接仍按原暂停/权限筛选，已归属客户不自动改派。
