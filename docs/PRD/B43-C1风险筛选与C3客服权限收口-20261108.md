## 旧状态只读库存

在目标环境先查询，不迁移或伪造历史单：

```sql
SELECT UPPER(status) AS status, COUNT(*) AS rows_count,
       COALESCE(SUM(amount_usd),0) AS amount_usd,
       COALESCE(SUM(ledger_id IS NOT NULL),0) AS posted_rows
FROM nx_wallet_asset_adjustment
WHERE is_deleted=0 AND UPPER(status) IN ('PENDING','PENDING_REVIEW','SUSPENDED')
GROUP BY UPPER(status);

SELECT UPPER(status) AS status, is_deleted, COUNT(*) AS rows_count
FROM nx_wallet_asset_adjustment
GROUP BY UPPER(status), is_deleted
ORDER BY status, is_deleted;
```

`PENDING`、`PENDING_REVIEW` 为旧待复核，`SUSPENDED` 为旧红线挂起；现有后端仍可审批、驳回、由发起人撤回，`historyOnly=true` 会排除这些状态。`ledger_id` 非空只表示已有关联账本，不能假定尚未入账。有效库存为零时该历史处理场景记为不适用，不造历史假单；非零时先核对单号、人员、金额、账本与锁，再与 PC 确认可读可处理方案。本次不擅改旧状态或前端列表。

- 客服客户资料 `identity.data.inviter` 使用 B73-BE-02 四态基础字段，另给 `navigable` 和 `customerId`。原入口先完成客服对象授权；只有 `PRESENT` 且目标在当前客服 `canRead` 范围时 `navigable=true`、`customerId` 为非空字符串，否则为 false/null。范围外或已删除邀请人仍只显示昵称/用户编码，不返回归属客服、分组、队列、手机号、资金、会话或其他导航字段。会话详情默认携带的客户资料复用同一 `identity`，`includeCustomerProfile=false` 时不追加。
- 客服完整档案 `/full-profile` 复用 C1 `/360` 投影，但按客服入口返回 `profile.inviter`：该入口必须始终带 `customerId` 键，可导航/范围内为字符串，否则显式 null；目标可读沿该入口原 `ownership.canRead`，不使用角色捷径。C1 原 `/360` 入口继续不返回 `customerId` 键。
- `statistics.data.invitations` 在现有 `direct`、`descendants` 基础上增加 `withinRewardRange`、`beyondRewardRange`（均为 `{observed, confirmed, status}`）和 `reasons`。四项人数与 B73-BE-01 同一次遍历、同一采样代，`descendants.confirmed` 为 total，只有状态 AVAILABLE 才给 confirmed；首充、金额及其他统计保持原来源状态。
- 客服资料不新增团队成员名单；完整档案沿用原角色团队裁剪。B73-BE-04 的 `/customers/overview` 名单、B73-BE-06 的旧代缓存版本和 B73-BE-07 的 V/L 等级字段不在本项；B74/B76 已合的资金与审计展示保持。
- 不新增权限、迁移、搜索字段、导出或实时推送字段；PC 含 PR0 兼容解析的版本在共享 TEST 实际运行前，B73 后端不进入共享 TEST。

## B73-BE-06 客服采样旧代兼容升级

- 复用 B73-BE-01 的邀请树内部新字段（`withinRewardRange`、`beyondRewardRange`、`inviterReasons`）。`SupportAnalyticsCacheCodec` 先读取外层 `schemaVersion`：新代写/读 `schemaVersion=2`；读到 `schemaVersion=1` 时按旧代结构迁移，不把旧代整体判为 503。
- 旧代迁移保留首充、金额、权限、分页和其他可读事实；所有通过旧结构校验的 v1 邀请行（含历史 `FAILED`）将原因**只保留** `GENERATION_UPGRADING`（不保留旧 `DELETED_NODE`、`SOURCE_READ_FAILED` 等异常），标记 `completeness=UNKNOWN`，邀请人数不再确认，页面按既有「—」处理，不补零；其它非邀请来源失败和 v2 真实 `FAILED` 仍拒绝。内部无深度字段只填满足校验的占位值，UNKNOWN 状态阻止其成为确证人数。
- M1/M3 回包实际读取缓存的 `compiled.customers` 指标；迁移同时把这些客户视图里的邀请人数（含历史 `FAILED` 指标）`status` 降为 `UNKNOWN`、清除 `confirmedValue` 并把原因改为仅 `GENERATION_UPGRADING`，避免旧代已确认人数继续显示；旧代没有的 `withinRewardRange`/`beyondRewardRange` 指标补为 UNKNOWN 空计数，首充、金额和邀请子树入账金额保持。迁移前按旧代严格创建器、类型和枚举预校验（含 completeness、摘要和 Count status 非空），缺字段、未知字段、非法枚举等坏缓存仍返回既有 `SUPPORT_ANALYTICS_CACHE_INVALID`。
- 新一代 `schemaVersion=2` 原样严格读取并接管；真正损坏、未知版本、缺关键结构、未来 asOf 等仍返回既有 `SUPPORT_ANALYTICS_CACHE_INVALID`。
- M1/M3 正常接口沿用原客户授权、分页和采样来源；旧代迁移不改变首充、金额、身份或其他统计，也不触发重新采样。B73-BE-01 依赖单独列出，B73-BE-06 只增加兼容读入和版本切换。

## B73-BE-04 客服统计共用客户行邀请人四态

两个名单入口都新增 `inviter` 四键（`state`、`userNo`、`nickname`、`reason`），与 C1 列表（B73-BE-02）同一套 `UserInviterView` 语义与同一批量读取：
- M1 名单 `/api/admin/content/support-workbench/customers`（`/overview` 为别名）由 `SupportWorkbenchService.snapshot` 的当页 `mapper.customers(q)` 结果一次批量读取；
- `/analytics` 由 `SupportAnalyticsPrivateQueryService.customer` 共用客户行提供，在筛选、排序、分页之后按当前页客户 ID 批量读取。
两处空页都不发查询。

- 每页按当前页客户 ID 一次批量读取直接 `sponsor_user_id`，不递归、不逐行查询；`PRESENT` 给邀请人 `userNo`、`nickname`，`DELETED` 只给 `userNo`，`NONE` 三项为 null，`UNKNOWN` 只给原因码 `DANGLING_SPONSOR`／`ENVIRONMENT_CONFLICT`／`UNKNOWN_ENVIRONMENT`／`SOURCE_READ_FAILED`。
- 方案 A：范围外邀请人同样只给昵称与用户编码，不返回数字 ID、`customerId`、导航标记、归属客服、分组、会话或其他信息；不参与关键词匹配、筛选、排序、分页与条数，也不参与对象授权。
- 邀请人读取失败只把该页各行记为 `SOURCE_READ_FAILED`，不影响人数、首充、金额等其它来源，也不使整页 503（§5「邀请人状态与人数状态互相独立」）。
- 只在 OVERVIEW / CUSTOMERS / ACTIVITY 的客户行出现；FINANCE、DEVICES、AGENTS 视图与原字段不变，导出与实时推送不加该字段。

## B73-BE-07 客服客户资料等级拆分 vRank / userLevel

客服客户资料 `SupportCustomerProfileService` 的通用 `identity.data` 新增 `vRank`、`userLevel` 两个字段，分别取该客户本来的团队等级与用户分层；空字符串归一为 null，缺哪个就为 null。原 `level` 保留，值仍是两者中第一个非空者，旧前端照常读取。

本项只加两个字段，不改等级判定规则、身份读取权限、其它 identity 字段、邀请人与资金投影；会话详情等复用同一 identity 的入口随之拿到这两个字段，但资料邀请人（B73-BE-05）与两档人数、B74 资金入口不在本项。
