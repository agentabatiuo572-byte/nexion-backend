## 1. 背景与原始事实

- 原始待办：`uvel-docs` `origin/main` `handoffs/2026-10-28/backend/20-backend-pending-20261031.md:1582` I1-BE-08。
- `MybatisCopyAbRepository.toExperimentRow` 已调用 `CopyExperimentVariantMapper.listRuntimeMetrics`：
  - 每组的 `COUNT(DISTINCT a.user_id)`（`a.exposed_at IS NOT NULL`）是**去重曝光人数**；
  - 每组的 `COUNT(DISTINCT c.user_id)` 是**去重转化人数**；
  - 当前只用于计算 `cvr`；返回 `CopyExperimentVariantView` 时丢弃，管理端每组没有独立曝光/转化数，实验表只有总曝光/总转化。
- 现有查询没有时间窗口、状态或历史版本过滤：按 `experiment_id` 和组统计，累计至读取时；不是“最近 7 天”，也不是事件次数。
- 组稳定标识：`nx_content_experiment_variant` 的 `experiment_id + variant_name`；`copy_version`、`split_pct`、`sort_order` 在创建实验时写入，之后启动/停止不重写该表。查询以 `variant_name` 关联 assignment/conversion，版本字段固定；当前实现不新增归属规则。
- 总量 `CopyExperimentRow.impressions/conversions` 是同一 runtimeMetrics 列表的求和；组与总量来自同一批指标，不能另拆或补 0 推测。

## 3. 空组/缺组/历史状态

- `listRuntimeMetrics` 以 `nx_content_experiment_variant` 左连接 assignment/conversion，故每个未删除组都有行；无曝光/无转化时 `COUNT(DISTINCT ...)=0`，`cvr=0.00`。
- `metric == null` 的既有 fallback 为 0；本候选不把缺失改成 null，也不新增猜测；正常查询下组行存在。
- SCHEDULED/未启动实验没有 assignment，组计数为 0；RUNNING/CONCLUDED/STOPPED/ADOPTED/DISCARDED 等非删除实验均由 `listExperiments` 读取，指标按实验 id 保留；归档/历史版本不改变已有 assignment/conversion，仍可读。
- 曝光要求 `exposed_at` 非空；仅分配未实际曝光不计入。转化要求同一实验/同一用户的 eligible conversion 行；一个用户多笔转化只按用户计一次，不等于订单数/事件数。

## 2026-11-16 补充：版本历史的时间不再只有月日

`GET /api/admin/content/ab`（`CopyAbOverview.versions`）里的版本行此前只带 `ts`：那是写入时用 `MM-dd HH:mm` 生成的标签（`nx_content_copy_version.ts_label`），跨年后无法分辨年份，也没有任何字段能还原真实时刻。

现按真实持久时刻补足，且不猜历史：

- 版本行新增两个字段 `createdAt` / `updatedAt`，直接取记录自身的 `BaseEntity.createdAt` / `updatedAt`，以 ISO-8601 字符串返回（含年份、秒）；记录没有该值时返回 `null`，不用读取时刻或当前年份补。
- `ts` 保持原样：历史行仍是当年写入的 `MM-dd HH:mm` 文本，后端不解析、不补年份、不回填、不改历史行；它的语义是「写入当时生成的显示标签」，不是权威时间。
- 新写入（草稿保存、发布、实验采用、回滚）改用 `yyyy-MM-dd HH:mm`（`ts_label` 为 `VARCHAR(32)`，无需改表），从此标签本身带年份；这一变化只影响今后写入的行。
- 未改动：版本内容/多语言/翻译、发布与草稿状态机、实验与排序、权限与校验、前端与下发文案、任何表结构或历史数据。

## 2026-11-17 补充：采纳实验优胜前必须先处理未发布草稿

采纳优胜的写入（`MybatisCopyAbRepository.adoptExperimentWinner`）把优胜版本置为 `PUBLISHED`、归档旧发布版本，并且**只有在文案没有 `draftVersion` 时**才把文案本体置为 `PUBLISHED`（`if (!hasText(copy.getDraftVersion())) copy.setStatus("PUBLISHED")`）。于是当文案已被下架（如 `ARCHIVED`）且仍留着一份未发布草稿时，采纳会返回成功、优胜版本与 i18n 也已写入，但文案状态不变 —— 用户侧看不到这次「已采纳」的优胜内容。

按原句「采纳时重新发布，或拒绝并说明先处理草稿」，本轮取**保持现有对外状态的最小拒绝支**：

- `adoptExperimentWinnerOnce` 在真正写入之前先判：文案存在 `draftVersion` 且文案不在**对外公开状态**时 → `409 COPY_ADOPT_DRAFT_PENDING`，不落任何写入。对外公开状态与运行期公开谓词一致（`ContentExperimentRuntimeMapper` 与 `CopyContentMapper` 的 `c.status IN ('PUBLISHED','DRAFT_SAVED')`），在本视图里渲染为 `published` 与 `draft-saved`。
- 因此「已发布内容 + 新草稿」这种仍对外可见的正常并发编辑（库里是 `DRAFT_SAVED`）**不拦**；只有 `ARCHIVED` 等已下架状态 + 草稿会被拒绝。
- 不自动重新发布、不丢弃草稿、不改文案内容与状态；实验分流、运行状态、优胜统计、权限、幂等/哈希/TTL、以及采纳成功后的既有回放与审计顺序均未改。
- 拿到该拒绝后，运营先自行发布或删除草稿，再重新采纳；这一步属既有文案发布流程，不在本项内自动完成。
