# H8 新人礼与邀请奖励参数审批

H8-A01～A05 沿用 `PATCH /api/admin/growth/referral-rewards/params/{key}` 和 `growth_h8_write`。三项基础金额增加、发放模式 `risk_bucket → direct`、奖励停用转启用须提交审批，直接写入返回 `409 A2_CONFIRMATION_REQUIRED`。金额降低、切回 `risk_bucket`、停用按原接口立即保存，不因低覆盖率被阻断。

| 参数 | 基础金额或枚举 |
| --- | --- |
| `newcomer.usdt` | 0～50 USDT |
| `newcomer.nex` | 0～500 UVT |
| `inviter.nex` | 0～249999999.75 UVT |
| `newcomer.lockMode` | `risk_bucket`、`direct` |
| `enabled` | `false`、`true` |

基础金额最多六位有效小数，不进行静默舍入。按 H1 倍率计算的单份有效奖励沿用六位小数四舍五入，且不得超过 `999999999.000000`。字段内部名称 `nex` 保留，用户资产仍为 UVT。

放大通过 `POST /api/admin/platform/audit/operations` 发起，命令为 `H/h8_reward_param_change`，`params.values` 严格只含 `{key,value,expectedVersion}`；`key` 和 `value` 必须是字符串，版本必须是整数。提案来源为 `H8`，对象为 `current`，唯一锁目标为 `H/h8_reward_policy/current`。理由在提案外层填写，操作者及 maker ID 由已登录管理员身份绑定。持原参数写权限的管理员可发起及按原命令号查询本人回执；此能力不授予 A2 队列读取、他人回执或奖励结算权限。

另一位具备 A2 审批权限的有效超管批准或驳回。批准重新校验固定目标、H8 版本、放大方向、拟有效额和可靠的当前 B1。B1 使用原始金额判定生成的 `redlineBreached`，即使页面显示 `100.00%`，实际低于红线仍拒绝。失败保留待审及现有配置，恢复条件后可按原命令重试。

待审期间基础值、整体版本、`effectiveAt`、对外奖励配置和结算快照保持原样。收紧立即推进整体版本；旧版本提案批准时返回 `H8_CONFIG_VERSION_CONFLICT`，不能覆盖后来的收紧。五键继续使用既有 `H8_REWARD` 数据库互斥，不新增预测人数、锁表或全局 H1 锁。

基础金额及预期 H8 版本是审批意图。审批摘要里的 H1 月份、倍率和有效额明确标为“提案参考”；批准按当时 H1 重算合法有效额，领域审计记录实际月份、两类倍率、三个有效额和 A2 单号。H1 独立变更不等于覆盖 H8 基础配置；参数配置不将未知未来注册人数计入当前负债。

实际批准后才按原规则推进配置版本和奖励生效时间。重新启用或修改其他参数会更新 `effectiveAt`，只覆盖此后注册且符合原资格的账号，不补发旧候选。停用保留已存在的生效时间。无码、客服码注册的新人礼包及仅有效邀请人才取得邀请奖励的 B9 合同保持原样。

`direct` 只放宽原风险审核条件，仍执行 K2 硬拦截和 B19 注册渠道的首购冻结。既有冻结礼包仍以原结算金额、原发放模式和原注册冻结标记处理，只有首笔非零实付购买满足现有条件时解冻。已结算及邀请人历史奖励不重定价，不恢复 H4 钱包或持仓触发器。

旧 `h8_referral_settlement`、`h8_referral_settlement_user` 仍使用 `growth_h8_settle`、原 H8／H1 奖励快照及结算目标锁；本次参数审批不替代实际发奖审批。原始精确 B1 判断同样用于既有结算和首购解冻前后检查，钱包与账本在失败时沿原事务回滚。

当前可部署运行态仅支持单一 `dev` 或 `prod`。遗留 `test` 沙箱是内置自动化入口，不是可独立部署的服务；独立启动会被运行态门禁拒绝。本批通过隔离 `dev` 验证正式账号与真实钱包记账，不将其表述为已运行遗留沙箱业务。`dev` 不注册 H8 acceptance 路由，新参数审批也不接受 `runId` 或自报环境字段。
