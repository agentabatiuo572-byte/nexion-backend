# F3 数字边界与精确百分比

2026-11-06。对应 BUG-192、T14 / F-PD10、后端交接 BE-23。只修复 F3 数字配置与消费者，不改页面、其它奖励比例或历史账务。

## 数值合同

| 参数 | 输入单位与范围 | 精度 | 生效存储 |
| --- | --- | --- | --- |
| `F.binary.threshold` | 金额，大于 0、不超过 5000 | 最多 6 位小数 | 十进制金额文本 |
| `F.binary.matchRate` | 百分数，大于 0、不超过 20，可带尾部 `%` | 百分数最多 10 位小数，换算 ratio 最多 12 位小数 | 带 `%` 的十进制文本 |

裸 `1` 与 `1%` 都是 1%，ratio 为 `0.01`；`0.1` 是 0.1%，ratio 为 `0.001`。不根据数值大小猜测单位。百分数以十进制小数点左移两位精确换算，不使用 `HALF_UP` 或截断来接受超精度输入。非数字、空、0、负数、越界和超精度输入拒绝；尾随零同样计入输入小数位数。

`10.0000000001%` 的 ratio 为 `0.100000000001`。放大方向比较也使用这一精度，不能把该值与 `10%` 当作相同值。结算金额仍遵循现有 USDT 六位小数向下取整规则，不改变这项发放规则。

## 入口与生效

- `PATCH /api/admin/teams/commissions/config/{key}` 写入前校验两字段。
- `POST /api/admin/platform/audit/operations` 的 `F/f_ui_config` 提案创建前校验；`POST /api/admin/platform/audit/operations/{id}/approve` 批准时重新校验旧待审命令，非法命令保持待审且配置不生效。
- 两字段的非法值返回业务码 `422`，分别为 `F3_THRESHOLD_INVALID`、`F3_MATCH_RATE_INVALID`；空直接写入保留现有 `TEAM_CONFIG_VALUE_REQUIRED`。
- 新写比例规范成带 `%` 的文本，例如裸 `1` 写为 `1%`，消除存储和回退时的单位歧义。
- 门槛降低、比例提高仍按现有 B1 资金护栏检查；修复缺失或非法旧配置会恢复结算，也按资金放大处理。业务权限、A2 权限和双人审批要求不变。

结算读取、A2 执行时方向比较、App `/api/team/binary` 与公开 `/api/config/commission/guide?schemaVersion=2` 共用 F3 解析。其它 F1/F2/F4 百分比解析保持原样。存量非法配置阻止新结算，手动结算批准返回 `409 F3_THRESHOLD_INVALID` 或 `409 F3_MATCH_RATE_INVALID`，不新增结算、佣金事件或账本；公开规则不展示无效 F3 规则。既有结算回执、佣金事件中的历史 ratio、冷却和账本不重算。

## 转结模式的跨日补结

结算以业务日截止时间为界，读取截止前 A、B 两腿的有效实付额。每腿扣除同一用户所有已提交结算的匹配额，包括先批准的较晚日期。剩余正额再按门槛、当期比例和日封顶结算。相同用户的跨日结算由现有用户行锁串行，已结算日期从原回执读回。月清使用该月窗口，每次对碰清零使用原消费游标。

## 2026-11-17 补充：F3 管理读取的原金额、H1 上限原值与统计范围

F3 管理读取 `GET /api/teams/overview` 与 `GET /api/teams/binary` 原先部分金额由 SQL `ROUND(...,0)` 输出，H1 日上限在总览只给紧凑文本，统计也没有机器可读的窗口/状态依据。现只新增原值字段与只读依据，旧展示字符串、label、说明和既有整数字段保持：

- 汇总原值：`monthlyMatchedUsdRaw`、`dailyMatchUsdRaw`、`maxDailyCapUsdRaw`、`maxTrackGmvRaw`、`residualPoolUsdRaw`；总览对应 `binary...Raw` 字段。汇总无行时 `MAX`/沉淀原值为 `null`，不以 0 冒充未知；总和 0 仍按真实零值。
- 结算行原值：`trackARaw`、`trackBRaw`、`matchAmountRaw`、`todayPaidRaw`；`formula` 同步给出可用的原值。原 `trackA`/`trackB`/`matchAmount`/`todayPaid` 整数字段不变。
- H1 上限：总览新增 `binaryDailyCapRaw`，取既有 H1 `GrowthRhythmSnapshot.binaryDailyCap` 原值；`GET /api/teams/binary` 既有 `dailyCap.h1BinaryDailyCap` 保持原值，`currentLabel` 紧凑文本不变。
- 统计依据：总览 `binaryStatistics` 与 F3 `binary.statistics` 以机器字段说明每项来源、聚合、过滤、时间窗口、状态集合及是否 distinct：
  - `participantCount`：全部未删除结算的 `COUNT(DISTINCT user_id)`，全状态、全历史；
  - `blockedCount`：全部未删除结算中 `BLOCKED/REJECTED/FAILED/FROZEN` 行数，非按用户去重；
  - `monthlyMatchedUsd`：`settlement_date >= 当前业务月起始` 的 `matched_volume` 求和（SQL 无上界）；
  - `dailyMatchUsd`：`settlement_date = 当前业务日`；
  - `autoPlacement7dCount`：既有自动分配条件、`assigned_at` 从数据库当前时间前 7 天至当前时间；
  - `maxDailyCapUsd`/`maxTrackGmv`：全部未删除结算的最大值；
  - `residualPoolUsd`：当前 residualPolicy 下既有 captured/consumed 差额，状态与窗口按实际 SQL；
  - `settlements`：全部未删除结算按 `settlement_date DESC, id DESC` 最新 100 条；
  - `h1BinaryDailyCap`：H1 当前业务月/阶段的 `growth.phase.month.<month>.binaryDailyCap` 只读值。
