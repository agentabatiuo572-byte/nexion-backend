# P5 六设备拒绝直推结算短路

## 来源与范围

本批接续一万人、每人六设备的 PROD #39 复测。TEST 候选从 `origin/test` 的 `bce19109` 建立，只修改 `DirectReferralService` 与本 PRD。当前用户批准对应旧 PROD #39；本批编译、独立复核、推送 test 或准备窄 main 候选均不授予 main 合入、推送或发布权限，须由用户针对本批另行批准。

原 `settle` 在 `prepareSettlement` 新插拒绝记录后仍无条件 `resumeSource`。对新插 `direct_device_earning/REJECTED`，后续查询只会读取既有结算，再分别进入 `calculateWaiting` 和 `materializeGroup` 事务并早退，没有计提或资金写入。

## 现场证据与预期节省

主任务 N008 在原私库、应用停止状态完成只读诊断：全部 2,846,357 条结算均为 `direct_device_earning/REJECTED/NO_ELIGIBLE_DIRECT_SPONSOR`，r2 新增的 285,800 条同态。全部拒绝行 `amount_usdt/amount_nex` 为 0，`usdt_event_id/nex_event_id` 为 NULL；风险簇表为 0 行。该证据用于定位本批路径，不改写原 r2 结果或旧 FAIL。

每次命中可省 `resumeSource` 的一次 `existing` 查询、`calculateWaiting` 的普通 group 读取及 `lockGroup FOR UPDATE`、`materializeGroup` 的同样两次读取，共 5 条 SELECT、2 次行锁及生产代理下的 2 个事务。按 r2 新增 285,800 条静态推算为 1,429,000 条 SELECT、571,600 个事务；这是代码路径推算，不是新产物实测提速或容量通过。

## 行为约定

- 仅当 `prepareSettlement` 本次 `insertSettlement` 成功，且 `kind=direct_device_earning`、`status=REJECTED` 时，返回内部命名 sentinel `NEW_REJECTED_EARNING`。`settle` 明确识别该值并转换为原业务返回值 0，跳过本次 `resumeSource`。
- 原来源核验、环境与用户校验、政策快照、拒绝原因、零金额拒绝行及唯一键全部保留。原 prepare 事务提交后才由调用方短路；插入失败继续抛错，不返回 sentinel。consumer 仍真实认领并完成 SUCCESS/created_commissions=0，随后由原 dispatcher 更新 PUBLISHED，不伪造消费或提前发布。
- 已存在结算的返回值 0 不变，继续原恢复路径；新 WAITING_CALCULATION 的返回值 1、正常双资产佣金、settleSeven、全部 direct_purchase 和退款均走原逻辑。尤其已退款 purchase 仍需进入原退款/撤销及资金回执流程，不能按 REJECTED 一并短路。
- 新拒绝 earning 在现有业务入口中不因后续政策启用、sponsor 或钱包恢复而重新计提。若 prepare 已提交后进程中断，重投仍命中既有结算并走原恢复路径；同事件及同来源新 eventId 的 claim、幂等、租约、失败重试和 DEAD 规则不变。
- 保持单 JVM、计算 16／公共 12／Hikari 64 及原调度、事务和锁策略；600 秒任务、资金金额、全量范围、事件 60 秒与目标 1800+60 秒测量约定不变，无页面变更。
