# BE-25 G2 兑换队列失败退还预占

G2 批处理执行兑换时，钱包更新拒绝本次交易的订单终止为 `FAILED`，批次回执在失败项中返回 `WALLET_BALANCE_CONFLICT`。若订单已有成功的来源币预占，则原币原额退还到用户可用余额，并写入一条 `<exchangeNo>-REFUND` 兑换流水。历史无预占单在失败时没有资金变动。

订单终止、余额回退、退款流水和资金凭证在同一个事务内提交。回退不能完成时，批处理事务回滚，待处理订单仍为 `QUEUED`。退款不发放目标币，不扣手续费。重复读取原批次回执或处理下一批不会再次退款。

资金凭证沿用 `CANCEL` 阶段表达预占释放，记录的原单终态仍为 `FAILED`。对账须核对原预占与退款的金额、币种及钱包变动。现有 G2 批次事件和审计记录保留失败统计和结果，事件注册补齐已发送的 `failed_count` 和 `outcome` 字段。

升级时恢复当前生效事件版本中已软删除的这两个标准字段。持既有客服读权限且能读取该客户的操作者，可从客服资金流水按原币读取同一条 `<exchangeNo>-REFUND` 记录。

## 原批次回执核对

G2 批次成功后保留幂等回执和发起管理员的稳定编号。本人具备 G2 批处理权限时，可带原 `Idempotency-Key` 调用 `GET /api/admin/market/exchange/queue/process`，返回原批次统计及各订单结果。查回执不执行兑换或更新队列。

缺少本人归属、历史未绑定归属或暂不可读取的原命令返回 404。历史 POST 的原请求指纹和原成功回执继续可重放；服务端仅向新批次发起人提供该批次回执。页面先查回执，再读当前队列。

## 2026-11-17 G2-BE-02：当前批处理与地域取消合同确认

当前 Java 主代码由具备原 G2 批处理权限的管理员请求 `POST /api/admin/market/exchange/queue/process`，经过既有命令边界调用 `G2ExchangeQueueBatchService.process`。没有实现 G2 午夜自动跑批任务；现有市场午夜 cron 属于 G3 帧推进，不能当作 G2 队列调度。原 GET 仅查本人批次回执，不会跑批。

存在批次内的地域取消：订单执行到 `geoBlocked` 检查且被判为 blocked 时，才按原事务取消该单，并在有来源币预占时按原链释放。此前的熔断、用户、钱包或额度条件可能使订单先跳过；不能宣称地区受限单在策略变更或下个批次一定立即取消。

当前地区策略更新链不扫描兑换队列，也不调用该批处理或立即取消入口；G2 参数批准仅保存参数。管理端单笔取消、App 本人取消及既有 A2 `g2_exchange_cancel_queue` 单笔回放仍沿各自规则，不能称为审批批处理。

以上按原“确认实际有没有”要求明确现有 Java 合同，没有新增午夜任务、地区变更消费者、取消政策或资金操作，不改变页面或下发说明。结论不代表检查过外部 cron 或实际环境；本条没有 Java 增量，复用既有同生产源码与构建配置的 Java17 跳过测试构建，未执行 E2E、HTTP、数据库或部署验证。
