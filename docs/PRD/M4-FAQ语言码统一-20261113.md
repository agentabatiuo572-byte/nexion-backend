# M4-BE-01：FAQ 检索统一长短语言码（候选 PRD）

基线：`nexion-backend` / `origin/test` = `63a4f669281753e6c5511faa268f935291dbb352`（当前 #522 公共 TEST 候选）。本项只修 Nova 检索边界的长短语言码比较，不改维护 API、存储、App/PC、FAQ 内容或其它语言能力。

## 现行合同

- 维护端 `OpsSupportKnowledgeService` 接受 `zh-CN`、`en-US`、`vi-VN`、`id`、`ms`、`fil`、`ru`、`kk`、`uz`；空语言默认 `zh-CN`，不支持的值返回 `SUPPORT_FAQ_LANGUAGE_UNSUPPORTED`。
- App Nova 请求只接受 `zh`、`en`、`vi`（`AppNovaAiService.validate`）。
- FAQ 存储为维护端长码；读取 SQL 会把历史短码转换为对应长码，未知历史值按 `zh-CN` 映射；维护端不允许未知码。
- `RagNovaAiGateway.publishedDeviceEarningsAnswer` 已把 `zh/en/vi` 映射为 `zh-CN/en-US/vi-VN`，该路径本身可达；本次不改它。
- `RagNovaAiGateway.novaQuestion` 却直接用请求短码与 FAQ 长码 `equalsIgnoreCase` 比较，导致 `surface=Nova` 的已发布 `zh-CN/en-US/vi-VN` FAQ 在 Nova 对话中无法进入知识上下文。这是本次确认的可达错配。

## 最小修复

1 个 Java 文件 `+20/-1`，只改 `RagNovaAiGateway` 的比较边界：

```java
String faqLanguage = canonicalFaqLanguage(normalizedLanguage);
...
.filter(faq -> faqLanguage.isBlank()
    || faqLanguage.equalsIgnoreCase(canonicalFaqLanguage(faq.language())))
```

新增私有 `canonicalFaqLanguage`：

- `zh` / `zh-CN`（大小写等价）→ `zh-CN`
- `en` / `en-US` → `en-US`
- `vi` / `vi-VN` → `vi-VN`
- `id` / `ms` / `fil` / `ru` / `kk` / `uz` 原样精确比较
- 未知/其它标签（如 `en-GB`、`xx`）原样保留，不猜测、不回退英语
- 两侧都规范化，使历史短码/长码等价；不迁移历史行
- 空白语言保持原行为：不按语言过滤

`publishedDeviceEarningsAnswer`、维护端语言校验/默认值、存储格式、SQL、App 请求校验、回答文本、发布/有效性/租户/权限过滤、排序/条数/截断均不改。未新增语种、翻译或迁移历史 FAQ。

## 业务验收矩阵（自然样本，由小6执行）

只使用 TEST 现有已发布 FAQ 和正常 Nova 会话；不新建/发布 FAQ、不发送真实外部 LLM 请求、不改数据。没有样本记未验。

1. 取一条 `surface=Nova`、`status=PUBLISHED`、语言 `zh-CN` 的自然 FAQ，记录 ID/问题；用正常 App Nova `zh` 会话提出与 FAQ 语义匹配的问题，确认回复/引用体现该 FAQ 内容；同一内容用 `en`/`vi` 请求不应误选该中文 FAQ；未发布或 `surface=Help Center` 的 FAQ 不应进入 Nova 上下文。
2. 同一自然样本分别以等价长短码请求（在允许入口内，`zh`/`zh-CN`）得到同一 FAQ 选择；`en`/`en-US`、`vi`/`vi-VN` 同理。若 App 入口只允许短码，长码仅做只读等价性核对，不改客户端发送值。
3. 未知码/不支持码请求按原合同拒绝或原样不匹配，不因本次修复回退英语、猜测新语种或带入其它语言 FAQ。
4. 复用现有已发布 FAQ 的排序、20 条上限、字符截断和 `Nova` surface 过滤；DRAFT/无效 FAQ 不入结果。
5. 测试后不修改 FAQ/内容/语言/发布状态；保留原数据。测试账号、MFA、角色和浏览器由小6按既有受管流程处理。
