## 写入契约

以下接口保留现有路径、业务校验及成功返回结构，新增必需的 `Idempotency-Key`。键去除首尾空白后最长 128 字符；空键拒绝。每个动作与当前认证管理员各自隔离，不能通过传入管理员编号、scope 或目标对象切换归属。

前缀均为 `/api/admin/finance/cregis`：

| POST 路径 | 请求内容及摘要范围 | scope（末尾由服务端追加本人管理员编号） | 恢复 operation |
|---|---|---|---|
| `/addresses/provision?network=BEP20` | 选定网络与原 JSON body；无 body 仍兼容 | `CREGIS_ADDRESS_PROVISION:` | `address-provision` |
| `/addresses/policy` | enabled、target、lowWatermark、batchSize、concurrency、version、reason | `CREGIS_POOL_POLICY:` | `pool-policy` |
| `/reconciliation/run?network=BEP20` | 选定网络与原 JSON body；无 body 仍兼容 | `CREGIS_RECONCILE:` | `reconcile` |
| `/review-cases` | cid、reason、evidenceHash | `CREGIS_REVIEW:PROPOSE:` | `review-propose` |
| `/review-cases/{caseId}/decision` | 路径 caseId 与 expectedVersion、decision、reason | `CREGIS_REVIEW:DECIDE:` | `review-decision` |
| `/exception-ownership/challenges` | sourceType、sourceId、action、targetUserId | `CREGIS_OWNERSHIP_CHALLENGE:` | `ownership-challenge` |

network 缺省仍为 BEP20，并按既有三网解析与业务可用性校验。网络参数与 body 分开绑定，改理由也属于改请求内容。保存地址池和申请签名原文在回放前仍校验当前活动管理员及既有 D1 权限。

- 同管理员、同动作、同键、同内容返回保留的首次完成结果；内容改变返回 `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`，不执行业务。不同管理员使用同一字符串键不会取得或复用他人的回执。
- 补地址的 `QUEUED` 入库与成功回执在同一事务提交，连续或并发重试不另入队。现有库存上限、网络开关、风险总闸、冷却时间及供应商能力校验保留；没有直接调用供应商建址的新入口。
- 补地址因 `CREGIS_PROVISION_GATE_BLOCKED` 拒绝时，可能已写入的风险封闸与拒绝回执一同保留；原键重试继续返回原拒绝，不因后续状态变化再补地址。
- 对账、入金复核保留原先的局部事务边界，避免命令回执事务回滚掉已落地的风险封闸、失败对账或异常记录。原业务完成结果和明确返回的失败均保留；失败原键回放返回原错误。独立业务已可能提交而回执保存失败时，保留 PROCESSING 围栏，后续按既有到期规则转 UNKNOWN；不标为可重试 FAILED，也不写“业务已回滚”的证据。对账运行中的 `RUNNING`、无地址的 `NO_ADDRESSES`、已追平的 `CURRENT` 均为首次业务回执，不代表完整对账成功。
- 复核同一事件的待处理提案限制、case 版本、证据新鲜度、maker 与 checker 不同、原入账校验保持。不同管理员再次决定必须走原业务规则，不能凭他人的键跳过双人复核。
- 签名原文同键回放返回相同 challengeId、message 和 expiresAt，不再插入 challenge，不延长十分钟期限。过期或已消费的原文仍受既有签名、证据和单次消费校验限制；需要新原文时显式发起新的业务命令。

## 本人原命令结果读取

`GET /api/admin/finance/cregis/commands/{operation}?commandKey=原键`

operation 仅允许上表六值。请求必须是活动管理员，并保持原写入口所需权限：补地址、立即对账、复核发起及决定要求 `finance_d1_channel_manage`，地址池配置和签名原文同时要求 `finance_d1_read`；未登录、失权、停用及其他主体不能读取。精确 GET 权限规则允许原来只有管理权限的自定义角色读取其本人管理操作的回执，不能据此读取需要 D1 读权的另外两类结果。服务端固定 operation 到本人 scope，只按本人原键读取已存摘要，再复用现有 `recoveryResult`。不要求 PC 重现 Java 摘要，不接受客户端指定 scope、管理员、requestHash 或任意恢复路径。

正常返回为 `ApiResult`，data 形如：

```json
{"status":"SUCCEEDED","result":{"state":"QUEUED","count":1}}
```

读取结果只投影原接口业务字段：地址入队 state/count、地址池六项配置、对账原 runId/status/窗口/摘要/游标、复核 caseId/status/version、签名原文八项字段。不会返回原请求、内部异常、原摘要、数据库行或其他管理员的结果。

| status | result / error 与动作含义 |
|---|---|
| `SUCCEEDED` | result 为原成功回执；不能把对账 result.status=`RUNNING` 当作完整对账通过 |
| `FAILED` | result=null；已保留的业务失败附 error.code/message；未保留业务错误的底层失败不猜测原因 |
| `PROCESSING`、`UNKNOWN` | result=null，继续保留原命令，不声明可换新键执行 |
| `NOT_FOUND` | 本人该动作下没有可读回执；不等同供应商确认未执行，也不产生新命令 |
| `CONFIRMED_SUCCEEDED`、`CONFIRMED_NOT_EXECUTED` | 沿用原幂等记录经既有核查形成的状态，不重新执行或伪造原结果 |

GET 不 claim、延期、回收、重试、补地址、对账、生成签名或写幂等记录。另一管理员只会查询其本人 scope；本人没有同名命令时为 NOT_FOUND。响应和 POST 回放都不能用 UNKNOWN、FAILED、NOT_FOUND 推断“可以更换新键再执行”。补池配置和签名原文等普通 retained 底层失败恢复仍沿用现有幂等服务规则。
