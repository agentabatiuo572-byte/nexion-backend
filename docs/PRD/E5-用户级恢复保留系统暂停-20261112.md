- 来源：`uvel-docs/handoffs/2026-10-28/backend/BACKEND-REMAINING-CURRENT-20261112.md` E5-BE-10；`uvel-docs/admin-console/inventory/E/E5-设备管理.md` E5-A07/E5-A08。
- 开工基线：`nexion-backend` `origin/test@4e088aac`（含已公共 TEST 验收的 BUG-425）。复核时最新为 `149125b1`；`DeviceOpsMapper`、`OpsDeviceService`、`DeviceOpsRepository`、`MybatisDeviceOpsRepository` 四份设备源码在 `149125b1` 与开工基线完全相同，候选无需倒退或重开，也不与后发改动交叉。
- 范围：只修用户级「恢复该用户设备」的暂停原因边界和 `changedCount`。不改暂停写入、设备状态机、权限、前端、数据库结构。

## 1. 当前事实（基线静态核对）

- `DeviceOpsMapper.resumeDevicesByUser`（`:427–434`）按 `d.user_id` 清除该用户所有未删除、`paused_reason IS NOT NULL` 的运行时行，不看设备状态、归属或原因。
- 恢复候选 `lockE5BatchCandidateIds(pause=0)`（`:389–390`）同样只要求 `r.paused_reason IS NOT NULL`，把退款、解绑等系统暂停也选入。
- `OpsDeviceService.batchE5Devices`（`:3349–3375`）用候选列表大小作为 `changedCount`，因此系统暂停设备既被清原因，又被算入恢复台数。
- `changedCount` 同时写入 outbox（`changed_count`）、领域审计（`changedCount`）和响应；`device_ids` 使用候选列表。
- 第二轮复核补充：`lockE5BatchCandidateIds(..., 200)` 只锁/返回前 200 台，而 `resumeDevicesByUser` 旧实现按 `userId` 更新全部符合行；同一用户运营暂停超过 200 台时，响应 `changedCount` 会是全部影响行，outbox `device_ids` 和 `syncSimulatedPause` 却只有 200 台。仅共用 WHERE 片段不等于同一集合。
- 历史 3 台样本（1 台运营暂停、2 台退款系统暂停）来自旧隔离验证，只作为问题线索，不作为本次验收结果。

## 2. 暂停原因的真实写入来源

`paused_reason` 是 `VARCHAR(64)`。当前代码写入的固定系统值：

| 值（比较时大小写不敏感） | 写入点 | 含义 |
|---|---|---|
| `ORDER_REFUND` | `DeviceCatalogMapper:1717` 退款停止任务；`scripts/migrations/20261106_e4_refunded_device_tasks.sql:17` 同值回填 | 订单退款系统暂停 |
| `USER_DEACTIVATED` | `AppTaskAssignmentMapper:1161`、`CanonicalStateMapper:460`、`DevelopmentHomeSettlementMapper:327` | 用户/设备停用 |
| `PHONE_REPLACED` | `OnboardingCalibrationMapper:307` | 手机换机 |
| `PHONE_OFFLINE`、`PHONE_LOW_BATTERY` | `AppTaskAssignmentService:473–474` 手机心跳 | 手机离线/低电 |
| `unbind`、`deactivate` | `MybatisDeviceOpsRepository:229`（E5 取消激活/解绑） | 解绑/停用 |
| `replace`、`recycle`、`deactivate` | `MybatisDeviceOpsRepository:296`（E3 置换/回收/停用） | 置换/回收/停用 |

其余非空值来自 E5-A07「暂停该用户」的运营理由自由文本（`pauseDevicesByUser` 原样写入）。本候选不新增运营原因白名单，只把上述**已有代码写入的系统值**排除在可恢复范围外。

## 3. 资格合同

用户级恢复只处理同时满足以下条件的运行时行：

1. `nx_user_device d` 未删除，且属于「有效自有设备」：`E5_OCCUPIED_SLOT` —— 状态在 `ONLINE/BUSY/RUNNING/ACTIVE/OFFLINE`，`activated_at` 非空，`deactivated_at` 为空，`ownership_status='OWNED'`。
2. `nx_user_device_runtime r` 未删除，`r.id` 存在。
3. `paused_reason` 非空（`NULLIF(TRIM(...),'')`）。
4. `UPPER(TRIM(paused_reason))` 不在第 2 节的系统值集合中。

只有这些行会被清空 `paused_reason`；候选查询和实际 UPDATE 使用同一段 `RESUMABLE_OPERATIONAL_PAUSE` SQL 片段，并且恢复 UPDATE 限定在已锁定的候选 ID 列表内。

恢复候选 ID 对齐：

- 服务最多锁定/返回 200 个候选 ID；恢复分支把同一列表传给 `resumeDevicesByUser`，UPDATE 增加 `d.id IN (锁定候选ID)`，不会更新列表外的行。
- `syncSimulatedPause`、outbox 的 `device_ids`、领域审计和响应 `changedCount` 都基于这个锁定列表及其实际影响行数；同一用户运营暂停超过 200 台时，第一次最多恢复 200 台，剩余留给下一次调用，不再出现 `changedCount` 大于事件 ID 集合。
- 暂停分支保持原行为，不套用这项对齐；本单不声称暂停与恢复“各一次同集合”。

`changedCount`：

- 恢复：取实际 UPDATE 影响行数（`affectedRows`），只数真正被清除的运营暂停，且不超过锁定候选列表。
- 暂停：保持原 `deviceIds.size()` 口径，不改既有暂停行为（`pauseDevicesByUser` 的 `ON DUPLICATE KEY` 可能返回 2 行计数，不能直接拿影响行数）。
- 恢复分支的 outbox `device_ids`、领域审计 `changedCount` 与响应 `changedCount` 使用同一锁定候选列表/其实际影响行数。

边界结果：

| 情况 | 结果 |
|---|---|
| 同一用户 1 台运营暂停 + 2 台退款系统暂停 | 恢复 1 台；`changedCount=1`；退款两台的 `ORDER_REFUND` 保留；outbox/审计 `device_ids` 只 1 台 |
| 同一用户运营暂停超过 200 台 | 第一次最多锁定/恢复 200 台，`changedCount`、`device_ids`、SIM 同步均为这 200 台；剩余留给下一次调用 |
| 只有系统暂停（退款/解绑/停用/换机/手机离线等） | 候选为空，返回原 `404 PAUSED_USER_DEVICES_NOT_FOUND`；不清任何原因 |
| 运营暂停但设备已 `UNBOUND/DEACTIVATED/RECYCLED/INACTIVE/RETIRED` 或非 `OWNED` | 不恢复（有效归属/状态不满足），原因保留 |
| 运营理由文本恰好等于系统值（如 `unbind`，大小写不敏感） | 按系统暂停保留；这是保守边界，避免误清真实系统暂停 |
| 候选在锁后发生变化 | 原 `409 E5_BATCH_STATE_CHANGED` 保留 |

## 5. 前端接入影响

- PC 的「恢复该用户」按钮和提示当前按 `pausedReason` 非空判断，不能区分运营暂停与系统暂停。后端修复后：
  - 有运营暂停时，`changedCount` 只显示真正恢复的台数，可能小于页面上看到的暂停设备数；
  - 只有系统暂停时，接口返回 `404 PAUSED_USER_DEVICES_NOT_FOUND`，页面会走原错误分支。
- 本候选不改前端源码/文案。PC 后续接入需按「可恢复的运营暂停」口径显示按钮和结果，不要把系统暂停算入恢复台数。

## 6. 公共 TEST 业务验收（未执行，由 TEST 负责）

前置样本必须通过正常业务入口产生，不直接改库、不修改 TEST 账号/MFA：

1. 同一用户至少 3 台设备：A 通过 E5-A07 运营暂停（`paused_reason` 为运营理由）；B 通过退款流程产生 `ORDER_REFUND` 系统暂停；C 通过解绑/取消激活产生 `unbind`（或等价系统暂停）。
2. 调 `POST /api/admin/devices/batch/resume`，理由 8–200 字，带 `Idempotency-Key`。
3. 预期：响应 `200`、`changedCount=1`；A 的 `paused_reason` 清空；B、C 的原因保持原值；outbox `admin.device_resumed` 的 `device_ids` 只含 A、`changed_count=1`；领域审计同口径；A 的模拟槽按原逻辑唤醒，B/C 不被当作运营暂停唤醒。
4. 再次调用同一恢复（无运营暂停）→ `404 PAUSED_USER_DEVICES_NOT_FOUND`，不改变 B/C。
5. E5-A07 暂停该用户仍按原行为写入运营理由并按原 `changedCount` 返回；暂停/恢复幂等键回读保持。
6. 设备级激活仍保留其原行为（例如 `USER_DEACTIVATED` 的恢复路径不受用户级恢复影响）。
7. **>200 台边界**：不造 200 台夹具；以静态证据核对恢复 UPDATE 已限定锁定候选 ID。若公共 TEST 已有超过 200 台运营暂停的用户，再顺带核对 `changedCount`、outbox `device_ids`、SIM 同步只覆盖本次锁定的前 200 台，剩余设备可再次调用恢复；没有该样本则记未验。
8. 若公共 TEST 无法合法产生退款/解绑样本，则该项标记未验；不使用历史隔离结果冒充本次验收。
