- 可用目录只保留既有 USDT 网络及银行卡支付，旧 `card` 不出现在可用目录，也不能重新启用或受理新 admission；即使旧数据库开关仍为 true 也拒绝新单。原 admission 按冻结费用快照幂等回读，原结算/失败/拒付/对账回调照常处理。
- 银行卡通道保留原 `finance.topup.channel.vietqr.enabled` 总开关，名称为「银行卡支付」（Bank card payment / Thanh toán thẻ ngân hàng）；只通过 HDPAY。服务商未配置或关闭时配置返回不可用、创建返回 `HDPAY_CONFIGURATION_INCOMPLETE`，不得回落到 MANUAL 或收款账户池。

## H4 专门安装通道

### 模拟任务交接 22 的客服资金汇总

客服汇总读取授权范围内所选客户的钱包。USDT 和 UVT 分别核对可用余额，零奖励任务本身不增加钱包流水。资金净贡献采用原始凭证和资金归属规则，未知金额保持未知。采样读取失败时保留上一份完整快照及其时间，首次采样尚未成功时返回 503。

隔离库恢复必须包含受管资金例程、原触发器执行者和读取授权。还需保留客服规则主记录 `nx_support_rules.id=1` 的版本、运营阈值与生效时间。已运行的库从备份恢复原行，全新库由 S3 初始化。资金净贡献读取失败与客服规则缺失在服务日志中分别标识，以便核对恢复步骤。

- `20261011_*` 锁定 SQL 与 Java 资金只读基线保持原样。H4 候选生成器读取锁定 schema-reader 基线，唯一函数体变化是钱包触发器清单允许指定 `nx_wallet_h4_holding_observation`（AFTER UPDATE ROW，definer `nexion_app@%`）。其他多余触发器仍使 schema-ready 为 0。
- H4 必须在资金程序首次安装完成后的独立批次安装；缺 reader 时前置拒绝。保留资金首次安装“原钱包仅 1 个触发器”的门禁，不能把 H4 和资金首次安装并为一批。
- 获批 H4 安装先用 root 重建 reader，definer 仍为 `nexion_support_schema@localhost`，恢复并核对原 `SUPPORT_EXECUTE_GRANTS`，再创建 H4 触发器，最终 reader 必须返回 1。钱包原 AFTER UPDATE journal 顺序为 1，H4 必须为 2，原 BEFORE UPDATE 顺序约束不变。
- 函数已重建但 GRANT 失败时，重入该安装步骤仍补回两个授权；DROP/CREATE 中途断连则维持发布 hold，按已核验备份恢复缺失函数后重新走候选，不自动放行或启动旧服务。任意结构/权限漂移仍拒绝。
- H4 固定触发器安装仍需主机 `allow_fixed_h4_trigger_install` 显式开启、固定 SQL 哈希与 MySQL 8.4 前置，不安装到 TEST 业务库。本轮候选生成与隔离库证据不能替代真实业务环境发布/资金只读 API 验收。

### 本地启动链重放（BUG-001，2026-11-04）

- 空库先按既有资金迁移安装 journal 和 reader，再执行 Bash 的 H4 后置迁移。首次完整安装结束时，以及已有 H4 的旧库连续重跑完整启动链后，`nx_support_fund_schema_ready_v1()` 均须返回 `1`，客服授权账号继续读取其负责客户的资金统计。
- Bash 和 Windows 启动入口在原迁移位置执行相同校验。钱包的四个既有触发器继续按基线核验。仅另外接受已审 SQL 中的 H4 持仓触发器，它必须属于 `nx_user_wallet`，是 `AFTER UPDATE FOR EACH ROW`，按序位于 journal 之后。对于历史本地 `root@localhost` 模式，reader 的在线检查也会拒绝错误正文、执行者、触发时机、顺序或额外的钱包触发器。
- 旧库可能保留完整的钱包 journal 和本地 `root@localhost` 安装的 H4，却在还原时遗漏 reader。本地启动链通过 journal 及资金操作表的原始校验，再核对 H4 正文与顺序，按锁定定义补建 reader。已存在的 `nexion_app@%` 获得该函数的 `EXECUTE`。
- 对 `nexion_app@%` 安装的受管 H4，reader 保留受管发布器认可的原正文和 `nexion_support_schema@localhost` 执行者。H4 精确正文和执行顺序由本地安装入口在重放前检查，Bash 在 H4 后置迁移结束时再次核验。受管 reader 缺失且没有本次中断的恢复凭据时停止，按受管流程还原。已有 reader 只接受已审基线、受管 H4 版本或本地兼容版本，并核对程序签名。
- journal 及前置迁移通过、执行到 reader 升级步骤时，启动器在执行用户的私有目录持久保存原执行者、函数级授权和数据库标识，再由 root 写入只携带随机编号的临时恢复标记。DROP、CREATE 或 GRANT 中断后，使用原数据库与原执行用户重跑，按同一凭据恢复。缺失或不匹配的凭据阻断启动。函数、原授权和资金就绪状态通过后清除标记及凭据。reader 开始升级前的失败不保留闲置凭据。
