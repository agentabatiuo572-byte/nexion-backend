# G2/G7 参数放大方向审批（BUG-277）

## 需求与边界

依据 uvel-docs 的 BUG-277 及产品 T02、2026-11-11 T11 补充：放大资金流出的参数改动必须提交 A2，由另一位超管批准后生效；收紧方向保持原直接写入路径。仅实现后端，不改变 PC 页面、文案或恢复交互，不恢复已退役功能。

## 方向与资金检查

| 模块 | 放大方向 | 确定新增应付 Δ（USDT） |
|---|---|---|
| G2 | userDailyCap/platformDailyCap 提高；fee/feeMin 降低；queueMode 从 REJECT 改为 QUEUE | fee/feeMin 按当前真实 QUEUED 单在新旧规则下的净额正差逐单相加；每日上限提高、REJECT→QUEUE 为 0 |
| G7 | apy/nurture 提高；penalty 降低 | 0；年化/提前解锁参数只对新开仓生效；好友倍率不新增发奖 |

G2 使用与队列批次相同的有效当前价格（UVT/USDT，5 分钟新鲜度窗口）及 gross→fee→net 算法、6 位 HALF_UP 舍入：费用率为 0 时费用为 0，否则比例费用与最低费用取大。新规则费用不低于本金的单仍跳过；旧规则跳过、新规则可执行的单以旧可支付净额 0 计入完整新增净额，不得漏计。只纳入现行队列批次采用的有效、非沙箱用户记录，不预测未来兑换量。

提案和批准分别重算 Δ，并用可靠 B1 快照比较 `储备 × 100 >= (应付 + Δ) × 红线百分比`；破线拒绝。G7 查当前覆盖率，不预测未来新单。没有有效价格或可靠资金快照时拒绝，不伪装为 Δ=0。

## 后端契约

- G2/G7 放大方向直写分别返回 409 `G2_EXCHANGE_PARAM_APPROVAL_REQUIRED` / `G7_REPURCHASE_PARAM_APPROVAL_REQUIRED`。G2 先拒绝未经批准的直写，再读价格/队列，避免把审批要求误报为价格不可用。
- 复用 A2 提案入口 `/api/admin/platform/audit/operations/proposals`。命令 `domain="G"`，`op="g2_exchange_param"` 或 `"g7_repurchase_param"`，客户端 params 提供 `{paramKey,value}`。
- `sourceDomain` 分别为 `G2`/`G7`，`obj=paramKey`，单个 `target={domain:"G",type:"exchange_param"|"repurchase_param",id:paramKey}`，不得同时给多目标列表。
- 服务端绑定发起人、当前参数旧值 `expectedValue` 及规范资金类提案摘要；不信任客户端提供的发起人或旧值。工单为 fund、amplifies=1、超管审批门槛。
- 发起人须具备该参数原有精确业务写权限；批准须为另一位超管并具备 `platform_a2_operation_approve`。实际回放写入口仍执行该参数业务权限检查，因此操作账号也须满足原写入权限，不因审批绕过。
- 批准回放核对当前操作 ID、工单单目标锁归属、旧值快照；旧值变化分别返回 409 `G2_EXCHANGE_PARAM_STALE` / `G7_REPURCHASE_PARAM_STALE`。批准后沿原参数写入/审计路径生效，沿 A2 原键查询与幂等恢复机制处理回执。
- G7 当前页面直接写入口同样阻断放大方向；其他非放大参数仍沿原合同。PC 尚未映射新错误码或发起新提案，前端接入及页面验收属于后续任务，不得宣称端到端已闭环。
