# C5-BE-03：全设备退出审批的另一有效超管约束（候选 PRD）

整合说明：本次后端候选在 origin/test `38600e3239ad038858b5acb0dbb426c4dd96f78c` 同时保留H1与C5两处已复核的批准入口约束，不包含K1／K3／E5／H5其它候选。以下原候选基线保留来源意义；公共TEST业务尚未运行。

基线：`nexion-backend` / `origin/test` = `38600e3239ad038858b5acb0dbb426c4dd96f78c`。本项只补 B47 C5-BE-03，不重开 BUG-349 全部范围，不处理 H1-BE-01、C5-BE-01/C5-BE-02、单设备退出、MFA/支付密码或其它 C 操作。

## 规则

C 域 `c2_session_revoke_all`（“退出全部设备”）的 A2 **批准入口**必须由另一位有效超级管理员执行；发起人仍按既有 A2 提案创建和业务权发起。

- 有效超管以现有 `SuperAdminAuthorization` 的数据库事实为准：管理员未删除、`status=1`、`super_admin=1`。
- 批准人还须有 `platform_a2_operation_approve`；这是对既有 A2 权限的叠加，不替代。
- 业务权维持现状：`user_c2_session_revoke_all` **或** `user_c5_session_revoke_all` 任一即可（C5-BE-02 已定，不收窄）。
- 保留 A2 既有非本人、可见范围、待审、对象锁、幂等、回执、回放顺序；不改变驳回、发起人、直接写入或单设备退出合同。
- 不新增配置表、通用操作框架、页面文案、角色授权或其它域操作。

## 现版本缺口

`AuditReplayBusinessPermissionGuard.isUserSessionRevocation`（`:258-261`）只识别 `c2_session_revoke_all`；`validateOrdinaryProposalPermission`（`:681-692`）只要求 `platform_a2_operation_approve` 与 C2/C5 业务权。`A2AccessPolicy.canDecide`（`:113-116`）也只要求 A2 批准权和活跃管理员。`OpsAuditCenterService.decisionQualification` 的非本人、待审和回放前检查没有超管身份判断。因此非超管若被授予 A2 批准及 C2/C5 任一业务权、能看到 C 域，仍可批准该 A2 提案。

## 最小修复

在 `AuditReplayBusinessPermissionGuard.validateDecisionPermission` 的 J1 检查之后、`validateOrdinaryProposalPermission` 之前，对 `isUserSessionRevocation(command)` 增加：

```java
if (!hasAuthority("platform_a2_operation_approve")
        || !superAdmins.isSuperAdmin(SecurityContextHolder.getContext().getAuthentication())) {
    return ApiResult.fail(403, "C5_SESSION_REVOKE_APPROVAL_FORBIDDEN");
}
```

这样：

- 非超管批准在回放前被拒，票保持待审、锁和会话不变；
- C2 或 C5 任一业务权仍由后续 `validateOrdinaryProposalPermission` 接受；
- 非本人检查仍先于本检查，本人批准仍返回 `A2_MAKER_CHECKER_REQUIRED`；
- 驳回路径仍在 `!approving` 早返回，不受影响；
- 直接 `revokeUserSessions` 的 `A2_PROPOSAL_REQUIRED` 和回放路径不变。

不新建类、不复制 H1 候选、不把 H1 或其它冻结候选带入本 worktree。

## 公共 TEST 最少整体业务场景（未来实现后执行）

固定三个不同角色，不能把发起人和尝试批准人混为一人：

- **M（maker）**：非超管，具有 C2 或 C5 任一专权及正常 A2 提案创建权；提交“退出全部设备”提案。
- **N（非超管 checker）**：与 M 不同，具有 `platform_a2_operation_approve` + C2 或 C5 任一专权，并可见 C 域；用于验证 C5 专属超管拒绝。
- **S（有效超管）**：与 M、N 不同，实际 `SUPER_ADMIN` 且有 A2 批准权 + C2/C5 任一专权；用于验证合法批准。

若 TEST 没有合法 N，记录“前置缺失”，不授予角色、不伪造超管身份；不能把 S 当 N。C2 和 C5 两把业务权至少验证一项，另一项按现有合法账号补足，不强制新增授权。

1. M 从正常 C5/PC A2 入口提交 `c2_session_revoke_all` 提案；确认票 pending、目标锁存在、用户会话未变化、原命令回执可查。
2. N 批准 M 的同一票：期望 403 `C5_SESSION_REVOKE_APPROVAL_FORBIDDEN`；票仍 pending、锁仍在、会话未变化、审计/事件不增加。因 N≠M，应在 A2 非本人校验之后命中本分支，不得被 `A2_MAKER_CHECKER_REQUIRED` 遮蔽。
3. S 批准 M 的原票：期望 200、目标用户全部设备退出、领域审计/事件各一次；同批准键同体重放返回原回执，不重复退出。
4. 本人批准独立验证：若合法 M 同时具备 A2 批准权，M 在 pending 阶段批准自己的票仍返回 `A2_MAKER_CHECKER_REQUIRED`；没有该合法账号时记录前置缺失，不授权、不宣称通过。
5. 收紧/其它操作回归：单设备退出 `c5_session_revoke_one`、C5 其它操作、MFA/支付密码及直接写入合同不受影响；C2/C5 任一业务权组合保持。
6. 最终以真实 HTTP、数据库和 PC 页面为准；编译/静态审查/本回执不能替代业务验收。
