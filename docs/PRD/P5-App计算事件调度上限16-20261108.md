## 问题与当前范围

目标为单 JVM、16 CPU / 64 GiB、一万 App 接口容量。正式基线为 PROD #36 / main `0af359d92ceb5d743809e5bfe9cc8a88e5d54016`；本批 TEST 候选基线为 `8ecdf8f297090221af4df4375b846c839e550247`。两个目标 Java 文件在这两个基线间无额外差异，其他 TEST 修改不属于本批窄 main 范围。当前实际 compute outbox 为8个调度分区、8线程，Hikari maximumPoolSize 64 / minimumIdle 8。

固定 r5 anchor `23509447` 的同一只读 RR 查询耗时13.98秒，按 canonical type 得旧 PENDING earnings 1,355,436、task 785,193；type/name alias 可能重叠，不相加。瞬时应用 CPU 256.8%、数据库 CPU 524.73%、磁盘约5153 IOPS低于当前12000 IOPS，不能由此单次观测判定最终瓶颈。私有 CLI 批量250→100小试已经生效，全 outbox 发布标记上界短窗约195.7→207.6/s；两窗非等输入比较，也不是精确 compute 唯一事件吞吐，不能承诺本批提速比例。

r5 沿原1800秒 warm 未达到准入条件，所有压力档均未启动。一万容量仍未通过。用户当前容量范围为 App 接口，客服 analytics / leaderboard 新代际不作为 App 压测前置；本批不优化这两个后台，也不补造模拟产品策略历史、修改金额或跳过资格判断。

## 最小实现约定

- `ComputeOutboxDispatchScheduler.LANES_PER_TYPE` 由4改为8；`task.completed`、`earnings.credited` 各8分区，`MAX_WORKERS` 由原计算式得到16，不新增事件类型或调度器。
- 现有 `nexion.outbox.compute-dispatch-workers` 的缺省值由引用 maximum 改为明确8，默认线程并发保持8；原 `max(1,min(configured,maximum))` 继续生效，允许实际配置到16。配置16及实际效果尚待新产物验收，本地代码和编译不改变PROD有效运行配置。

原 `MOD(id DIV 2,laneCount)` 将从4分区变为8分区，每个类型的事件集合仍由全部分区覆盖。默认8线程现在执行16个定时回调，排队、每批扫描分布和处理交错可能变化，不保证每事件、同用户或跨事件类型的全局顺序。原每页40条、升序读取、SQL、delay / initialDelay、消费者、claim、token、TTL、失败与重试规则保持。

事件级 advisory lock、owner 条件和 consumer claim / 幂等继续走原链；分区锁本身不替代事件级锁。原钱包、回执、收益、账本、金额、资格、去重及UNKNOWN判断不变。更多实际并发可能增加Hikari连接等待、数据库锁与CPU竞争；不因上限提高而修改连接池、金融规则或验收门槛。不增加参数、抽象、缓存或测试框架。
