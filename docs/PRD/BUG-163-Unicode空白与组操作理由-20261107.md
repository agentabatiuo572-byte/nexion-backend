# BUG-163：Unicode 空白与组操作理由

2026-11-07。补充现行 I6 三语非空、占位文本禁止及 B16 欢迎语合同；本次不调整管理端页面。

## I6 与共享发布检查

占位词识别先去掉 ECMAScript WhiteSpace + LineTerminator，再按原规则检查连续填充、`test`、`todo` 等占位文本。该集合等价于 Java 默认 ASCII `\s`、Unicode Separator（`\p{Z}`）和 U+FEFF 的并集，包含 NBSP、BOM，不包含 NEL（U+0085）或 U+001C–U+001F。必填正文不能完全由该集合或 Java 空白字符组成，混合输入同样拒绝；原 Java `hasText` 对无正文输入的拒绝继续保留。该非空判断不裁剪正文中的 NEL 或 C0 前缀，也不把它们加入占位词压缩集合。

I6 发布、完整性缺语种与占位文本扫描、完整覆盖率统计使用同一判断；A/B 文案同步发布到 I6、课程发布及额外语种现有质量调用亦使用该共享判断。草稿仍可保存待修正文，发布拒绝不产生新发布版本。占位参数等集、退役品牌、权限、版本、原命令及审计规则沿用原合同。

## M1 组操作理由

用户本轮明确决定：`SupportGroupService` 的组管理命令理由统一为去掉原 Java `trim()` 首尾字符后 8–200 个 Unicode 码点，7 和 201 拒绝，生僻字/补充平面字符各计 1。仅修复该组管理入口，不传播到超时策略或其他未涉及命令。原 `SUPPORT_GROUP_REQUEST_INVALID`、权限与对象范围、版本、幂等键、理由保存及审计继续沿用。

PC 当前组操作理由的最小值按码点，最大值与文本框仍按 UTF-16 的 200 个代码单元限制；含补充平面字符时，页面不能录入后端合同允许的全部 200 码点范围。该页面限制登记为待处理，本次不修改页面、不宣称已统一页面上限。支付规则理由的 C0 控制字符差异同样保留，不能依靠不可见控制字符凑足可见理由。

## 验收终点

通过真实 HTTP 词条草稿/发布、完整性重扫和 App 词条读取，检查 Unicode 分隔占位文本被拒、纯空白缺语种被识别、合法内容仍可发布与消费；覆盖现有 A/B 或课程共享消费者及原参数/品牌门。欢迎语通过 PUT、回读、原键恢复、新注册欢迎消息及旧消息原文保留验证；正文覆盖 500/501 码点、NBSP/BOM、NEL、U+001C 和纯空白。组管理通过真实组命令验证 7/8/200/201 码点、拒绝无写入/无回执、原键与权限。构建与作者自测不替代主智能体独立验收；本次后端部分完成不等于 BUG-163 整单关闭。
