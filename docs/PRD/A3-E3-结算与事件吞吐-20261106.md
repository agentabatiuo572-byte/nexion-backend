# A3 / E3 任务结算与事件吞吐

2026-11-06

## E3 任务与收益

- 后台工作线程按到期时间和设备 ID 取下一条任务。在 MySQL 事务内先锁账号，跳过其他事务持有的账号，再核对设备所有权、运行代次和到期条件。不同账号可以并行，同账号仍按原顺序更新设备和钱包。
- 结算读取数据中心暂停状态时使用共享锁。设备、运行记录和资金更新继续持有原有写锁。暂停操作仍可与正在进行的结算互斥。
- 任务终态、计算回执、按资产生成的收益、钱包入账和对应 Outbox 事件在同一事务提交。事务中断会释放账号锁。失败重试只推迟尚未被其他事务推进的同一到期记录，已退款的设备不会被恢复为待结算。

## A3 事件投递

- `task.completed` 和 `earnings.credited` 各使用 4 条投递通道。每条通道在同一个数据库中最多由一个 JVM 处理，每轮最多 40 条，分别取最多 35 条最新到期记录和 5 条最旧到期记录，各批内按 ID 升序处理。每轮条数和通道数控制投递并发，新增事件优先处理，历史积压持续分配处理名额。磁盘使用量和实际发布速度须在运行中单独观测。
- 每个事件仍使用原有逐事件锁、消费者业务键和失败重试。进程退出后同一数据库的其他 JVM 可以接管。其他事件继续按各自的调度处理。
- 仅供记录的事件仍须满足原有类型名单和 15 分钟宽限期。归档扫描按类型和状态索引取最旧记录，扫满一批后继续处理，少于一批时等 15 秒再扫。C1 审计反查沿用原条件。
- F5 设备收益按事件发生时点读取生效规则。读取可并行，规则发布仍互斥。分佣来源、接收人、钱包与重放去重规则保持原有约束。
- F5 购买来源与购机、激活采用买家先行的行锁顺序。处理事务先按订单号定位来源买家，在同一事务内取得该用户行锁，再按原订单号和同一买家重读并锁定订单，之后推进分佣结算、奖励事件和钱包。首次分佣、恢复、释放及退款追回共用此顺序；无外层事务的恢复预检单独完成来源认领事务，各层计算和发放继续分别提交。等待期间来源不匹配时沿用原来源缺失或退款校验结果。来源买家已停用但未删除时仍可追溯退款，收佣人的有效资格检查保持原规则。恢复入口经现有代理为来源认领开启事务，后续各层处理继续独立提交。策略金额、价格、资金权限及业务重试沿用原规则。

## App 商城目录读取

- `/api/store/catalog` 每次校验用户资格和生产环境，按商品查询顺序生成目录。一次请求读取一份 H1 节律、E1 阶段和代次门禁快照，供各商品的发布计算复用。商品可见性、价格、库存和展示字段取自本次商品记录，交易入口按现有金融规则校验。

## K2 检测与榜单快照

- 定时检测和管理端套利概览触发的整轮权威投影使用 READ COMMITTED 事务。榜单快照的 `INSERT … SELECT` 从已提交的佣金及用户事实读取，不再为源表扫描持有共享行锁，避免与结算、分佣持有的账号写锁相互等待。隔离级别调整限定在这两个 K2 入口，沿用原事务传播方式及资金锁。
- 一轮内的换新、试用、新人礼和榜单投影、五分钟桶快照及对应信号仍在同一事务提交，运行异常时整轮回滚。周起点、佣金金额与状态范围、直接邀请计数、异常阈值和处置权限保持原规则；每条读取语句可见其开始时已提交的事实，跨语句可能读到不同提交时点。

## 验收口径

在 PROD 同机隔离数据库、缓存和支付替身上运行 7,200 人混合档，达标后依次运行 9,500、15,000、20,000 人档，再逐步增加在线人数。K2 修复通过定时检测和管理端概览两条入口验收，核对运行态事务隔离级别、源表锁等待、快照与投影结果及完整结算链路。每档记录登录、前台活跃、WebSocket、查询、订单、提现、任务结算和正式公网探测结果。按任务号和回执号核对账本唯一性及金额，按固定事件 ID 和时间窗比较新增与实际发布，分别记录历史积压、失败和死信。TEST 分支用于代码保留。

## 单 JVM 运行与软件配置

- 按用户当前要求优先保留单 JVM，同一进程通过现有线程池并行处理不同账号。各压测发生器使用不同账号集合，连接同一个候选后端进程。
- 隔离对照使用单个 48 vCPU、72 GiB 容器和 8–28 GiB 堆，Hikari 上限 128，Tomcat 线程上限 400，文件描述符 262,144。WebSocket 连接上限按档位配置，Tomcat 连接上限至少 20,000，并在 WebSocket 上限之上预留 4,096。事件调度间隔为 250 毫秒，正式环境以实际生效配置和验收回执为准。
- 四个发生器入口共用同一 JVM 的具名上游，Nginx 每 worker 缓存最多 256 条空闲 HTTP 上游连接，使用 HTTP/1.1 和对应 WebSocket Upgrade 头。Nginx 基线使用 4 个 worker、每 worker 65,536 个连接槽和 262,144 文件描述符。每条代理 WebSocket 同时占用下游和上游连接槽，后续大档分别核对源端口、连接槽和文件描述符。
- 超过单个上游临时端口池容量的隔离档位，四个发生器入口分别连接同一后端容器的四个内部网卡地址，每个上游每 worker 缓存 64 条空闲 HTTP 连接。后端仍只有一个 JVM，数据库、Redis 和支付替身继续使用原内部网络。附加网络仅连接本任务的后端容器，代理信任名单只增加对应三个网关的精确地址。启用前停止候选并完成账本审计，重新创建候选后核对四组实际 TCP 目的地址、回调、认证及进程数。
- 在同机 m7i.16xlarge 的内存预算内，隔离 MySQL 缓存从 16 GiB 扩到 64 GiB，容器额度从 48 GiB 扩到 96 GiB。保留 512 MiB redo、I/O capacity 1500/3000、`sync_binlog=1` 和 `innodb_flush_log_at_trx_commit=1`，以相同档位重新验收。
- 在线口径分别记录认证会话、WebSocket 就绪和心跳、60 秒内前台查询成功人数。连接保持、查询错误、完整交易、任务收益一致性及事件积压分别给出结果。10 万在线容量须由对应档位的实际结果确认。

## 高在线档位的补充事件时限判据

- 原 ID 水位和末 180 秒吞吐判定完整保留。历史固定队首为空时，补充报告将历史推进记为不适用；存在历史队首时继续要求推进。旧队列清空后不新增人为积压。
- 30,000 人起，在启动前固定完整稳态区间和 60 秒事件发布时限。按数据库整秒时间取 `[ceil(T0), floor(T1))` 的两类事件，分别报告数量、状态和发布延迟 p50、p95、p99、最大值。成熟集合为其中创建时间早于 `floor(T1)-60` 的事件，要求全部已发布、单条延迟不超过 60 秒，且无失败或死信。
- 完整窗口的每分钟切片分别记录新增未发布数量、最旧年龄和死信，要求最旧年龄不超过 60 秒且新增死信为零。最后 60 秒的事件和窗口结束后 60 秒收尾另列，收尾结果不回填原窗口判定。该有限时段结果用于决定后续探索档位，长期容量仍需更长持续验收。
