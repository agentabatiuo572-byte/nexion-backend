# H4 规则开放、创世抽奖与转盘护栏审批

首批对应 BUG-286 的 A62（含护栏 POST）、A67、A70。本文件也记录 A57～A60 转盘奖池和 A50～A52 旧活动的后端审批，沿用现有角色权限和玩法。跨权益换奖（旧活动改币种、转盘奖档改奖型）的放大口径已按 T11-6 定为「按资产分开看」：任何一种可兑现奖励或券的数量增加都算放大，减少的不能抵。

## 方向与原业务行为

| 入口 | 必须先审批 | 保留直接写 |
| --- | --- | --- |
| `PATCH /api/admin/growth/event-rules/{eventCode}` | 从未激活且当前关闭的规则首次 `enabled=true`，本次完整拟规则和 UTC 期限随批准一起生效 | 关闭草稿编辑、已启用同规则保持、关闭。已激活条款/期限冻结，关闭后不可重开 |
| `PATCH /api/admin/growth/genesis-raffle/{id}` | `DRAFT→OPEN` | POST 即使传 true 仍建 DRAFT；DRAFT 编辑、OPEN 零报名退 DRAFT。再开放仍审批；有报名及 PROCESSING/DRAWN 的原锁定不变 |
| `PATCH /api/admin/growth/quest-events/wheel-guards/{key}` | budget 提高、kill 按真实旧值语义从关闭变开启 | budget 降低、kill 关闭、历史真值等价规范化 |
| `POST /api/admin/growth/quest-events/wheel-guards` | 不存在时创建正 budget、开启 kill，堵住同源新建旁路 | 创建关闭 kill。cap 仍由库存派生，写入拒绝 |

放大直写返回 `409 H4_APPROVAL_REQUIRED`，不提前保存规则、开放报名或写 shadow 配置。提案仅创建 A2 单据和对象锁，不改变业务 revision/enabled、q 状态、护栏、抽奖状态、用户票和经济事实。批准复用原事务、校验、审计、`OpsGrowthCommandBoundary` 幂等回执及 `admin.growth_config_changed` 事件。

预算和 kill 仅控制原 USDT 真实奖；UVT comfort、UVT 奖和券仍按原轮盘消费者兑现。`growth.wheel.*` 是既有 shadow 配置，不新增同步到活奖池/护栏的消费者。历史 kill 的 `1/true/on/enabled/open/开` 按真实消费者的真值比较，避免把已经开启误判成关闭。

## 固定 A2 合同

仅支持以下专用 op，`command.domain=H`、`sourceDomain=H4`；`obj` 必须为精确目标 ID，禁止额外 targets。params 的客户输入只有 `values`，maker、原状态、原提案原因由服务端绑定；before/after、资金方向及审核分类也由服务端生成。

| op | target.type / ID | values |
| --- | --- | --- |
| `h4_event_rule_enable` | `h4_event_rule` / 九个原 eventCode 之一 | eventCode、expectedRevision、enabled=true、startsAt、endsAt、完整 rules |
| `h4_genesis_raffle_open` | `h4_genesis_raffle` / draw ID | id、expectedRevision、enabled=true、三语标题、startsAt、drawAt、完整 prizes；可带 titleTranslations。奖项保留原三语和附加语名称、权益及数量等字段 |
| `h4_wheel_guard_create` | `h4_wheel_guard` / budget 或 kill | guardKey、guardLabel、guardValue、note（键存在，可空） |
| `h4_wheel_guard_update` | 同上 | guardKey、value、expectedValue |

规则/抽奖 maker 使用原 `growth_h4_write`，护栏 maker 使用 `growth_h4_wheel_pool_write`。只放行这两类业务权限的精确提案和本人原 idempotency key 恢复，不授予泛 A2、跨域或他人单据读取。批准/驳回须另一名当前有效超管并持 `platform_a2_operation_approve`；本人批准、App、只读或非超管不能执行。

审批绑定规则的 revision、enabled、activated_at、disabled_at、rules/期限及 q 状态/删除；抽奖绑定 revision/status、完整奖快照、期限、开放记录、翻译及报名；护栏绑定真实存在性和旧行。批准重新锁读、比较绑定状态，并重跑原文案、期限、商品、券、正式促销及按商品汇总库存等 readiness。后来草稿编辑、关闭、删除或资源失效，旧票不得覆盖新事实。资金分支在提案和批准两端保留原可靠性约束，使用 B1 精确 `redlineBreached`，实际低一微但显示 100.00% 仍拒绝；未修改全局 coverage 方法。

`evt-anniversary-spin` 是唯一历史只读发布专例：首次发布仍须双人审批和完整 CAS，审核分类为 `param / amplifies=false`，摘要明确“发布历史活动只读记录”；保留过去 UTC 期限及原 coverage 豁免，不开放抽奖或新奖励。

## 完整审核与部署前置

合法 20 奖、每奖三语及六附加语长名称会使完整旧/拟快照超过 TEXT 65535 bytes。必须先应用新增正向迁移 `scripts/migrations/20261106_h4_approval_command_capacity.sql`，把既有 `nx_audit_operation_ticket.command_json` 从 TEXT 扩至 MEDIUMTEXT；保留旧命令字节、NULL、注释、字符集和排序规则，已是 MEDIUMTEXT/LONGTEXT 时不降级，迁移可重跑。初始化 schema、mapper 建表和启动迁移清单同步，不改历史迁移。

ticket 的短 before/after 列只存有界对象摘要；A2 返回、批准回执及本人原 key 回读从不可变 command 的 `expectedState/values` 投影完整审核内容，不能截断或压缩丢条款。A2 审计保留短摘要、原键、对象、原因、身份和分类，通过原票关联完整命令，避免超出全局审计限长后原 key 被包进 preview。全域审计限长不变。

创世抽奖待审不能报名，不提前扣票、开奖或发奖。批准后仍由原 App enter 扣可用票，原调度固定赢家/原奖快照，再经原币钱包、账本或设备交付；失败保留原结果重试。结构化 reward 文案仅展示，不参与派奖。H4 钱包余额/持仓观察触发器需求已取消，本批不创建、恢复或兼容它们，不运行旧 H4 迁移触发器段。

## 首批本地验收范围

独立候选基线 `415544a5`，新 H4 库实测审批、受限 maker 恢复、拒绝/原键恢复、精确 B1、真实转盘 UVT/USDT/券、新人奖励、签到倍率/预算回基础、赠机及调度抽奖真实兑奖。20 奖完整多语命令实际 92421 UTF8 bytes，完整审核、重复批准及本人回读一致；迁移重跑且 73 条既有命令 SHA/NULL 不变。

消费者逐项及未验前置见本轮 SELFTEST；不能以 enabled=true 代替全部消费者通过。正式促销发布/实付与区域结算、真实旧复投持仓等缺项保留未验；邀请资格使用明确初始账号关系夹具，注册流程遇 CAPTCHA 未验。券经原 grant→报价→建单核销，支付未验。以上未执行公共 TEST 部署、推送或合 main；阶段结果不关闭整个 BUG-286。

## A57～A60 全局转盘奖池

| 原写入口 | 必须先审批 | 保留原写入路径 |
| --- | --- | --- |
| `POST /api/admin/growth/quest-events/wheel-tiers` | 新增可被抽中的 UVT、USDT 或券，含可被选作安慰奖的零概率 UVT | 零概率非安慰奖新增的分类待定，沿用原校验 |
| `PATCH /api/admin/growth/quest-events/wheel-tiers/probabilities` | 任一 UVT、USDT 或券档概率提高，即使另一档下降 | 合计仍为 100 的明确收紧 |
| `PATCH /api/admin/growth/quest-events/wheel-tiers/{tierName}` | 同币种金额提高、可兑现奖概率提高、可兑现奖有限库存增大或改为 0（不限），以及限量后可能改发更高金额的同币种 UVT 安慰奖。任一维度提高即审批；改奖型（含 UVT/USDT/券互换）时旧奖型数量视为 0，新奖励数量大于 0 即审批 | 奖名、金额降低、明确收紧、同券的展示金额改动、改奖型后新奖励数量不高于原同奖型数量 |
| `DELETE /api/admin/growth/quest-events/wheel-tiers/{tierName}` | 删除零概率非真实 UVT 档后，可能兑现的安慰奖金额提高 | 等额、降低或不存在更高可达安慰奖的合法删除。保留原零概率、整池签名和删除后至少两档校验 |

创建仍校验活动档上限和概率和不超过 100。改档及批量改概率仍校验合计恰好 100，概率至多四位小数。批量必须包含全部当前档位。跨权益替换同时提高已明确的概率或库存时，该提高仍触发审批。券的 `rewardAmount` 仅展示，实际由原 H7 依据 `voucherId` 发放一张券并核对发放期和库存。积分退役残留由 BE-13 处理。

UVT 档限量按现有安慰奖选择顺序比较。可直接抽中的低额 UVT 若因新限量缺货，安慰奖可能来自前序或后序。仅作安慰奖的 UVT 限量时，从该档之后判断，还需有另一个可抽中的奖可能触发降级。顺序中首个其他不限量 UVT 会挡住后续档。实际可达的安慰奖金额高于原奖才审批，等额或更低的档仍按原路径直接写。

放大直写返回 `409 H4_APPROVAL_REQUIRED`。奖池专用 op 共用 `H / h4_wheel_pool / ACTIVE_POOL`，`sourceDomain=H4`、`obj=ACTIVE_POOL`。`params` 仅接收 `values`，禁止额外 targets。提案人使用原 `growth_h4_wheel_pool_write`，另一名当前有效超管持 `platform_a2_operation_approve` 才能决定。

| op | `values` |
| --- | --- |
| `h4_wheel_tier_create` | `tierName`、`rewardName`、`expectedSignature`，其余按原 DTO 可传 `probabilityPct`、`rewardKind`、`rewardAmount`、`realOutflow`、`voucherId`、`dailyStock` |
| `h4_wheel_tier_update` | 同上，`tierName` 为原 PATCH 的路径档名。省略字段沿用原继承规则 |
| `h4_wheel_tier_delete` | 原 DELETE 路径的 `tierName` 和 `expectedSignature` |
| `h4_wheel_probabilities_update` | `expectedSignature`、完整 `probabilities` 档名到概率映射 |

A2 金额及概率使用定点十进制字符串或 JSON 整数，以保留精度。`realOutflow`、`dailyStock` 仍用 JSON 整数。提案和批准持原 `H4_WHEEL` 锁，比较原全池 `expectedSignature`，并复核原玩法校验和 B1 估值可靠性、精确红线。原签名和完整有序档位快照由服务端绑定。待审期间改名、收紧、删除等改变全池状态后，旧票批准返回 `409 H4_CONFIG_STALE`。历史抽奖回执继续保留原中奖结果。

App 实际发放转盘真实奖使用 B1 估值可靠性及按原始储备和负债计算的红线结果。估值不可用或精确覆盖率低于红线时，按原降级规则选择有库存的安慰档。精确覆盖率恰好达到红线时，继续检查真实奖开关、日预算和库存。显示的覆盖率按原精度展示。原键恢复保留已完成抽奖的回执。

本人恢复使用 A2 提案的 `Idempotency-Key`。批准使用独立的批准键，同一批准键重试回读原回执。批准键同时用于原 `OpsGrowthCommandBoundary` 的领域写入、领域审计和 `admin.growth_config_changed` 事件，理由使用原提案理由。直写拒绝使用的键单独保留其回执。

A60 待审期间沿用原奖池。批准执行同一删除校验并落库后，后续抽奖读取生效奖池。PC 删除确认框接入本审批命令仍待办。

## A50～A52 旧活动奖励与开放

| 原入口 | 处理方式 |
| --- | --- |
| `POST /api/admin/growth/quest-events/events` | 在规则服务可用时仍直接创建 upcoming 活动和关闭的规则草稿。继续执行原字段校验 |
| `PATCH /api/admin/growth/quest-events/events/{id}/reward` | 正式固定玩法存在规则行时沿用原说明编辑逻辑和权限，转盘奖励仍由奖池管理。自定义关闭草稿沿用原奖励字段校验。有实际开放状态和有效可领奖窗口的无规则旧活动，同币种正额提高或从无正额资金义务变为正额 UVT／USDT 须审批。明确降额和落盘等额仍可直接写 |
| `PATCH /api/admin/growth/quest-events/events/{id}/status` | 无规则行的旧活动从 upcoming 转 ongoing 后会开放正额 UVT／USDT 报名时须审批。沿用原状态、J1 及三语发布校验，英文可按原规则回退。关闭沿用原路径。有规则行的活动仍由 A67 的规则启用状态决定是否可报名 |

用数据库真实 `reward_type/reward_amount` 判断旧资金义务。原 PATCH、提案快照及批准回放共用奖励文本规范化和金额解析，按 `DECIMAL(18,6)` 实际落盘值比较。旧玩法需满足 App 支持的活动类型、正目标和有效时间窗口。草稿维护、过期和无可领奖目标的活动沿用原直接路径及其原校验。已存在正额的纯跨币种替换按 T11-6 处理：奖励按资产分开看，改币种时旧资产数量视为 0，新资产正额即须审批，原资产数量更大也不能抵。

跨权益换奖（A50～A52 旧活动改币种、A57～A60 转盘奖档改奖型）统一口径：各种奖励分开看，任何一种可兑现奖励或券的数量增加都算放大、走审批，减少的不能抵；不给券估价，券只比数量；转盘保留整池顺序、库存和递补（`increasesUvtFallback`）的判断；只查当前覆盖率，不计应付 Δ。

两个专用 op 共用 `H / h4_legacy_event / {eventCode}`，`sourceDomain=H4`，`obj` 为实际 eventCode。客户端 params 仅接收 `values`，其中是 `eventCode`、原 PATCH 的 `value` 和 `expectedValue`，禁止额外 targets。提案人持原 `growth_h4_write`，决定人须为另一名当前有效且持 `platform_a2_operation_approve` 的超管。

| op | `value` / `expectedValue` |
| --- | --- |
| `h4_legacy_event_reward_update` | 新奖励文本 / 当前奖励文本 |
| `h4_legacy_event_open` | `ongoing` / `upcoming` |

提案和批准均持 `H4_EVENT` 并复核 B1 可靠性和精确红线。服务端绑定事件行标识、规则归属、删除状态、状态、目标、期限、奖励说明及实际资产金额。发布另绑定该活动的当前翻译，审批回读包含实际拟生效资产和六位小数金额。状态或快照改变后旧票返回 `409 H4_CONFIG_STALE`。原 PATCH 放大直写返回 `409 H4_APPROVAL_REQUIRED`。本人回执用 A2 提案原键。批准和重试用同一批准键，按原业务入口写入一次领域审计及 A4 事件。

待审期间旧活动仍按原状态报名和生成参与快照。批准后只影响之后报名的奖励快照，历史参与的资产和金额保留。App 报名原键重放返回首次回执，活动开放后的新报名使用新键。旧领取沿用原进度和参与快照校验。

实际旧活动报名依赖 A4 `event.joined` 的现有登记。目标库须具备 ACTIVE revision 93、`campaign_id` 属性和 REGISTERED 扩展条目。启动链的登记缺口由 BUG-327 单独跟踪。

## 无结构化规则的旧活动领取

`GET /api/events/{eventCode}/detail` 在旧活动当前开放、处于 UTC 可领奖时窗、参与记录实际进度达标且未领取时，按参与快照投影可领资格。UVT 和 USDT 须为正额，奖章须能按原发放规则获得或已由本人持有。符合时返回 `eligible=true`、`eligibilityReason=READY`。已领、未开始、已结束和实际进度不足返回对应原状态。

详情和原领取入口共用活动、时窗、进度及未领条件。原领取按参加时保存的资产与金额入账，按原键重试读同一领取结果。受管活动和运行环境由原引擎处理。
