# A9-BE-01:开发者申请管理端时间统一存储时基

状态:候选,未提交、未推送、未部署、未业务验收。
日期:2026-11-15
仓库:`nexion-backend`;基线 `origin/test@2aa01c03da143f901af34a26630ffcfbe82df17a`。

## 1. 问题

A9 管理端申请行的时间字段由 `OpsDeveloperAccessService.instant` 把 `LocalDateTime` 直接 `atOffset(UTC)`:

- 存储墙钟 `2026-11-15 09:11:44` 被输出成 `2026-11-15T09:11:44Z`;
- App `AppDeveloperAccessService` 用 `Asia/Shanghai` 解释同一存储值,输出 `2026-11-15T01:11:44Z`;
- 管理端比 App 多 8 小时。

## 2. 时间列与写源

表/迁移:

- `nx_developer_access_request.created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`;
- `updated_at DATETIME ... ON UPDATE CURRENT_TIMESTAMP`;
- `reviewed_at DATETIME NULL`;
- `nx_developer_access_review_idempotency.result_reviewed_at DATETIME NULL`.

生产写源:

- App 申请插入 `created_at=NOW(),updated_at=NOW()`(`AppDeveloperAccessMapper:28`);
- 管理 approve/reject/revoke `reviewed_at=NOW(),updated_at=NOW()`(`OpsDeveloperAccessMapper:104-105`);
- 幂等完成 `result_reviewed_at=#{resultReviewedAt}`(取自 `updated.reviewedAt()`,仍是 DB 写值),`updated_at=NOW()`(`:89`);
- 所有时间均来自数据库 `NOW()`/表默认值,不是应用 `LocalDateTime.now()`。

读源:

- `OpsDeveloperAccessMapper` 的 page/find/findForUpdate 读取三列;
- idempotency `result_reviewed_at` 读取后用于 replay 行;
- `OpsDeveloperAccessService.view` 同时用于列表、审核成功、原 key replay;
- `AppDeveloperAccessMapper` 的 `created_at submittedAt`;App service 已有 `atZone(Asia/Shanghai)`。

## 3. 存储合同

- `BusinessCalendar.STORAGE_ZONE = Asia/Shanghai`(`shared/config/BusinessCalendar.java:27-28`);类注释明确 storage timestamps 保持北京固定 +08,仅业务日历切日/周/月。
- `DateTimeFormatConfig.BUSINESS_ZONE = Asia/Shanghai`(`:16`);LocalDateTime 全局序列化 `yyyy-MM-dd HH:mm:ss`。
- Hikari 默认 `SET time_zone='+08:00'`(`application.yml:37`);prod 不覆盖 Hikari init。
- App 的 `BUSINESS_ZONE = Asia/Shanghai` 已是同一存储解释;管理端应复用它,不是 UTC 或 A3 动态业务时区。
- **未证**:当前部署池实际 `time_zone`、历史 `created_at/reviewed_at` 未在本单采样;root 的新诊断会话 UTC 不能反推应用池。本候选按源码存储合同修复;公共 TEST 需只读自然行对照。A3 改变业务时区只影响展示/业务日,不改变存储 instant。

## 4. 最小实现

`OpsDeveloperAccessService.instant`:

```java
// before
value.atOffset(ZoneOffset.UTC).toInstant().toString();
// after
value.atZone(BusinessCalendar.STORAGE_ZONE).toInstant().toString();
```

- 保留 ISO UTC 格式(Instant.toString,通常 `...Z`);
- `null` 保留 null;
- 前后示例:
  - 存储 `2026-11-15 09:11:44` → 旧 `2026-11-15T09:11:44Z`;新 `2026-11-15T01:11:44Z`;
  - `reviewedAt`/`updatedAt` 同理;
  - pending `reviewedAt=null` 保持 null。
- 只替换管理端 `OpsDeveloperAccessService.instant`;不全局改 developer 其它 API/webhook 时间,不改 App 的 `AppDeveloperAccessService`。
- 不写数据库、不改历史值、DDL、会话、JVM、A3 配置。

## 5. 受影响响应与旧回执

所有使用 `OpsDeveloperAccessService.view` 的响应同时修正:

- 列表 `GET /api/admin/developer/access-requests` 的 `records[].createdAt/updatedAt/reviewedAt`;
- approve/reject/revoke 成功回执(同一 `view(updated)`);
- 原 key replay(`view(completed)`,含 `resultReviewedAt` 对应的 `reviewedAt`);
- 分页/总数/statusCounts、userId/userNo/C1/客服对象范围、状态机、权限、幂等键/hash/TTL 不变。

旧成功 key 仍先按原幂等回执恢复,不因时间转换被拦;回执中的时间会从旧的错误 UTC 解释变为正确 instant。PC 不自行加减,页面文案/链接/权限冻结。App 已正确,不改;App 字段 `submittedAt` 行为保持。
