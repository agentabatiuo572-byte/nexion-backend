# B25 商城目录算力点

`GET /api/store/catalog` 的每个商品增加 `computePoints`，供 App 和 H5 Lite 商品详情显示「每台为团队增加 N 算力点」。该字段表示当前 SKU 每台贡献的算力点，不使用价格推算，不读取订单快照或团队统计。

## 响应字段

| 字段 | 类型 | 规则 |
|---|---|---|
| `products[].computePoints` | JSON 非负整数 | 等于该商品的 `nx_product.compute_points`，包括值为 `0` 的商品；不得返回字符串、小数或 `null`。 |

App 和 H5 Lite 收到正整数时显示算力点说明，值为 `0` 时隐藏。已发布客户端也兼容缺失或 `null` 的旧响应，但其他类型会导致整个目录解析失败。

## 数据来源

| 模式 | 算力点来源 | 目录范围 |
|---|---|---|
| 正式 | `AppTradeinMapper.listPurchasableCatalogTargets` 直接选择 `nx_product.compute_points`。 | 保留现有商品可见性、发布及登录主体规则。 |
| 验收沙箱 | `CommerceAcceptanceSandboxMapper.listSandboxCatalog` 从现有的 `nx_product` 关联行选择 `compute_points`，与该查询中的商品号、名称、价格使用同一来源。 | 保留当前 run 的 `nx_commerce_sandbox_catalog` 范围；库存与已售仍来自沙箱。服务分支要求严格 `test` profile 的 `LOCAL_SANDBOX` 模式；独立应用入口的限制见下文。 |

两条路径共用商品响应投影，以 Java `Long` 输出 JSON 整数。沙箱不新增算力点副本或价格换算。订单快照、团队统计及其他接口的业务规则保持原样。

## 编辑生效

服务每次请求查询目录，没有目录缓存或基于 `revision` 的短路。PC E1 SKU 更新会写入 `nx_product.compute_points` 并递增 `updated_at`，正式目录的 `revision` 为返回商品中最新的 `updated_at`。验收沙箱每次请求先同步本 run 的目录，随后从关联的商品行读取当前算力点。运营修改在下一次目录读取生效，无需重启或清缓存。

## 验收

- 执行 `mvn -B -o -q -DskipTests compile` 与 `mvn -B -o -q -DskipTests test-compile`，主代码与现有测试调用方均能编译；不运行测试。
- 在隔离库 `nexion_p66` 上启动真实后端，按 App 客户端使用 `Content-Type: application/json` 和登录取得的 `Authorization: Bearer …` 请求目录。逐商品比对数据库值，确认 JSON 类型为整数。
- 修改一个 SKU 的 `compute_points` 并按 E1 方式更新 `updated_at`，紧接着重新读取目录，确认新值；恢复原值后再读确认。覆盖 `0` 时仍返回整数、客户端可隐藏该行。
- 在严格 `test` profile 的验收沙箱模式以沙箱用户请求同一接口，逐商品核对值，并确认修改后下一次读取生效。
- 对修改前后的正式和沙箱目录 SQL 执行 `EXPLAIN`，确认新增投影列没有引入新的全表扫描。
