# B25 商城目录算力点

`GET /api/store/catalog` 的每个商品增加 `computePoints`，供 App 和 H5 Lite 商品详情显示「每台为团队增加 N 算力点」。该字段表示当前 SKU 每台贡献的算力点，不使用价格推算，不读取订单快照或团队统计。[B25 交接规则](https://github.com/agentabatiuo572-byte/uvel-docs/blob/67993fc/handoffs/2026-10-28/backend/20-backend-pending-20261031.md#b25-商城目录下发每件商品的算力点用户-2026-11-03)

## 响应字段

| 字段 | 类型 | 规则 |
|---|---|---|
| `products[].computePoints` | JSON 非负整数 | 等于该商品的 `nx_product.compute_points`，包括值为 `0` 的商品；不得返回字符串、小数或 `null`。 |

App 和 H5 Lite 收到正整数时显示算力点说明，值为 `0` 时隐藏。已发布客户端也兼容缺失或 `null` 的旧响应，但其他类型会导致整个目录解析失败。

## 数据来源

| 模式 | 算力点来源 | 目录范围 |
|---|---|---|
| 正式 | `AppTradeinMapper.listPurchasableCatalogTargets` 直接选择 `nx_product.compute_points`。 | 保留现有商品可见性、发布及登录主体规则。 |
| 验收沙箱 | `CommerceAcceptanceSandboxMapper.listSandboxCatalog` 从现有的 `nx_product` 关联行选择 `compute_points`，与该查询中的商品号、名称、价格使用同一来源。 | 保留当前 run 的 `nx_commerce_sandbox_catalog` 范围；库存与已售仍来自沙箱。服务分支要求严格 `test` profile 的 `LOCAL_SANDBOX` 模式。 |

两条路径共用商品响应投影，以 Java `Long` 输出 JSON 整数。沙箱不新增算力点副本或价格换算。订单快照、团队统计及其他接口的业务规则保持原样。

## 编辑生效

服务每次请求查询目录，没有目录缓存或基于 `revision` 的短路。PC E1 SKU 更新会写入 `nx_product.compute_points` 并递增 `updated_at`，正式目录的 `revision` 为返回商品中最新的 `updated_at`。验收沙箱每次请求先同步本 run 的目录，随后从关联的商品行读取当前算力点。运营修改在下一次目录读取生效，无需重启或清缓存。

## 本地旧库迁移

首次为旧库新增商品算力点列时，按商品价格乘以 10 取整，价格为零的商品记为 0。首次新增订单算力点列时，单品订单按数量乘以商品算力点建立快照，组合订单按未删除明细分别计算并求和，没有匹配商品明细的组合订单记为 0。商品列和订单列独立升级，已写入的数值（包括 0）始终保留。补算中断后再次启动只补仍为 `NULL` 的行。

Windows 的 `scripts/apply_startup_schema_migrations.ps1` 和 macOS/Linux 的 `scripts/local/bootstrap_db.sh` 共用 `scripts/local/20261028_compute_points.sql`，包括后者在初始化末尾的补跑。运营将有价格的 SKU 设为 0 后，重跑迁移仍返回 0。此前创建的订单继续使用各自的算力点快照。

## 验收

- 主代码与现有测试调用方均能编译。
- 正式和验收沙箱两种目录模式下，登录用户读取目录时，每个商品的 `computePoints` 均与 `nx_product.compute_points` 一致，且为 JSON 非负整数。
- 在 PC E1 修改 SKU 的算力点后，下一次目录读取立即返回新值，无需重启或清缓存；正式目录的 `revision` 随 `updated_at` 更新。
- 算力点为 `0` 时仍返回整数 `0`，App 和 H5 Lite 隐藏该行；正整数时显示对应的每台算力点说明。
- 对修改前后的正式和沙箱目录 SQL 执行 `EXPLAIN`，新增投影列不引入新的全表扫描。
- 旧库首次升级时核对单品及组合订单的补算结果。将有价格的商品设为 0，再次执行本地迁移，核对商品仍为 0 且历史订单的零值和正值快照均保持不变。
