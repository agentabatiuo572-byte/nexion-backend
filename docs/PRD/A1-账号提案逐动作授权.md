# A1 账号提案逐动作授权

A2 提交 A1 账号提案时，发起人须具备 `platform_a2_proposal_create` 或 `platform_a2_write`，并持有对应的 A1 动作权限。

| 动作 | 回放命令 | A1 动作权限 |
| --- | --- | --- |
| 编辑资料 | `a1_account_update_profile` | `platform_a1_write` |
| 改角色 | `a1_account_change_role` | `platform_a1_account_role_change` |
| 重置两步验证 | `a1_account_reset_2fa` | `platform_a1_account_2fa_reset` |
| 启用或禁用账号 | `a1_account_status_update` | `platform_a1_account_disable` |

提案锁定命令中的目标账号，委托发起的审批摘要取自回放命令。批准人须为另一位具备 `platform_a2_operation_approve` 和对应动作权限的超级管理员。执行时继续校验账号版本、双超管下限及恢复模式限制，执行失败的提案仍待处理。

当前 PC 页面的四类发起入口仍要求 `platform_a2_write` 及对应动作权限。上述授权契约适用于 Java A2 提案接口。

## 2026-11-15 后端直写约束与有效超管人数

- A1-BE-01：编辑资料、改角色、启停账号、重置两步验证及全部会话退出，保留既有治理恢复、动作权限、账号版本、对象锁及人数校验；实际业务写入前必须处于既有 A2 批准回放上下文，否则返回 `409 A2_CONFIRMATION_REQUIRED`。资料未发生变化仍返回当前资料。创建账号、重置密码、单个会话退出、安全基线及 RBAC 不在本次修复范围。
- 既有成功原键仍由 controller 的 actor 绑定幂等回执先于业务动作恢复，不因新增守卫重做操作；无法证明操作者的 legacy 回执仍拒绝恢复。正常 A2 批准继续调用同一组业务方法。
- A1-BE-06：降级、停用或重置两步验证时，仅目标本身满足 `AdminAccountGovernance.effectiveSuper(role, status, tfa)` 才从有效超管人数中减一。未绑定 MFA 的目标原本不计入有效人数，不再误减。最低有效超管仍为两人；恢复模式、未绑定 MFA 的重置拒绝、版本、对象锁和权限不变。
- 本次只改后端；PC 中同类人数计算尚未修改。源码复核与构建不代表新 TEST 账号、MFA、会话及双人批准业务验收完成。

## A1-BE-04：取消头像的原命令与终态（2026-11-16）

运营头像取消在调用原业务服务前，以当前管理员、资产 ID 和 `Idempotency-Key` 绑定持久回执；命令号取自请求头，不由图片 token 或上传记录推造。相同原命令恢复结果，异操作者或资产不混用；原取消服务的 uploader、READY/ATTACHED 和存储清理规则保持。

持有 `platform_a1_read` 的原操作者可通过精确 `cancel-result?commandKey=` 路由纯读该取消的持久状态，不能用图片 404 推断已取消。返回仅为状态，不读取图片或再次取消，不扩大 App 上传/管理员可见范围。本轮代码复核和编译，未 E2E。
