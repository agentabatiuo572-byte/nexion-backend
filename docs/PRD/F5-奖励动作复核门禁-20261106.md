# F5 奖励动作复核门禁

冻结、解冻、提前解锁、结算发放及驳回状态转换须经 A2 审批。持有相应 F5 动作权限的管理员直接调用奖励状态接口时，返回 `409 A2_CONFIRMATION_REQUIRED`；缺少对应动作权限时返回 403。审批回放仍核对当前版本和合法状态，再写入奖励、账本和审计。

现有 F5 动作权限允许发起相应的 F5 提案，并按原键找回本人的工单及当前状态。其他账号的键返回 404。发起者仍须通过准确的动作、对象和锁目标校验；A2 总览、日志和批准权限沿用原规则。

新建 F5 状态处置、冲正、补发及暂停／恢复提案的发起角色由服务端认证身份确定：财务主管、风控主管及超管分别显示对应实际角色，不采用客户端自报角色，也不统一归为风控。新票响应与本人原键回执沿用该创建时角色，供 A2 角色筛选和详情展示；历史票保持原记录，权限、两人审批、资金和审计业务规则不变。

奖励状态使用专用 A2 指令和奖励记录锁。通用团队界面配置指令不能变更奖励状态。此前通过通用指令发起的待审工单可驳回。

审批处置按目标 `CM-{id}` 精确读取未删除奖励的当前状态、版本和所属用户，不受概览最近 100 条记录的范围限制。历史奖励仍按相同的专用对象锁、合法状态机和版本 CAS 校验执行；资金入账、冲正、任务事件和审计规则不变。

异常预警与近期审计动态继续使用全局最近 200 笔奖励样本，异常列表沿用相同的游标范围；样本读取复用不含账本编号关联计算的投影。主列表仍返回完整奖励、结算组、版本和真实账本编号，统计、样本量、状态及权限口径不变。

奖励列表的 `coolingDaysLeft` 始终返回非负整数。暂停等合法处置清空冷却截止后，冻结或终态记录明确返回 0；仍有冷却截止的记录继续按截止日期计算非负剩余天数，不因状态变为终态而清零。此读取修正不改变奖励状态、版本、冷却截止、钱包、账本或审计，也不放宽页面数据校验。

## 2026-11-15 暂停与解冻的真实冷却截止

暂停奖种不再清空冷却截止：批量置 `FROZEN` 时保留原 `unlock_at`，并记录冻结前状态到 `frozen_from_status`。冻结期间倒计时句柄仍是真实截止，列表 `coolingDaysLeft` 按原公式返回剩余天数。

解冻进入冷却（`FROZEN → COOLING`）时，用冻结时刻到原截止的剩余秒数设置新截止，即「解冻时刻 + 冻结时剩余冷却」：服完剩余天数，不重启完整冷却，也不立即 `UNLOCKED`；剩余秒数为负按 0 处理。自动到期仍只扫描 `COOLING`/`PENDING` 且截止非空的记录，到期才 `COOLING → UNLOCKED`，资金、账本与审计规则不变。

历史上已被旧代码清空截止的冻结记录没有可证明的原截止（暂停审计、操作记录、状态字段都不含原截止），不做重建、不用 `created_at` 或当前冷却天数回填、不放款；这类记录的解冻在版本 CAS、账本和成功审计之前直接返回 `409 F5_COOLDOWN_DEADLINE_UNRECOVERABLE`，记录保持 `FROZEN`、资金不变，需人工核查另有依据后再处置。

`direct_purchase`、`direct_device_earning` 的直接推荐分组有独立 `release_at`，不在本条范围内。`network` 已物化分组仍使用事件到期扫描，其实际恢复分支同样先拒绝空截止，有真实截止才按冻结剩余秒数恢复，避免提前返回绕过保护；不以独立分组的期限给历史空截止猜值。其它奖种、A2 权限、对象锁、版本与幂等、回执一律不变。

## 2026-11-16 补充：暂停奖种委托映射与八种业务奖种对齐

A2 暂停/恢复提案的奖种识别此前只认前六种（`network`、`binary`、`peer`、`cultivation`、`leadership`、`genesis`）且上限 6，而 F5 业务与 `normalizeKinds` 早已接受八种（另有 `direct_purchase`、`direct_device_earning`），导致只含新增两种或其组合的合法提案在委托校验被拒。

现委托识别直接复用 `F5CommissionService.KINDS`（该集合仍为不可变 `Set.of`，内容不变，仅由私有改为公开），上限取该集合大小。以下保持不变：非空 List、先转小写再比较、必须已排序且无重复、全部命中允许集合；旧六种的 target 仍为 `F:commission_user_kind:{userId}:{sortedKinds}`，目标/锁/hash/actor/checker/读写权限与批准回放不变。本补充只对齐识别范围，不改实际暂停范围、数据库触发器、恢复流程或资金政策，也不授予全局 A2 写权。

## 2026-11-16 补充：无分组事件解锁读暂停与兑付覆盖率

用户奖励暂停对八类奖种（`network`、`binary`、`peer`、`cultivation`、`leadership`、`genesis`、`direct_purchase`、`direct_device_earning`）的覆盖，此前只在分组奖励与新建事件上生效：分组释放读暂停，新建事件由 `trg_nx_commission_event_suspension` 置 `FROZEN`；**无分组的旧事件**既不在暂停时冻结，也能在冷却到期或人工解锁时直接入钱包。现补齐解锁侧读取：

- 人工解锁（A2 `f_commission_status` 目标 `unlocked`）在无分组分支、写入状态前，按该事件的用户与奖种读暂停行；命中 `SUSPENDED` 返回 `409 COMMISSION_USER_SUSPENDED`，不改状态、不写账本、不记经办，票保持待审。
- 同一分支在同一位置按补发口径读兑付覆盖率：快照不可靠返回 `503 COVERAGE_SNAPSHOT_UNAVAILABLE`，覆盖率低于红线返回 `422 COVERAGE_BELOW_REDLINE`，同样在任何写入之前失败。
- 自动解锁（冷却到期）对无分组事件同样先读暂停，命中则不解锁、保持 `COOLING`，恢复后下一轮自然解锁；不生成新截止时间，不补发、不追回。
- 分组分支的既有暂停检查（`DIRECT_REFERRAL_SPONSOR_FROZEN`）、对象锁、版本 CAS、幂等回执、状态机与账本幂等键不变；`frozen`/`cooling`/`rejected` 等非解锁方向的转换不加这两道检查。
- 只读新增一条按事件查暂停的连接查询；不新增表、锁、字段、迁移、配置或事件，不改金额与历史数据，不改页面与下发文案。

## 2026-11-16 补充：按奖励业务号读取原记录（F5-BE-08）

GET /api/admin/commissions/{commissionId} 沿用 network_f5_read 与原 F5 列表的查询范围、字段及脱敏，接受既有 CM-<正整数> 奖励业务号，返回该条的用户标识、奖励类型、金额、币种及当前状态；不存在返回原 404 COMMISSION_EVENT_NOT_FOUND。列表读取继续不加单号过滤，原写入、审批、冻结和解锁保持。该接口满足原条“按奖励号读单条”的方案，不修改申请单说明或客户端，也不新增敏感用户信息。

## 2026-11-16 补充：F5 汇总金额按原精度返回

`currencySnapshot` 负责把按币种分组的聚合行（`monthlyCommissionSpend`、`coolingBalance`、`withdrawableThisMonth` 以及分组行的 `amounts`）汇总成 `usdt`/`nex` 两个数，此前对每个合计做了 `setScale(2, HALF_UP)`：库里是 `DECIMAL(18,6)`，接口却只回两位，等于在读取处重新量化了金额，`0.000125` 这类值会被舍成 `0`。

现改为直接返回合计的原始精度（累加 `DECIMAL(18,6)` 得到的标度，不再取舍），其余不变：

- 币种分组、`F5_COMMISSION_CURRENCY_UNKNOWN` / `F5_COMMISSION_AGGREGATE_INVALID` 校验、筛选条件与统计口径、`count` 计数全部保持；
- 某币种没有任何行时仍返回真实 `0`（`BigDecimal.ZERO`），不改成 `null`；
- 不改动 F5 结算、发放、冻结/解冻、费率、金额列定义或任何写入路径；跨币种异常与 F5-BE-02 无关，本笔不涉及；
- 需要一并知晓的呈现影响：`monthlyCommissionSpendLabel`、`coolingBalanceLabel`、`withdrawableThisMonthLabel`、分组 `amountLabel` 由同一合计拼出，文本里的金额小数位会随原精度变化；这是数值真相的直接结果，本次不改这些 label 的模板或前端格式化。

## 2026-11-17 补充：逐笔提前解锁与冲正的当前可用资格

F5 奖励列表、单条奖励读取及管理端相关投影为每条奖励增加当前快照下的 `canUnlock`、`unlockBlockedReason`、`canReverse`、`reverseBlockedReason`，分组奖励同时返回 `groupStatus`。四个资格字段只描述读取时点能否提交，不调用解锁/冲正执行方法；提交后仍须按原 A2、版本 CAS、状态机、权限、资金、账本、审计和写前复核执行，读取为可用不代表未来一定成功。

- 分组网络奖励的解锁要求事件当前为冷却态、组状态为 `COOLING`/`FROZEN`/`UNLOCKED`、未记录冲正且 `release_at` 已到期；仍处冷却期返回 `DIRECT_REFERRAL_COOLING_ACTIVE`，组状态或冲正记录不允许返回 `DIRECT_REFERRAL_RELEASE_STATE_CONFLICT`，状态机不允许返回 `INVALID_STATE_TRANSITION`。
- 分组直接推荐奖励的解锁按既有整组释放范围只接受组状态 `COOLING`/`UNLOCKED`；分组冲正统一接受组状态 `COOLING`/`FROZEN`/`UNLOCKED`、未记录冲正，网络奖励另要求事件状态为 `COOLING`/`FROZEN`/`UNLOCKED`/`AVAILABLE`。
- 无分组 legacy 事件的人工解锁按既有 A2 状态机从冷却态发起，冷却期内仍可手工解锁；冲正按原执行范围接受 `PENDING`/`COOLING`/`UNLOCKED`/`AVAILABLE`，旧 `FROZEN` 不可冲正并返回 `COMMISSION_REVERSE_STATE_CONFLICT`。
- 原始事件状态（或分组奖励的组状态）无法取得时，不按展示状态猜测，两操作均返回不可用及 `F5_COMMISSION_STATE_UNAVAILABLE`。
- 可用时原因为 `null`；不可用时只返回上述稳定机器码。原金额、币种、状态、版本、账本、统计、权限、查询范围及全部说明 label 文案不变，不新增表、字段、回填、执行探测或前端页面。

## 2026-11-17 F5-BE-10：分组人工解锁共用兑付覆盖率门

人工状态处置经 `OpsTeamService.updateCommissionEventStatus` 完成原版本、合法状态转换与审批对象校验后，分组分支在目标为 `UNLOCKED` 时、调用 `DirectReferralService.changeStatus` 及其实际钱包释放之前，同样执行既有 `requirePayoutCoverageForUnlock`。不另算阈值或覆盖率：沿原快照，不可取得或不可靠返回 `503 COVERAGE_SNAPSHOT_UNAVAILABLE`；比率或红线缺失、比率低于红线返回 `422 COVERAGE_BELOW_REDLINE`；可靠且比率达到红线可继续走原校验。失败不进入分组钱包、账本、状态或经办写入。

管理端直接调用仍按原权限及 `409 A2_CONFIRMATION_REQUIRED` 拒绝；实际 A2 `f_commission_status` 批准回放进入同一 writer，执行时重新读该覆盖率，既有成功幂等回执在 writer 前恢复。无分组分支原“用户暂停检查后再查覆盖率”的顺序保持；分组原来源、到期、用户暂停、组状态、冲正及资产已入账检查保持。

本补正只覆盖原合法人工 `UNLOCKED` 目标，不对 `FROZEN → COOLING` 解冻或冲正加门，不修改 `DirectReferralService.release/releaseEvent/releaseSelected` 及自动到期释放、结算或钱包算法。原权限、锁、快照、事务、CAS、哈希和历史成功回执保持；不修改页面、下发说明、历史数据或配置。本轮未实际启动、E2E、HTTP、数据库、真实解锁或部署。

## 2026-11-25 BUG-725 第 6 项 好友双币结算的审批互斥

发起 F5 状态处置、冲正或补发提案时，仍提交所选的 `CM-{id}`。后端根据已有的结算关联识别整组处置的好友奖励，并在同一事务中锁定组内两条币种记录。任一币种已有待审锁时，从任一币种发起这些提案均返回 `409 OBJECT_ALREADY_PENDING`。补发批次选中同组两条记录时，同一币种只加一次锁。并发抢锁失败时整笔回滚。原发起人仍可按原请求键读取已创建的工单。

旧工单持有单币种锁时，同组后续提案同样受阻。状态处置批准接受原事件锁或本次新增的整组锁，继续校验原指令的目标、事件版本和状态。批准、驳回和撤回按工单释放全部持有的锁。

操作范围为 `single_event` 的网络奖励、普通未分组奖励继续按单条记录互斥。暂停及恢复按原用户和奖种锁定。补发提案共用好友双币组锁，执行资格仍沿用原来源校验，好友奖励须通过来源核查恢复。审批权限、原键恢复、账本和资金处置沿用现有规则。
