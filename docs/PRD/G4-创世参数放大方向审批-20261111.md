# G4 创世节点参数放大方向审批（A01、A02、A04～A08）

2026-11-11 · BUG-286 · 后端 · 口径依据产品 T11 补充（`uvel-docs/admin-console/decisions.md` T11-4）

## 生效规则

`PATCH /api/admin/market/nex/genesis/params/{paramKey}` 的写入按参数分别判定「放大资金流出」的方向，放大方向必须先取得 A2 双人审批票；收紧方向仍直接写入。A2 复用通用 `G/g4_genesis_param` 命令，不新增专用 op。

| 参数 | 编号 | 必须先审批 | 仍直接写 | 应付 Δ |
| --- | --- | --- | --- | --- |
| `supply` 节点总量 | A01 | 提高 ACTIVE 系列真实总量 | 降低或等额（仍受已售下限、100,000 上限与末档起点校验） | 0，只查当前覆盖率 |
| `price` 系列当前价（分红计价） | A02 | 提高系列当前价 | 降低、等额 | 现存合格同系列持仓逐笔「新日分红 − 旧日分红」求和 |
| `royalty` 内部转售手续费 | A04 | 按生效的整数基点比较，降低 | 提高、等额、亚基点级变化 | 0，只查当前覆盖率 |
| `airdropPct` 释放分配占比 | A05 | 任何改动 | 无（等价改动被 `G4_GENESIS_PARAM_VALUE_INVALID`/无变化拦截） | 0 |
| `emissionCurve` 释放曲线 | A06 | 任何改动 | 无 | 0 |
| `airdropLockDays` OG 倍率锁仓期 | A07 | 任何改动 | 无 | 0 |
| `divBase` 每日收益基数公式 | A08 | 任何改动 | 无 | 0 |
| `showcaseEnabled` App 商城入口 | A09 | 不审批 | 展示开关保持直接写 | 不适用 |
| `dividend` 每日收益比例 | A03 | 见 `G4-分红审批与真实补发.md` | — | 见该文件 |

- 放大直写返回 `409 G4_GENESIS_PARAM_APPROVAL_REQUIRED`，不落库、不写审计、不产生业务事件。
- `royalty` 落库列为 `nx_genesis_series.royalty_bps`（INT），因此方向判定按 `pct × 100` `HALF_UP` 后的整数基点比较；`2.5% → 2.4999%` 这类亚基点改动不算放大。
- A05～A08 按产品口径视为说明性配置：修改走审批、不计应付，本次不为它们新增释放或公式执行功能；分红仍按 S01 固定公式（系列价 × 持有量 × 日比例）。
- 无 ACTIVE 系列的纯目录维护沿用原行为：不查覆盖率，开售那一刻再由独立闸门检查。

## 拟值覆盖率 Δ

不预测未来的量。审批时只把这次改动确定能算出的新增应付 Δ 加进应付款，检查「储备 ÷（应付 + Δ）」不破红线；算不出确定新增的，Δ 取 0，只查当前覆盖率。提案时算一次，批准回放时按当时的数据重算。

- `price` 的 Δ 与 G4-A03 同一算法：对现存合格同系列持仓逐笔计算新日分红减旧日分红，逐笔按 `HALF_UP` 保留六位后求和，负差计 0。
- A01 总量提高、A04 手续费降低、A05～A08 说明性配置的 Δ 均为 0。
- 覆盖率不可靠（`ratioReserveUsd`/`ratioLiabilitiesUsd` 缺失或 `redlinePct` 非正）返回 `503 B1_COVERAGE_UNRELIABLE`；Δ 计入后破线返回 `422 COVERAGE_BELOW_REDLINE`。

## A2 合同

- 复用既有通用命令：`command.domain=G`、`command.op=g4_genesis_param`，`sourceDomain=G4`，`obj` 与 `target.id` 为该参数键，客户端 `params` 只提供 `paramKey`、`value`（A05 airdropPct、A06 emissionCurve、A08 divBase 另提供 `decisionRef`）。发起与批准的业务权限按各参数原有直写权限校验（`finprod_g4_write`、`finprod_g4_price_write`、`finprod_g4_royalty_write`、`finprod_g4_airdrop_pct_write`、`finprod_g4_emission_curve_write`、`finprod_g4_airdrop_lock_days_write`）。
- 服务端专用 `G4ParamApproval` 在提案时绑定：发起人、规范拟值、旧值 `expectedValue`、现行系列 `expectedSeries`（`seriesId:seriesCode`）、可选 `decisionRef`。客户端不能提供旧值或系列。
- 提案预览与批准各按拟改值复核方向、当前旧值和现行系列，并按 T11 重算覆盖率；提案阶段破线或旧值/系列已变化即拒绝，不会把一次批准应用到另一条系列或另一个旧值上。
- 批准回放经 `G4AdminCommandService.updateParam`，保留原幂等键、`G4_GENESIS_PARAM_CHANGED` 领域审计、业务事件和 `decisionRef`；A05、A06、A08 的回放同样要求原直写入口的 `decisionRef`。
- 锁目标统一为 `{domain:"G",type:"genesis_param",id:paramKey}`；同一参数待审时再次提案返回 `409 OBJECT_ALREADY_PENDING`。

## 2026-11-15 补充：divBase 合法空旧值与参数业务权直接提案

- **divBase 合法空旧值（G4-BE-12）**：`GenesisCatalogService` 新建系列时把 `dividend_base_formula` 初始化为空字符串，这是合法旧值。`G4ParamApproval.values()` 只对 `paramKey=divBase` 且服务端绑定的 `expectedValue` 是真正的空 String 时放行；`expectedValue` 键缺失、空白且不是实际 String 的旧值、其它参数键的空白旧值仍返回 `422 G4_PARAM_PROPOSAL_INVALID`；非空旧值仍按既有 `text` 转换参与比较，本次不新增通用输入收紧。预览与回放继续与服务端当前值精确比较，旧值在待审期间变为非空返回 `409 G4_GENESIS_PARAM_STALE`。批准回放的第二层校验改用 G4 专用 `requireExactSnapshot`：`expectedValue` 为 null（无快照直写）保持原路径，非 null（含空串）一律比较；G2/G7 等共用 `requireUnchangedSnapshot` 的行为不变。候选值校验不变（空、超长、含退役词仍 `422 G4_GENESIS_PARAM_VALUE_INVALID`），空串只作为旧值参与快照，不作为候选值。
- **参数业务权直接提案（G4-BE-13）**：`POST /api/admin/platform/audit/operations` 的方法级 `@PreAuthorize` 增加 `@g4ParamApproval.canPropose(#request.command())`。只有该参数精确业务权（上表 `finprod_g4_write`、`finprod_g4_price_write` 等）、没有 `platform_a2_write`/`platform_a2_proposal_create` 的管理员可直接发起该参数的 A2 提案；不授予批准权、查单/列表/导出权，也不放行其它参数或非 G4 的 A2 命令。批准侧仍要求另一位有效超管持有 `platform_a2_operation_approve` 与该参数业务权。同一精确 `POST` 入口的 RBAC 前置白名单（`AdminRbacAuthorizationFilter.requiredAuthority`）同步补入这四种参数业务权码（`finprod_g4_royalty_write`、`finprod_g4_airdrop_pct_write`、`finprod_g4_emission_curve_write`、`finprod_g4_airdrop_lock_days_write`），否则只持这些精确权的合法发起人会在进入方法级校验前被 `403 ADMIN_PERMISSION_DENIED`；白名单只决定能否进入该 POST，具体参数、目标与命令仍由方法级 `canPropose` 与服务层 `validateProposalContext` 校验，查单与 GET 提案读取入口不放宽。
- 提案上下文、服务端绑定旧值与系列、锁目标 `G/genesis_param/paramKey`、幂等键与回执均不变；`sourceDomain=G4`、`obj=paramKey`、单个 `target` 的校验仍在工单与对象锁创建前执行。

## 2026-11-16 补充：四项精确业务权可读取本人原审批单（G4-BE-18）

`GET /api/admin/platform/audit/operations/proposals/by-idempotency-key` 按原请求编号查本人原单，此前只承认 `finprod_g4_dividend_rate_write`/`finprod_g4_write`/`finprod_g4_price_write`，导致只持其它四项精确业务权的发起人提案成功、查单必然 `403`。三层须同时接通，缺任一层都会在归属校验前被拒：

- HTTP 前置 `AdminRbacAuthorizationFilter` 对该 GET 的精确权限名单加入 `finprod_g4_royalty_write`、`finprod_g4_airdrop_pct_write`、`finprod_g4_emission_curve_write`、`finprod_g4_airdrop_lock_days_write`；
- 控制器方法级 `@PreAuthorize` 名单同步加入这四项；
- `A2AccessPolicy.requireProposalReader` 接受这四项（该方法同时被命令追查入口复用，那里仍有 `originReadAuthority` 与原操作者本人的既有校验，不因此放宽他人记录）。

归属仍是服务端 actor + 原键 + ticket maker：`proposalByIdempotencyKey` 先按 `findA2ProposalId(actor,key)` 定位，再要求 ticket maker 等于当前管理员；G4 参数提案的本人读取沿用既有 maker 分支。队列、审批详情、导出、批准、其它域命令与全局 A2 读取均不放宽，也不改提案权限、G4 参数值或资金链。

本节是对上一节「查单与 GET 提案读取入口不放宽」的限定：放开的仅是这四项精确业务权对**本人原单**的按原键读取，队列、审批详情与导出仍维持原样。
