# Payment password backend contract

The payment password gate applies only to `WALLET` in order payment (including both route aliases), trial conversion, trade-in (including `/api/devices/replace`), capacity replacement and capacity keep purchases, including zero-value wallet purchases. A legacy request with no payment method means wallet and cannot bypass this gate. `HDPAY_BANK` and `CREGIS_USDT_BSC` use their external payment chain and must never read or validate a PIN; a PIN lock does not stop them. The existing pricing, wallet, inventory and fulfillment rules remain the purchase services' authority. Creating an unpaid order and claiming a free trial do not authorize payment.

Install `scripts/migrations/20261030_payment_password.sql`, the additive `20261031_payment_password_permissions.sql` and `20261031_l6_payment_password_route.sql` through the canonical startup migration installer before starting this revision. Existing accounts have no credential; no default PIN or password migration is generated. The new tables contain credentials, independent attempts, permanent command receipts, verified phone evidence, single-use recovery challenges, versioned policy, lock/exception history, required audit and administrator command receipts. Times in these tables are UTC epoch milliseconds to avoid database/JVM time-zone ambiguity.

Configure `NEXION_PAYMENT_PASSWORD_PEPPER` with an independently provisioned secret of at least 32 bytes and `NEXION_PAYMENT_PASSWORD_PEPPER_VERSION` (default label `v1`). Keep the secret outside the database and source control. Missing/invalid configuration fails closed with `PAYMENT_PASSWORD_UNAVAILABLE`. PINs use HMAC-SHA256 with this pepper as BCrypt input, then a fresh BCrypt salt and work factor 12; neither PINs nor an unkeyed PIN digest enter business summaries or attempt records. Changing the pepper/version without retaining the original secret deliberately prevents old credentials from authenticating. Restore the matching secret/version or use the already trusted recovery channel to reset; coordinate rotation with the deployment's secret owner. There is no default pepper or automatic fallback.

The database policy starts at 5 errors in 15 minutes with a 15-minute lock. C5 can change it with the dedicated `user_c5_payment_password_policy_write` permission, a version, explicit confirmation, 8–200 character reason and durable idempotency key. New checks use the latest policy; existing lock deadlines remain unchanged. Payment verification and current-PIN changes share the account counter. An attempt identifier binds the account, purpose, business key and credential version. New guesses need new identifiers; a resend reads its original failure and cannot count twice or reuse successful authorization. Attempts commit in a separate physical transaction; purchase rollback cannot erase them. Successful verification, expiry of a lock, and a valid reset clear the active failures.

Public status is `{configured, credentialVersion, lockedUntil, remainingAttempts, serverTime}`. UTC times serialize as ISO-8601. Lock expiry returns `lockedUntil: null`; clients must read status again before re-enabling input. Incorrect PINs are business errors (`code: 422`, `PAYMENT_PASSWORD_INCORRECT`) with status in `data`; only a missing authenticated session uses 401. Locking is 429 `PAYMENT_PASSWORD_LOCKED`; stale versions are 409 `PAYMENT_PASSWORD_VERSION_CONFLICT`. Setup/change/reset successes return `{commandKey,status:'SUCCEEDED',state}`.

Purchase POSTs accept `paymentPassword`, `credentialVersion`, `attemptNo` and retain their original `Idempotency-Key`. The command digest excludes all three authorization fields. The permanent command effect receipt commits in the same transaction as the existing purchase action; a business rejection rolls the action back to a savepoint and freezes `REJECTED`. A runtime failure rolls the transaction back, allowing safe recovery with the same intent, summary and a fresh PIN attempt. A completed command returns the original receipt without PIN. Original successful idempotency receipts can be imported without executing a purchase. Result GETs never execute the action: `{kind,commandKey,status,canResumeSameKey,receipt?,code?,message?}`; `receipt` is the original response data, not an ApiResult envelope. A nonblocking row lock reports `PROCESSING`; an unseen/rolled-back intent reports `NOT_SEEN` with safe same-key recovery, and an unresolved legacy record reports `INDETERMINATE` or `PROCESSING` with recovery disabled.

Account setup/change/reset and their result endpoints follow `/api/app/security/payment-password` and the approved API table. Setup only inserts a credential once. Change and reset require the expected credential version; successful mutations increment it under the same account lock used by purchase authorization. Setup never authorizes a purchase. Required security audit records contain only the account and resulting credential version.

First setup does not require SMS. Successful existing OTP registration, phone binding and login record verified-phone evidence. A credential snapshots the currently verified phone on setup or a valid current-PIN change. An unverified/missing phone, or a newly bound phone after an existing PIN, cannot recover that credential and returns `PAYMENT_PASSWORD_RECOVERY_UNAVAILABLE`. The existing current-login-password plus old/new phone OTP change chain can transfer an existing recovery channel. A recovery challenge binds user, session, phone hash, credential version and reset purpose; it uses the existing OTP TTL/cooldown/day/attempt configuration. Verification creates a five-minute proof, which is consumed atomically with the new credential. A phone change, session change, credential change, expiry or prior consumption invalidates it. No arbitrary replacement phone or support password-clear endpoint is added.

The PC endpoints match `payment-password-contract.ts`, `payment-password-client.ts` and `payment-password-routes.ts`: `/api/admin/users/security/payment-password-policy`, `/api/admin/users/security/payment-password-records`, profile `/security/payment-password` status/summary/attempts and support-scoped `/api/admin/content/support-workbench/customers/{id}/payment-password` summary/records. Lists support user ID, user number, nickname, exact phone, state, business-date range and pagination. Details, attempts, audit history, release and original-command queries share stable record IDs. Support reads and mutations recheck customer ownership; a support account cannot use the global endpoint to cross that scope.

Release requires `user_c5_payment_password_release`, record/user identity, expected record version, original state, explicit confirmation, reason and a durable command key. It atomically clears only the wallet PIN lock/counter and records required audit/receipt. Login unlock permissions do not grant it; login guards, sessions and the PIN itself remain untouched. The migration initially grants the new mutation permissions only to existing super-admin roles. Administrators cannot view, clear, set or reset a user's PIN. Naturally expired and previously released records remain available. Known payment exception records can be closed with `CLEAR_EXCEPTION` without clearing an unrelated PIN lock.

User numbers are derived with the existing user-domain `CONCAT('U',LPAD(id,GREATEST(8,LENGTH(CAST(id AS CHAR))),'0'))` expression; nx_user has no physical user_no column. Record and count filters explicitly correlate the same outer security-record user. See [C5 list repair PRD](PRD/C5-支付密码异常列表用户号-20261031.md).

Targeted isolated verification uses `PaymentPasswordPolicyTest`, `OpsPaymentSecurityServiceTest`, `PaymentPasswordMySqlIntegrationTest`, the affected purchase service/controller tests and `OpsConsoleArchitectureTest`. The MySQL test requires an explicit `PAYMENT_PIN_TEST_DB_*` bundle for loopback port 33348 and database `payment_pin_backend_test` or its isolated suffix, or the exact dedicated C5 schema `purchase_http_it_c5_list_20261031`; nx_user is installed from the actual scripts/schema.sql DDL, with no invented user_no column. It covers real list/count/search/state/date/pagination, persistence, locking, rollback, servlet HTTP DTO behavior, administrator CAS/idempotency and required-audit rollback. Its SMS delivery is an observable test double. Full production-service purchase flows, APP/H5 browser behavior and actual SMS delivery remain separate integration acceptance steps.
