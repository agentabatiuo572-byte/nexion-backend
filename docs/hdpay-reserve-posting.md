# HDPay 到账与 D3 储备一致性

2026-09-16：HDPay 钱包充值结算此前只更新用户钱包、账单、充值订单和通知，未增加 D3 储备，导致测试环境有真实到账和应付余额而 B1 覆盖率为 0%。

## 新到账

`HdPayCallbackSettlementService` 在原有验签、供应商查单、金额/订单/BANKQR 校验之后，同一事务调用既有 `recordTopupReserve`。凭证号使用原充值订单号，储备号沿用 `RSV-TOPUP-` 规则。订单行锁和 CREDITED 状态处理重复回调/查单；唯一凭证冲突或后续步骤失败会回滚钱包、储备及订单变更。没有新增入账接口或放宽 B1 红线。

HDPay 的 INFLIGHT 对账占位行没有 received_vnd，成功后软删除，不参与 VietQR held-reserve 计算；手工 VietQR 入账不受此次修改影响。

## 历史到账修复

`scripts/ops/backfill_hdpay_reserve.py` 是显式执行的 TEST 运维工具，不在应用启动或 CI 发布时自动运行。必须先 `--plan --expected-backend-sha <完整 SHA>`，检查来源及金额，再以同一 SHA 和计划返回的 `--expected-source-sha` 执行 `--apply`。

- 限定运行态 public-test、dev、CD test 版本；持有发布锁，拒绝发布/迁移中的环境。
- 逐笔比对 HDPay CREDITED / 已支付状态、充值意图及唯一用户账单；有未解决争议、已计入的 VietQR 储备或无法映射的手工注资时停止，避免双计数。
- 只增加缺失的储备及 A2 修复审计，保持钱包和提现状态不变；已有一致凭证跳过，冲突凭证拒绝。发现可能自动出款或解除冷却的提现状态时停止。
- 使用单个 MySQL 事务和真实行锁。源数据变化会使摘要失效；失败/断开在提交前回滚。提交响应不明时用原计划重试，唯一凭证及源码摘要保证不会重复补账。
- 变更前快照保存至服务器 `/srv/nexgrid/backups/hdpay-reserve-*`，目录 0700、快照 0600。恢复时先核对当前充值、储备及后续出款；不能用旧快照覆盖钱包，不能因部署回退再次删除真实到账储备。

本次无需改表，也不重放充值通知、修改用户余额、模拟供应商回调或执行提现放行。
