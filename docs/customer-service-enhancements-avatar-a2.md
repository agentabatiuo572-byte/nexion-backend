# A1 avatar through original A2 approval

A maker uploads an avatar, then another administrator approves the original A1 create/update ticket. Approval keeps the checker principal. The server stores the maker's numeric ADMIN ID outside client command params and grants attachment only for that locked pending ticket's complete frozen command, asset and actual account target. Checker SUPER status, A1 write and A2 approve remain required.

Avatar proposals require one exact A/account target. The server derives the displayed object from the command; approval checks the persisted display, source and ticket-owned lock again. Create binds the generated insert ID; update binds its original target only after account-version CAS. Ordinary replay flags, direct dispatcher calls and requested maker fields cannot issue attachment authority. Expiry, cancellation, storage, idempotency, transaction propagation and self-only preview/cancel retain their original checks. Pending avatar tickets from before this change have no trusted maker snapshot and must be withdrawn and proposed again.

Run `scripts/support-avatar-a2-unit-check.ps1 -EvidenceRoot <external-directory>` for the pure A1/A2/attachment suites and compilation of all tests. This runner loads no shared credentials and starts no server. It checks current XML, positive execution counts and zero failures, errors or skips. These tests exercise the original service pipeline with mapper/storage doubles; they do not certify real database rollback or browser behavior.

`SupportAdminAvatarA2RuntimeTest` is an opt-in original HTTP/MySQL/private-storage acceptance harness. It covers different-admin create/update, retries, self/foreign-asset denial, CAS/lifecycle/storage failures, target mismatch and real persisted rollback/read-back. It uses only newly created fixture administrators/assets and cleans those resources. It requires a fresh approved isolated resource lease plus both avatar-A2 and inherited BULK gates; no existing real-resource wrapper may be run merely because this source compiles. The current implementation phase leaves actual HTTP/DB/browser acceptance, full core/bulk reruns and final test-branch integration to the main chat.
