# H7 优惠券发行额度与用户领取状态

2026-10-25，缺陷 #645（读取可领状态）与 #648（并发实际超发）。适用正式 App/H5 优惠券状态查询及所有共用 H7 发券入口，保持原发行额度与券核销合同。

- `issuanceLimit=0` 表示无限发行；正数表示该券全局累计发行上限。已发行数量与正式发券命令一致，计算同一 `voucher_id` 的所有 `is_deleted=0` grant，不按用户或 AVAILABLE 状态缩小范围。核销、过期、撤销都不自动恢复发行名额。
- 未领取用户只有在人群、券定义开放状态和剩余发行额度均满足时，`claimable` 才为 `true`；领取弹窗 `popupEligible` 在此基础上继续应用已配置节奏。额度耗尽时两者均为 `false`，不虚报可领取。
- 全局额度耗尽只阻止新增领取，不删除、撤销或变更本用户已经形成的 grant。原 `grantId`、`AVAILABLE` / `USED` 等状态继续保留，已有券是否可用由其原有效期、状态及结算合同决定。
- 读取结果不预占发行额度。GET 之后若其他用户领走剩余名额，POST 仍可能返回 `H7_VOUCHER_INVENTORY_EXHAUSTED`；发券命令继续以券定义行锁、全局额度校验和幂等约束为最终裁决，不能因为 GET 曾可领而越过额度。
- 发券命令获得券定义行锁后，必须读取当前上限和当前全局发行数量，不能继续使用等待该锁前形成的事务快照。即使外层事务为 `REPEATABLE READ`，两用户并发领取限额 1 的券也只允许一个新 grant，另一请求返回额度耗尽；重试按原幂等合同恢复。此要求同时覆盖用户领取、转盘发券和晋升奖励发券，不仅适用于单一 App 入口。
- 查询只读取本人持券状态，发行数量只用于服务端判断，不扩大其他用户 grant 的可见范围。测试 sandbox 沿用自身 run 隔离事实，不混用正式发行状态。

验收：限额 1，C 正常领取唯一 grant 后，D 刷新读到不可领取且无领取弹窗；D 实际领取仍拒绝，C 原 grant 可见且有效。无限发行与仍有剩余额度保持原路径。自测与发布后 TEST 实景验收分别记录，不以单元测试代替用户实际操作。

并发验收：正常创建新的限额 1 券，两名合格用户同时领取，核一个成功新 grant、一个额度耗尽，胜者重放同 grant、败者重试无增发；再覆盖已领券正常报价/未付建单/取消恢复，核新增锁不会造成不可恢复的领取或核销失败。#648 的旧版本真实双成功证据与修复后验收分别保留。
