- 只把源码核查称静态证据；单元测试、MySQL事务、HTTP联调、fixture浏览器、真实服务浏览器和生产分别记录。

## 4. 最小验证实验与证据标准

先做R08与R09的失败测试：证明旧重放会重新分配封顶、简单双入口会重复L1；然后验证新订单快照和单入口能消除反例。再用R06逐位差分证明L2–L7金额未变。退款以R19–R23的真实MySQL事务为核心，不用仅mock通过替代。

测试环境使用现有隔离本机MySQL、Redis和端口，记录库名、runId、四仓HEAD和实际服务源码。只用明确隔离资料，不向生产写配置或资金。前端HTTP fixture验证交互，另以真实API与数据库证明审批持久化和钱包事实。

资金每个场景保存：原订单/凭证、模式及层预算、两币佣金事件、钱包前后余额、入出账本、消费回执、实际追回与欠额；刷新后的API与UI一致。源码、数据、服务或证据变化后重跑受影响检查，不沿用旧报告hash。

最终验收包括后端相关单测与数据库场景、PC全量verify、App/H5完整verify和各自来源证据、独立Java/TS及操作友好审查、done-review六维。未执行项写未执行，不能将方案评审通过称为功能完成或上线。

## 5. 墨菲预演

最危险的失败依次为：旧七层重复消费超cap、原L1与新purchase同时发、关拆分重新走旧规则重复发、缺价换上级、退款漏深层或F5补发、两个币半成功、配置并发生成混合政策、App恢复页面却API漏L1、USDT历史累计被称可提现、导出与净收入/榜单不同账。

每个风险均对应上表反例。任何未解决P1都阻止发布；代码可编译、页面有内容、单独一仓通过均不代表此跨仓资金规则完成。
