# Cregis PROVIDER payout

This change supports only USDT-BEP20. D5 fees, eligibility, address cooling, approval and reserved gross amounts keep their existing rules. App uses its existing `enabledNetworks` contract; no App or D2 UI change is required.

## Normal activation

The provider transport remains off by default. Public TEST retains its existing root-owned pay-in approval and additionally requires `/srv/nexgrid/secrets/cregis-payout-approved` with the exact public approval tag `PROVIDER` followed by one newline. The trusted deployment broker validates both approval files and emits `nexion.deployment.cregis-payout-approved=true` plus `nexion.finance.cregis.payout-enabled=true`. No other public TEST policy pin changes. Updating the installed trusted broker and creating approvals belong to the authorized Root deployment workflow; editing this repository does not activate the host.

The existing normal server configuration supplies `NEXION_CREGIS_MODE`, `BASE_URL`, `CALLBACK_BASE_URL`, `PROJECT_ID`, `API_KEY` and `BSC_RPC_URL` under the `NEXION_CREGIS_` prefix. The archive RPC must support real historical `eth_getLogs`, transaction receipts, canonical block reads, chain ID and token calls. Never put secret values in this document or an API response. `NEXION_CREGIS_DEPOSIT_CONFIRMATIONS` retains its existing minimum 15.

The independent database payout bit starts off. D1's existing switch-case proposal/check endpoints use `finance_d1_channel_manage`, expected version and a different checker. `payoutEnabled` is optional on proposals; omitted/null preserves the locked current bit. Opening or restoring a bit requires the existing risk and recent complete reconciliation qualifications. An independent close retains the other two bits and does not require a fresh reconciliation. Emergency-off still closes all three. Status and App policy expose `providerPayout` with `configured`, `enabled` and nullable `disabledReason` (`NOT_CONFIGURED`, `SWITCH_OFF`, `RISK_HOLD`, `RECONCILIATION_REQUIRED`). Read APIs do not send or settle funds.

## Submission, recovery and settlement

Only new REVIEW_PASSED orders can be claimed for provider sends. A stable original business key and provider intent are persisted before HTTP. Expired PROCESSING is treated as unknown, never as permission to create again. A known CID is independently queried against original key, recipient and net amount. A signed callback can recover a lost CID through the same independent query. The implemented vendor query requires CID: if both create response and callback are permanently missing, TX_ORPHANED and reserved funds remain for normal vendor investigation; there is no invented query-by-key endpoint or automatic second create.

Supplier status 6 is progress, not chain success. The observer reads the real successful receipt, exact USDT token Transfer, recipient and net amount, receipt/log transaction and block identities, canonical block and at least the existing 15 confirmations. Only then does the original finalizer atomically settle reserved gross funds, retain required proof audit and payout ledger, bind the funds-source journal and publish `withdraw.confirmed`. Confirmed transaction hashes are normalized to lowercase `0x` form for the existing single-use constraint. RPC failures, reorgs or mismatches leave funds reserved. A documented pre-broadcast rejection, independently queried and without success evidence, uses the existing atomic refund and `withdraw.refunded` event with the original K4 risk snapshot. Success evidence and failure refunds share the existing customer lock. Observation uses a 50-order keyset page with wrap-around, so long-pending orders do not permanently prevent later orders from being checked.

### Lost create response and lost callback

D2's withdrawal detail reads `GET /api/admin/finance/withdrawals/{withdrawalNo}/cregis` to distinguish provider submissions from historical channels. A provider `TX_ORPHANED` order can be recovered using the CID obtained from Cregis: `POST /api/admin/finance/withdrawals/{withdrawalNo}/cregis/recover`, `Idempotency-Key`, and JSON `{ "providerCid": "<positive int64 string>", "reason": "<10–300 characters>" }`. The operator needs both `finance_d2_read` and `finance_d2_withdrawal_approve` as an active administrator. CID remains a string in the browser to avoid numeric rounding.

The server queries Cregis independently against the original project, business key, recipient, currency and exact net amount. A customer/order lock then rechecks the immutable snapshot and binds only the same original submission, with required administrator audit and durable idempotency. A wrong CID or conflicting evidence changes nothing. The action resumes observation; it never creates another payout, directly marks success or refunds reserved funds. Keep the original idempotency key when a response is unknown, then refresh the original withdrawal detail.

Generic D2 actions cannot reset or refund a started provider attempt, and manual txhash confirmation cannot substitute for BSC proof. The sender's intent CAS and D2's order lock prevent freeze/reset races before HTTP. Existing bank settlement and local development simulation remain separate.

## Callback route

Exact POST `/api/cregis/callbacks/payout` and existing `/openapi/v1/withdrawals/cregis/callbacks/payout` share the signed durable callback service. Both deposit and payout callbacks require an exact source IP from `NEXION_CREGIS_CALLBACK_SOURCE_IPS`; the payout route takes the socket peer resolved by the existing trusted-proxy configuration. Only an accepted durable receipt returns literal `success`; invalid callbacks return `rejected`, and failed durable writes cannot acknowledge success. Provider callbacks use the existing callback rate budget and exact Geo exception. Root must verify the actual public edge forwards the configured callback path to this backend; there is no PC public proxy in the current source.

The official [wallet payout query](https://developer.cregis.com/api-reference/request-apis/payout/payout-query) requires CID. The documented response does not require CID; when a response does include it, the adapter strictly verifies the integer matches the requested CID. The official [payout notification contract](https://developer.cregis.com/api-reference/callback/payout) supports re-pushing a real failed callback from the project's callback records. This does not provide an unconditional test event without a real transaction.

## Historical catch-up

`NEXION_CREGIS_CHAIN_SCAN_MS` is an existing ordinary scheduler setting (default 300000 ms, no explicit code lower bound). `NEXION_CREGIS_CHAIN_SCAN_BLOCKS` defaults to the original 500 blocks and can follow the actual archive endpoint's tested range capability. Its value must exceed the existing 100-block overlap to advance. The scan retains `from=max(first,cursor-100)` and `to=min(cursor+N-101,finalized)`; default 500 therefore still advances net 400, while 20000 advances net 19900. RPC errors do not advance the cursor. Confirmation count, 60-address limit, 8-second RPC timeout, 1 MiB response limit, cursor CAS, observation transactions and full-reconcile watermark rules are unchanged.

Full reconcile also invokes the same scan. Root may temporarily adjust the interval and batch within the authorized archive token's actual capability, retaining the existing single scheduler worker and avoiding overlapping manual full reconciliations. Revert the batch to 500 or remove the override to restore the original behavior. Do not jump the cursor or manufacture empty results. No new catch-up framework or test timing policy is added.
