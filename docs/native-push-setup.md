# Android/iOS native push setup — first batch

This change is code and configuration preparation. UniPush has not been opened for this application. External sending and scheduling default to **disabled**. Local controlled tests do not prove TEST deployment, provider delivery or either platform's real-device acceptance.

## Official transport and prerequisites

The Java backend calls an authenticated URLized uniCloud cloud function. That function uses the official `uni-cloud-push` extension and `uniCloud.getPushManager({appid}).sendMessage(...)`. It does not call the UniPush 1/GeTui REST API.

Official references checked 2026-10-29: [UniPush 2 overview and native setup](https://uniapp.dcloud.net.cn/unipush-v2.html), [uni-cloud-push server API](https://doc.dcloud.net.cn/uniCloud/uni-cloud-push/api.html). The latter specifies `push_clientid`, `request_id` (10–32 chars), `force_notification`, `settings.ttl`, and per-CID result statuses. A provider's `successed_online` / `successed_offline` is an acceptance/downstream handoff receipt; neither proves notification display or device delivery.

Before a separately authorized TEST activation:

1. Open UniPush 2 for the actual DCloud App ID; select its uniCloud space. Bind the native App to that exact App ID. Supply the actual iOS bundle ID and APNs push certificate/entitlement, Android package signing and relevant vendor credentials. Rebuild the native App/custom debug base with UniPush 2 and offline push. A standard debug base cannot establish offline push acceptance.
2. Copy `integrations/unipush2/native-push-bridge/` into that space's cloud-functions directory. Keep its `package.json` `uni-cloud-push` extension. Install the two collection schemas from `integrations/unipush2/database/`; server-only permissions deny all client access. `_id` must retain its database unique constraint. Create a TTL index on `native_push_nonce.expiresAt` where supported, or periodically remove expired nonce records with a server-side maintenance job. Never delete unexpired nonces. Retain delivery receipts while a delivery could be retried; do not TTL them independently of backend delivery retention (at least 90 days recommended).
3. URLize only the `native-push-bridge` function as a POST endpoint using an HTTPS URL. Do not expose an unauthenticated direct push function. Set its server environment: `NATIVE_PUSH_APP_ID` (the DCloud App ID), `NATIVE_PUSH_BRIDGE_SECRET` (a separately generated random secret of at least 32 bytes), `NATIVE_PUSH_ENABLED=false` until activation. No secret belongs in manifest, source, PRD or reports.
4. Apply `scripts/migrations/20261029_business_notifications.sql` and `scripts/migrations/20261029_native_push_transport.sql` before the backend scheduler. The migration creates three dedicated tables; it does not rewrite `nx_notification.push_status` or backfill historical native deliveries. The cutover row records the current maximum inbox ID exactly once; rerunning the migration preserves that boundary.
5. Configure the backend properties below from protected runtime configuration. Verify current profile/audience, schema, URL and App ID separately for TEST. Turn on bridge and backend sending only for the intended TEST acceptance run. No production activation is included.

The health component `nativePush` reports `channel=DISABLED`, `MISSING_OR_INVALID_CONFIG`, or `CONFIGURED`, with scheduler state. Intentionally unopened push returns `UNKNOWN` component health so it does not stop the existing application. Configured means configuration presence, not a successful external connection. If scheduling is enabled while sending is disabled/misconfigured, queued deliveries become visible `BLOCKED` rows, retrying configuration every five minutes without consuming the five-send retry allowance. A migration/schema failure is a scheduler error and must be resolved before enabling it.

## Authenticated client contract

All routes use the ordinary bearer/session authentication. The backend obtains user ID and session context solely from authentication, never a body user ID.

* `PUT /api/me/push-installations/{installationId}` with `{clientId, platform:'android'|'ios', permission:'granted'|'denied'|'unknown', appVersion}`. Requires an authorized **APP** session with exactly that installation ID persisted by the existing login system. The client must create and persist a cryptographically random 32-byte binding proof before the first PUT and send it as `X-Push-Binding-Token` (43–128 URL-safe characters; 64-char hex is supported). This makes a lost first response safely retryable. Response is `ApiResult<Void>`.
* `DELETE` the same route, same token header, before logout when possible. It requires the current owning APP session and proof. A delayed old-account delete cannot remove a new-account binding. Keep the token across logout/account switches. Logout/session revocation or replacement also blocks pending send even if DELETE fails.
* `GET /api/me/push-notifications/{notificationId}` returns `ApiResult<{notificationId,route}>` only to the current owning user with a live authenticated session. The payload is just a numeric notification ID; it does not carry a trusted route. Device and conversation targets are checked again for current ownership. Allowed routes are exact `/pages/me/trial`, `/pages/earn/device-detail?id=<numeric-id>`, `/pages/me/wallet-bills`, `/pages/me/security`, `/pages/support/chat?cid=<conversationNo>` according to the business kind. External URLs, extra query fields and unknown routes are rejected. Business page APIs must still enforce their own access checks.
* `POST /api/me/push-notifications/{notificationId}/opened` with `{installationId}` returns `ApiResult<Integer>`. Requires current APP installation, current binding epoch/user/session chain, owning notification and accessible target. It records `opened_at` once on that installation's attempted delivery (`attempts>0`, status `SENDING`, `ACCEPTED`, `UNKNOWN`, `RETRY` or `FAILED`). A genuine click can arrive after a lost acceptance response or ambiguous timeout; this records the separate open evidence while preserving provider status and `accepted_at` unchanged. Unattempted, cancelled, blocked and invalid-CID rows cannot acquire an open receipt; old user/epoch cannot update the current binding's receipt. Opening an inbox row never manufactures provider acceptance or device delivery.

Both installation ID and CID are ASCII URL-safe strings (8–128 chars). The proof hash is SHA-256 and compared in constant time. An existing CID cannot be claimed by another installation ID using request-body knowledge, even if the old installation is inactive. Updating the same installation across accounts requires its persisted proof and the new account's authorized APP session. Losing the private proof while retaining the same CID requires an operator-reviewed binding reset or a genuinely new native installation/CID; the API provides no insecure takeover fallback. This establishes continuity for existing bindings; it is not provider attestation of a never-before-seen CID.

Every user/session-chain/CID/permission/platform change, reactivation and unbind advances a binding epoch and cancels pending old deliveries. Idempotent PUT/app-version-only changes keep the epoch and bound time. Before sending, the worker locks the account and installation and holds these locks through its bounded HTTP call, checks epoch, permission, account status/blocklist/audience, live unexpired APP session, idle TTL, fixed current APP session context, no newer installation login on another chain, notification retention, and current notification preference. New registrations cannot commit while the old binding is in the final send section. Refresh rotations within a live chain remain valid. An already accepted provider task cannot be recalled by this code; the bridge uses the official one-hour offline TTL with generic content and reauthorization on click. A generic notice accepted before an account switch can still arrive later; its private target remains protected by current ownership checks.

## Discovery, delivery and recovery

The dispatcher discovers only `DEVICE_EXPIRY`, `DEVICE_ALERT`, `FUNDS_RESULT`, `ACCOUNT_SECURITY`, `SUPPORT_REPLY`. A row must have a `NATIVE1:` business key or a matching same-user `nx_business_notification_fact` receipt, which allows existing HDPay/card-unbind inbox rows to be reused. It must be newer than migration cutover, at most 24 hours old, and allowed by existing system notification preference (critical notifications remain mandatory). Ordinarily it must also be newer than the installation binding. The sole recovery exception is a recent critical `ACCOUNT_SECURITY` message: after a legitimate same-user re-login, the valid newly bound current installation may receive it once even if it preceded that binding. This covers password reset/new-login races. The worker still requires a live/current authorized APP session; revoked, security-removed, logged-out and replaced installations receive nothing. No revocation bypass is introduced.

The migration cutover is fixed. Each tick rechecks the bounded 24-hour range using a unique `(notification_id,installation_id)` key. Advancing `MAX(id)` alone would lose lower notification IDs committed out of order; it is deliberately avoided. New bindings do not backfill existing messages except the narrowly bounded critical security recovery above; finance/device/support history remains excluded. No new accounting, settlement or business mutations occur during push dispatch.

`nx_native_push_delivery` states: `QUEUED` → `SENDING` → `ACCEPTED`, or `RETRY`, `BLOCKED`, `INVALID_CID`, `CANCELLED`, `FAILED`, `UNKNOWN`. Acceptance is independent from legacy inbox `DELIVERED`; `accepted_at` and `opened_at` are separate facts. Worker claims use row locks / `SKIP LOCKED`, a 60-second lease and random lease token. Stale workers cannot finish a newer claim. Stale claims can be recovered, retries back off and stop after five attempts, invalid/dormant CIDs deactivate their binding and retire other pending deliveries, and expired/revoked/reassigned bindings cancel before any send.

Java uses stdlib HTTP, HTTPS only, no redirects, 3-second connect / 10-second request timeout and bounded response size. Each bridge request signs `timestamp + '\n' + nonce + '\n' + SHA256(exact-body)` with HMAC-SHA256; the bridge checks a 120-second clock window, 4-KiB body and a unique persistent nonce receipt. The nonce is fresh for each HTTP retry. Each delivery also has a stable 32-character request ID and persistent bridge receipt, so successful retries return the original task without resending. Database failures prevent sending.

An SDK send timeout or process interruption after a send could have reached the provider. The receipt stays `SENDING` or becomes `UNKNOWN`; subsequent requests return `UNKNOWN` and do not automatically duplicate the send. A provider explicit failure or preflight read failure can retry. Investigate bridge receipt and provider task records before any operator reset of an `UNKNOWN` receipt; resetting without evidence can duplicate a notification. Exactly-once device delivery is not promised by either the provider or this integration.

The bridge preflights `getClientDetailByCid`, retires explicit `invalidCids`, and recognizes the documented per-CID online/offline result as acceptance; `successed_ignore` is a dormant/invalid CID. Empty/malformed success responses are `UNKNOWN`. Lock screens always receive a generic Chinese/English/Vietnamese message without balances, amounts, credentials, device identifiers, security details or support text. No caller-supplied title/body/URL is forwarded.
