# TEST paid-device cloud execution protocol

This extends the existing loopback-only `ct1` executor service. It executes declared TEST BGE-M3 texts on the cloud runtime and independently verifies the 3x1024 result before the original receipt and wallet transaction. It does not attest that the purchased physical GPU performed the inference.

Set `nexion.compute-task.test-cloud.fleet-enabled=true` and `fleet-started-at` to a fixed ISO local DATETIME before making the new purchases. The cutoff uses the database DATETIME clock that writes `purchased_at` and `activated_at`, obtained from `SELECT NOW(6)` on the target TEST database. It is not an application-clock or UTC timestamp: existing database and application clocks can differ. Do not change global timezone or historical rows to enable discovery. Both purchase and activation must be at or after the cutoff.

The original configured owner/device/instance/executor remains the legacy single-device identity. It is excluded from discovery. Free onboarding phones retain calibration, current installation/session ownership, and real phone telemetry; cloud heartbeats do not update phone telemetry. Old executors and active tasks without an execution manifest are excluded and are never automatically cancelled or imported.

`GET /api/test/cloud-executors/v1/instances?afterDeviceId=0&limit=100` authenticates the same token and uses `X-UVEL-Executor-Id: fleet` (omitting this header on this GET is equivalent). It is a read-only query. The limit is bounded to 1..100. The standard ApiResult data contains the existing TEST canonical metadata plus:

```json
{"instances":[{"executorId":"fleet-1234","ownerId":7,"deviceId":1234,"instanceNo":"NEX-...","taskConfigId":"TK-6","model":"bge-m3:567m","modelDigest":"sha256:...","executionKind":"TEST_BGE_M3_V1","specVersion":"UVEL_TEST_BGE_M3_V1","deploymentScope":"TEST","serverCanonical":true}],"nextAfterDeviceId":1234,"hasMore":false}
```

Advance using `nextAfterDeviceId` while `hasMore`; after the final page restart discovery from zero. A concurrent eligibility or immutable-binding conflict can filter a row between the query and response, so the cursor may exceed the last returned device ID, including on an empty page. When `hasMore=true`, it must advance beyond the request cursor. The entire paginated inventory should be collected before retiring disappeared instances.

Every existing next-task, heartbeat, task heartbeat, complete, and receipt request for a fleet instance includes `X-UVEL-Executor-Id` with that item's exact executor ID. No owner ID or instance binding is accepted from the client. The server resolves the identity from authoritative paid ownership or its immutable registration. `next-task` registers the binding in its original locked transaction; the owner/device/instance/config/model tuple cannot change afterward. Each instance has its own durable intent journal and unique next/completion idempotency keys. Request and result payloads otherwise remain the original single-device protocol.

Discovery and every live mutation enforce paid completed order entitlement, matching order/product and quantity, active ownership, purchase/activation cutoff, no deactivation, datacenter pause, runtime marker ownership, and no unknown active task. A positive purchase subtotal with nonnegative final amount includes a lawful fully discounted purchase; it still requires PAID/COMPLETED/ACTIVATED and an ORDER instance, so unpaid, refunded, and non-order gifts do not acquire fleet rights. A pending deferred deactivation can remain discoverable only with its own active manifest; it may finish the existing task, but cannot claim another one. Refund, ownership change, account disable, or pause removes live eligibility. Historical receipt reconciliation uses the registered immutable binding and task/receipt/proof records, so revoked live entitlement does not grant a new task and does not erase settlement evidence.

The generic App claim and automatic scheduler reserve this same new paid fleet before first discovery, preventing an inputless task from racing the executor. Persistently registered fleet devices remain reserved when `fleet-enabled` is turned off. A stored TEST BGE task kind also blocks ordinary completion after configuration removal.

Cloud selection validates the whole active E2 configuration first, then intersects eligible tasks with the installed `EM / BGE-M3` runtime and configured task ID. Device VRAM remains unchanged; Cloud Share retains its existing 8GB routing equivalent while displaying its original physical value. Low-memory devices with no eligible installed model remain rejected. The selected BGE task's original E2 price, E3 capacity adjustment, E3 cooldown, paid Cloud Share UVT conditions, unique receipt, and ledger transaction are unchanged. It never receives an IG/VG/LL/FT reward for a BGE result.

Apply `20261030_test_cloud_fleet_binding.sql` before enabling fleet mode; it is included in the normal startup migration manifest. Fleet registration and execution evidence contain no bearer credential. Recovery reconciles an uncertain sent request using its original immutable binding and receipt before making any new economic request.
