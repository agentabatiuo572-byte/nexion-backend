# SPEC-07：跨仓集成验收与发布准备

状态：未开始。依赖：SPEC-01至06均有当前代码证据。此步不可用子步骤“通过”代替整体链路。

## 范围和目标

在四仓最终候选提交上验证共同规格§5全部S01–S41及[SPEC索引](../SPEC-INDEX.md)补充回归；完成迁移和兼容演练，形成可交付提交组合。允许修改受影响实现和测试以修正发现；修补后重开最早受影响步骤，旧审查不能沿用。生产部署不属于本步骤自动授权。

## 验证层次

1. 纯规则：使用服务端可控时钟验证滚动窗口左开右闭、间隔恰好达到、超额后足够记录移出、历史未知、同安装和真实替换区别。不得用客户端改系统时间当服务端时间验证。
2. 隔离数据库：真实事务并发与唯一性，两个App接管、首绑并发、绑定/计次/授权消费原子性、关闭/签发/撤销竞争、失败回滚和持久幂等缓存过期。验证过程重启服务后仍可读回原事实。
3. API合同：App/H5权限、旧会话与refresh拒绝、伪造组别、旧版本缺字段、C5对象越权/失权、E6四参版本冲突、各未知结果恢复。记录实际请求与脱敏响应，不能只断言页面Toast。
4. UI实景：App、H5、后台按同一业务序列执行；验证刷新、返回/取消、网络失败、输入保留、disabled原因和用户文案。App/H5覆盖现有三语、明暗主题及窄屏；后台按当前支持的语言、主题和布局验收，不扩展后台国际化范围。每个改动页面由未编写该页的审查者检查人工操作友好性。
5. 原生联调：至少两部支持运行的Android安装加第三安装并发/切换，以及不能运行手机任务的原生入口验证单点归组。APP手机校准、真实心跳和任务截止须由原生+真实dev后端证据支持；H5/Playwright的native fixture只作前端合同测试。

## 必须走通的端到端链路

| INT-04 | 次数不足→App协助申请→客服关联→C5部分/完整豁免→App确认 | 未豁免规则仍拦；用户主动提交；特批仅成功消费且真实计次 |

## 工程门

- 后端：根项目 `mvn test`；对本轮迁移/并发执行隔离数据库验收。单元测试绿色不代表MySQL真实锁与事务已证明。
- App：按仓库AGENTS执行候选暂存树full验证、提交及提交后干净树 `npm run verify`；生产构建与受影响真实页面核验同时保留。
- H5：按`docs/app-h5-sync.md`完成候选plan/apply、App提交后repin、H5候选验证/提交；最终源和目标各自full以及 `npm run sync:h5:check` 使用同一提交组合。
- 后台：先按SPEC-00显式设置并读回`NEXION_APP_ROOT / NEXION_BACKEND_ROOT / NEXION_PRD_ROOT`和Git基线，再跑`npm run verify` full。必须同时检查FAIL、NOT-RUN、SKIP、SCOPED-SKIP、innerSkipped均为0且没有DEGRADED；退出0或record的pass不足以证明完整。不能拿`--static`或acknowledged skip代替；受影响E6/C5真实后端操作实景另验。
- 独立review至少覆盖会话/权限/并发、界面可操作性、业务边界和跨文档一致性；P0/P1主线回源，所有本任务已证实缺陷修复并重验，不能只换测试断言。

按各仓既有门运行，不绕过hook、不添加临时known-red、不以`--no-verify`或逃生阀推送。共享输入变化后旧full证据失效。重测试只针对实际变化、失败或最终必须门，不反复无理由跑全量。

## 迁移、发布次序与恢复

先部署准备可向前兼容的数据结构与真实事件采集能力，再验证服务端新契约和旧客户端处理，随后配套客户端/后台；规则全面生效必须确认服务端鉴权、计次与事务已可用，不能先发仅前端限制。具体发布批次需部署负责人独立审批。

演练旧会话迁移归组、未知历史可靠覆盖起点、显式配置差异发布、缺新字段拒绝及最小支持客户端。不要从当前绑定时间捏造30天历史。回滚应用不能删除真实成功事件、消费事实、审计或新建绑定；若回退版本会恢复多App执行/绕过次数，禁止直接回滚该组合，保留最后兼容版本并按现有受控配置限制新换机。

INT-09：每一S编号都有测试名/实际提交/证据/结论；不得仅写“同SPEC通过”。缺真机、服务端或数据库则列未验证，保留目录，不进入08清理。
