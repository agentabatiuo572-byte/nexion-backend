# Direct purchase payment contract (17/18)

The existing purchase endpoints remain WALLET commands protected by the payment PIN. External purchases use POST /api/app/purchase-payment-quotes, POST /api/app/purchase-payment-intents and authenticated owner GET/lookup. Methods are HDPAY_BANK, CREGIS_USDT_BSC and CREGIS_USDT_ERC20; kinds are ORDER_PAY, TRIAL_CONVERT, TRADE_IN, CAPACITY_REPLACE and CAPACITY_KEEP. ORDER_PAY includes ordinary, promotion, quantity and bundle pending orders.

The server binds owner, kind, original payload, method/network, business pricing, fee version and expiry. An intent permanently binds the original command key and quote. Unknown HDPay creation can only query that intent's original merchantOrderId. Zero rounded external principal is rejected with ZERO_PAYMENT_REQUIRES_WALLET.

An explicit HDPAY payment time must not precede the original intent's created_at; retain that original paidAt and use PAYMENT_BEFORE_ALLOCATION review when it does, blocking both automatic delivery and explicit revalidation delivery.

External subtotal and each payable fee are Decimal with two digits, HALF_UP. The original business amount is preserved as businessAmountUsdt (six digits), the two digit collection principal is subtotalUsdt, and roundingAdjustmentUsdt records subtotal minus business amount. The receipt retains original amountUsdt and separately returns paymentSubtotalUsdt. Channel fees apply once to discounted subtotal; BSC has a separate networkConfirmFeeUsdt, HDPay has none. Supplier actual fees are recorded independently when known. HDPay freezes the current authoritative VND exchange rate once and collects integer dong. USD/USDT 1:1 is not VND conversion authority.

Actual delivery joins the existing purchase transaction and rechecks ownership, applicable source version, replacement and trial rules, price, stock, listing and device capacity. Every purchase kind uses F4b monthly quota when a tier applies. Replacement purchases and ordinary order lines that still need to incur E1 use the lifetime purchase gate. Trial conversion uses F4b only. The verified payment scope skips PIN checks and wallet principal debits/ledgers, while preserving legitimate independent trial rewards. Durable intent receipt, order link, provider payment record, inventory/devices, events and required delivery audit commit together. A failed delivery rolls back and enters D1 review. Trial accrual pricing freezes its business quote instant; elapsed time alone cannot alter a quoted payment.

BSC purchase creation never calls address/create. It proves a currently unassigned pool address belongs to the configured project and has zero provider/chain balances, binds a fresh canonical allocation block/hash, then atomically changes purpose to PURCHASE_DIRECT and state to DIRECT_PURCHASE with the new intent. The address remains permanently dedicated and is never allocated to a wallet or recycled. An unavailable pool fails before creating an intent. The existing replenishment worker remains responsible for provider address creation and unknown allocation recovery.

Signed callbacks, complete provider history reconciliation and periodic direct-address scans resolve direct ownership before wallet topup handling. Only exact provider and confirmed BSC Transfer proofs authorize fulfilment. Old transfers at/before allocation, short/over/late payments and additional arrivals remain finance exceptions; there is no automatic wallet credit or refund. Already delivered receipts survive later additional arrivals/reorg exceptions. Positive canonical-chain reorg evidence closes the existing Cregis risk gate and marks review; RPC unavailability alone does not establish a reorg.

D1 policy and record APIs use existing finance permissions, CAS, reason and durable idempotency. Manual revalidation uses gate -> intent lock order and one command transaction for CAS, observation, delivery, audit and command result. An audit failure rolls the entire manual command back. Cregis assignment/credit switches and risk gate apply to direct purchases. Policy output publishes authoritative bounds. Cregis minimum remains under its existing A2 maker/checker publication; this policy API cannot change it.

HDPay wallet recharge requests require positive integer principal at or above the D1 channel minimum. BEP20 and ERC20 recharge discoveries at or after the B84 cutover credit the original amount, up to six decimal places, minus the snapshotted recharge fee once both proofs and confirmations pass. The shared cutover is stored once in the application database timezone. Discoveries from the original integer-rule start up to the cutover retain the integer rule. Earlier discoveries follow their historical rule. Below-minimum arrivals remain in DUST_HOLD. Existing snapshots and dedicated direct address handling keep their original terms.

Existing attributed `REVIEW_HOLD` records still require D1 dual-admin approval. Approval requires the network and credit switches to be open and the original principal to meet the snapshot minimum. The credit is the original gross amount minus the snapshotted recharge fee, with the original decimal precision. Below-minimum arrivals follow the existing `DUST_HOLD` process.
Legacy wallet request DTOs explicitly reject any supplied paymentMethod other than WALLET at HTTP binding, even when a valid PIN is supplied; omission retains WALLET behavior. External payloads therefore cannot silently execute a wallet purchase.
External channel fees are fail-closed until each channel is explicitly configured. The policy publishes configured:false with null fees for an unknown channel. Partial policy PATCH accepts one or two complete channels, only marking those submitted entries configured; explicit zero is a valid approved free policy. New quotes/intent creation reject missing fee configuration, while already initiated intents preserve their snapshots.

## Ordinary order USDT wallet top-up (B84)

`NEXION_ORDER_USDT_TOPUP_ENABLED` is off by default. With it enabled, the App policy at `GET /api/app/purchase-payment-policy` includes `orderPayUsdtRoute: "WALLET_TOPUP"`. BEP20 and ERC20 availability comes from `GET /api/deposits/policy`. The direct-payment `channels` still cover the purchase types that use that rail.

Ordinary `ORDER_PAY` quotes and new intents using BEP20 or ERC20 then return HTTP 409 `ORDER_USDT_USE_TOPUP` after the existing business-intent, ownership, quote-use and idempotency checks. The rejection precedes pricing and address allocation. A command replay with the same key and quote retains the original intent contract. Reusing the key with another quote returns `IDEMPOTENCY_KEY_CONFLICT`. Historical intents retain their address, observation, settlement and recovery rules. Bank payments, trial conversion and trade-in continue through their existing entries.

`GET /api/app/orders/{orderNo}/usdt-topup?network=BEP20` is an authenticated owner read. It returns `state` (`PENDING`, `PAID`, `CLOSED`), `canonicalStatus`, `payable`, `deadlineAt`, `amountDueUsdt`, `walletAvailableUsdt`, `shortfallUsdt`, `minDepositUsdt`, `depositFeeUsdt`, `suggestedTransferUsdt`, `blocker`, `openIntent`, `reviewReason`, `paidAt` and `paidAmountUsdt`. Amounts are decimal strings. A zero-value order has zero shortfall. The effective deadline uses the earlier of the wallet-payment TTL and activity deadline. The suggested transfer is the greater of the current minimum and the shortfall plus recharge fee. It is zero when the shortfall is zero.

For pending orders, the first matching blocker is an existing open intent (`OPEN_INTENT`, with its owner-scoped `intentNo`, `paymentMethod` and `paymentAllowed`), financial review (`NEEDS_REVIEW`, `FINANCE_REVIEW`) or a retired bank session (`NEEDS_REVIEW`, `BANK_SESSION`). Completed and closed orders return `NONE` and have no payment action. Read failures return HTTP 503 `ORDER_TOPUP_READ_FAILED`. An invalid or missing network returns HTTP 400 `ORDER_TOPUP_NETWORK_INVALID`. An absent or other user's order returns 404 `ORDER_NOT_FOUND`. The read does not place orders or allocate addresses. Address display still requires a successful selected-network address read with credit permission. The user confirms the existing wallet payment command using the PIN.

`GET /api/app/wallet/bills` includes `deposit` on the caller's inbound USDT chain top-up rows. Its fields are `network`, `txHash`, `grossAmountUsdt`, `feeUsdt` and `creditedUsdt`, sourced from the linked original event. A missing or ambiguous link yields `null`. The existing ledger amount remains the net credit. Other bill categories and the cursor and offset contracts are unchanged.

## Replacement source check (B57-BE-02)

For `TRADE_IN` and `CAPACITY_REPLACE`, `POST /api/app/purchase-payment-quotes` and `POST /api/app/purchase-payment-intents` check that the old device runtime has drained. Active simulated devices with a current task or a scheduled next action are eligible only for wallet replacement. While an external payment is pending, a simulated task can credit earnings and move a trade-in across a credit tier. A rejection creates no quote or payment intent for that request, allocates no collection address and creates no provider payment order. If intent creation is rejected, its original quote remains under the existing validity rules.

| HTTP status | Response `message` | Reason |
| --- | --- | --- |
| 409 | `CAPACITY_REPLACEMENT_SOURCE_CHANGED` | For `CAPACITY_REPLACE`, the requested `payload.sourceDeviceId` must match the current replacement candidate. Both endpoints verify the match before checking the device runtime. |
| 409 | `SIMULATED_DEVICE_BUSY` | The simulated device runtime has not drained. |
| 409 | `COMPUTE_V2_DEVICE_BUSY` | The Compute V2 device runtime has not drained. |
| 409 | `COMPUTE_V2_LEGACY_REQUEST_UNRESOLVED` | An earlier execution request is unresolved. |
| 409 | `COMPUTE_V2_OWNER_CHANGED` | The runtime ownership record no longer matches the source device and owner. |
| 503 | `COMPUTE_V2_RUNTIME_RECOVERING` | The Compute V2 runtime is temporarily unavailable. Retry the request. |

Quote requests check payment channel readiness before checking the device. Intent creation rechecks the device for a new intent. Replaying a successful creation with its original key and quote returns the existing intent. If a simulated device starts a task after intent creation, verified delivery can cancel the current uncredited task in the replacement transaction once the existing price, source and delivery checks pass. A changed price or another delivery failure still sends confirmed payment to `MANUAL_REVIEW`.

## Purchase quota checks (BUG-549 phase 1)

For bank and USDT payments, both quote creation and new intent creation read the F4b tier, buyer requirements and active usage for the current business month. The requested quantity must fit the remaining monthly quota. A quota rejection creates no quote, intent, collection address assignment or provider payment order for that request. A rejected intent request leaves its original quote subject to the existing validity rules.

`GET /api/app/purchase-payment-intents/snapshots/{intentNo}` is the read-only counterpart for that recovery: it loads the row for the authenticated owner only and returns the same view projection without `refresh`, so it never queries the provider, writes reconciliation state, closes the intent or delivers a purchase. The existing `GET /api/app/purchase-payment-intents/{intentNo}` keeps its active refresh and delivery path unchanged.

### Original external trial checkout (B104)

New `TRIAL_CONVERT` quotes for bank and USDT payments include `trialPurchaseBreakdown`. The payment intent retains the same object, including for owner reads by the original `intentNo` after quote expiry. It contains `productNo`, `productName`, optional `productSubtitle` from the product's default catalog tagline, and six-decimal USDT strings `priceUsdt`, `promoDiscountUsdt`, `offsetUsdt`, `earlyDiscountUsdt` and `amountUsdt`. `priceUsdt` is the original trial product price used by the accepted conversion quote. `amountUsdt` is the exact discounted business principal before collection rounding and fees. The existing collection fields still give the quoted principal, fees, currency and total to collect. Other purchase kinds and historical quotes or intents without this object omit it.

For the same owner and purchase kind, an in-progress intent takes precedence over channel readiness, address selection, pricing and eligibility checks. It returns HTTP 409 `PURCHASE_PAYMENT_EXISTING_INTENT_REQUIRED` with `data.intentNo` set to the verified in-flight intent of that same owner and business (the field is omitted for `ORDER_PAY`, which keeps its previous response). A delivery receipt establishes a completed purchase even if later financial observations move the intent to `MANUAL_REVIEW`. `ORDER_PAY` matches by order number. `TRADE_IN` and `CAPACITY_REPLACE` match by source device and canonical target product, and `CAPACITY_KEEP` matches by canonical target product. A target ID and a product number resolve to the same identity when they name the same product. Trial conversion matches by the trial claim and checks the requested product against the original intent's stored product. A refreshed amount or quote version does not change that identity. Intent creation first handles original-key replay and quote reuse, checks for an in-progress intent before candidate address selection, and repeats those checks in the creation transaction.

`ORDER_PAY` uses the stored product and quantity for a single order and the stored product and quantity for each bundle line. Quantities for the same F4b tier are summed. E1 evaluates the current SKU gate with the buyer facts used at settlement, then compares each eligible line's quantity against the remaining lifetime quota. It skips legacy orders with `inventory_reserved` true or null and lines already marked `lifetime_quota_reserved`. The three replacement kinds check one unit of the canonical target from their existing server quote and retain the quote's E1 evaluation. Trial conversion checks the current conversion switch and the claim's actual conversion deadline. It checks one unit of the product resolved from the claim and requires the requested product to match.

## Purchase quota reservations (BUG-549 phase 2a)

With `PURCHASE_QUOTA_HOLD_ENABLED=true`, new successful intent creation freezes each purchased line's quota decisions and holds all applicable units in the same transaction. F4b counts held units against the business month at creation. E1 counts held units against the SKU's gate generation at creation. A bundle reserves every line together. A legacy order line with pre-consumed E1 keeps its original lineage and ownership. A successful quota check with no applicable quota still writes a reservation snapshot. The stored snapshot governs subsequent observations and delivery.

A verified payment made before its effective deadline and observed before grace ends uses the quota committed at creation. Delivery keeps the other applicable commerce checks and may enter D1 if one fails. A successful delivery converts reserved F4b usage to sold in the original month and converts held E1 to sold in the same generation. If the E1 generation changed, the fulfilled line keeps the original generation and the current generation's sold count stays as published. A recoverable D1 delivery failure keeps its hold and can consume it on a successful manual revalidation.

An unpaid intent releases its own held quota once when it commits expiry after the grace window, or when an unconfirmed intent first commits HDPAY status 5. A query outage alone keeps the hold. After the original identity has been queried at grace end, an intent with neither confirmation nor a receipt can expire even if the query is unresolved. A confirmed payment with temporarily unavailable proof keeps its hold. Cash received after release goes to D1 review under `PAYMENT_LATE_REVIEW`, including a status 5 followed by status 3 within the original window. Neither automatic nor D1 delivery can use a released reservation. Releases keep the usage and E1 ledger records for reconciliation.

A SQL NULL `quota_reservation_json` identifies a legacy intent, including one created with the switch off. Its full quota check remains at settlement. The switch defaults to false and applies to new reservations only. All purchase paths keep counting existing reservations, and delivery, release and recovery continue using stored snapshots. Apply `20261121_purchase_quota_holds.sql` through the startup manifest with this release. Enable creation after successful migration and after all purchase writers, delivery workers, observers and D1 revalidation run a compatible version. With outstanding reservations, keep writers on a compatible version or stop those writes during rollback.

The team quota response reports `soldThisMonth`, `usedThisMonth`, `pendingThisMonth` and `remaining` separately. `available` also requires positive `remaining`. Accurate remaining numbers require a team-page update that reads `remaining` directly. Installed versions that subtract sold from the cap can display a higher number.

## Refund closeout (BUG-549 phase 2b)

`POST /api/admin/finance/purchase-payment-records/{intentNo}/refund-closeout` requires D1 reconciliation permission, the administrator's `Idempotency-Key`, the current `expectedVersion`, and a 10–300 character `reason`. Use it after finance has completed a refund for a confirmed external payment with no fulfilment receipt. The command verifies the existing refund and records it without initiating a transfer or changing the user's wallet.

For bank payments the server re-queries the original HDPAY BANKQR order and requires refund status 4 with the original provider order and quoted VND amount. For USDT the request also supplies `refundTxid` and `refundLogIndex`. The server verifies the original single arrival and a later, finalized USDT transfer on the same network, from the intent's dedicated collection address back to the original token sender for the full received amount. A transfer log can close one intent. Partial refunds, multiple arrivals, and refunds sent from a different wallet require separate reconciliation.

The refund receipt, audit, quota release and eligible commerce-order closeout commit in the same transaction as the command result. The original payment evidence stays available. A pending ordinary order releases its own reserved inventory, vouchers and promotions and closes as `CANCELLED` with `close_reason_code=PAYMENT_REFUNDED`. The external payment record holds the refund receipt. This preserves first-purchase eligibility and excludes the unfulfilled order from completed sales and wallet refund reporting. Previously closed orders keep their prior stock release and return any voucher still bound to that order. A live or completed successor payment keeps its commerce order and resources. A still-active legacy bank session must resolve before closing a pending order. The original intent cannot deliver or re-enter the active-payment set. Any new USDT arrival on its old address is recorded for finance review without reopening the purchase.

Refunded payment records expose `refundStatus=REFUNDED` and an administrator-only `refundReceipt`. For existing App and PC parsers, the legacy payment status still projects as `MANUAL_REVIEW` with reason `PAYMENT_REFUNDED_REVIEW` until those clients support refund closeout. The App response suppresses the original collection address and checkout link. The user's original payment command reads back as `REJECTED` with `PURCHASE_PAYMENT_REFUNDED` and cannot resume. The Java D1 endpoint is available for PC integration. Apply `20261124_purchase_payment_refund_closeout.sql` through the startup manifest before running this version.

## 2026-11-01 deadline and result contract

ORDER_PAY expires at its original order creation + 30 minutes, capped by an earlier promotion pay_by. Other kinds start with a deadline of 30 minutes from the immutable business quote instant. For TRIAL_CONVERT, the quote's payment deadline is capped at the claim's current conversion cutoff. Intent creation uses the earlier of the quoted payment deadline and the claim's current cutoff. Quotes remain valid for at most 15 minutes and expire by their payment deadline. A new intent's expiresAt is its payment deadline. Responses also return confirmationGraceEndsAt and paymentAllowed. After the effective deadline, user responses suppress paymentUrl/address; the permanent supplier/address association remains available for reconciliation. A submitted hosted page or blockchain address cannot be revoked locally.

Confirmation grace is a reconciliation window. It ends at the stored intent deadline + 3 minutes for BEP20, + 5 minutes for ERC20 and bank. It only accepts proof of payment strictly before the effective payment deadline, observed strictly before grace ends. Canonical chain block timestamps bind the same block hash as the verified Transfer. Provider timestamps must come from a documented supplier field, never the current query time. If bank success is first observed before the deadline, that observation proves an upper bound on payment time; it does not fabricate supplier paid_at. Success first observed after cutoff without payment-time evidence enters PAYMENT_TIME_UNVERIFIED; proof of late payment or observation at/after grace enters PAYMENT_LATE_REVIEW. HDPAY expirationTime, when verified and present, caps the payment deadline; grace remains anchored to the stored intent deadline.

For `TRIAL_CONVERT`, delivery uses the verified payment time to check the original claim's cutoff. The original quote, reward and slot apply even when reconciliation or a delivery retry finishes after the cutoff. A late or unverified payment stays in financial review with its original payment channel.

An unresolved external payment for the same trial claim holds the trial and its slot while payment expires or delivery completes. An unpaid attempt stops holding the claim when reconciliation marks it expired or failed. Confirmed payment eligible for delivery keeps the claim available for retry. Payment eligible only for financial review holds the claim through that rail's grace window or until its refund is recorded. During the hold, App cancellation, extension and wallet conversion return the business code `TRIAL_EXTERNAL_PAYMENT_IN_PROGRESS` without changing the claim, slot or payment. The expiry scheduler revisits the same claim as it rotates through due trials. The wallet conversion deadline and the H2 approval route for forced cancellation continue to apply.

The generic order expiry scheduler excludes every order with a direct-payment history, including failed retryable attempts, and rechecks that ownership under the shared user mutex. These orders are ended only by the fixed direct-payment deadline/grace observer; legacy generic TTL changes cannot shorten or extend their window. At grace end the direct observer queries the original identity first. If the intent is still unconfirmed and has no receipt, the observer commits expiry together with release of the intent hold, and closes the original pending order and releases its inventory, quota, vouchers and promotions when no successor supersedes it. An unresolved query is durably recorded as reconciliationStatus=QUERY_UNKNOWN. EXPIRED intents remain in scheduled original-identity observation, without a replacement collection or automatic refund. Each run reserves 50 observations for active commerce attempts (including EXPIRED failures while their canonical order remains PENDING) and a separate 10 for historical/review/delivered attempts; even failed queries advance their historical rotation position. Historical volume cannot consume the active batch. A query outage does not extend the payment window: after that original query attempt, timeout still closes the order; any subsequent arrival is reviewed. No new unpaid order increments inventory on release. A failed old attempt cannot cancel an active successor.

HDPAY 5 produces EXPIRED/PAYMENT_FAILED and permits a fresh quote/new command key before cutoff; the original key remains bound to the original intent. HDPAY 4 produces MANUAL_REVIEW/PAYMENT_REFUNDED_REVIEW, including a refund discovered after delivery. Neither refund detection nor late-arrival review creates wallet money or automatically reverses delivered devices. Finance handles these exceptions.

Durable result facts commit with DELIVERED, PAYMENT_TIMEOUT or MANUAL_REVIEW. The existing business notification projector creates one message and native push identity per result. Order timeout deduplicates across failed/retried payment identities; other results deduplicate per intent. Projection and provider retries never re-run financial settlement. Order notification routes use /pages/store/order-detail?id= and native resolve rechecks the authenticated recipient owns the order.

Apply scripts/migrations/20261101_purchase_payment_deadlines.sql through the normal startup manifest before deploying this service. It only appends evidence/result schema and aligns all unresolved ORDER_PAY deadlines on still-pending orders, including failed attempts; it does not enable channels, set fees, allocate external accounts or rewrite historical delivered receipts. Actual hosted-page integration and merchant timestamp semantics still require TEST verification; no synthetic fixture is a real merchant acceptance.

The [supplied HDPAY interface documentation](https://www.eolink.com/share/inside/7e6a0a7950f9c43ceee62f6085d8400a/doc/630897/detail/769055), reviewed on 2026-11-01, names pay-in query fields expirationTime and payTime (successful payment time). Creation returns only a hosted URL and documents no requested lifetime. The pay-in examples use local date strings without an offset and specify no timezone; a separate payout example cannot establish the pay-in timezone or the merchant's actual lifetime. The HTTP adapter maps only these two named fields when their own ISO date strings carry Z or an explicit numeric offset. Missing, null, malformed, nontext and offset-free dates remain unknown evidence. It never substitutes createTime, an undocumented paidAt alias, country or application timezone. The documented offset-free examples therefore still cannot authorize post-deadline automatic delivery or establish an earlier absolute provider expiry; existing manual review remains in force. Explicit-offset parsing does not establish that the merchant actually emits that format.
